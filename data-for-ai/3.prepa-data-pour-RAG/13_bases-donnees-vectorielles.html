MODULE 01 / 08

Fondamentaux des bases de données vectorielles

Après trois cours consacrés au contenu des chunks (découpage, vectorisation, nettoyage, enrichissement), ce cours s'intéresse à leur contenant : la base de données qui les stocke et les retrouve. Ce module pose les bases conceptuelles avant de plonger dans trois solutions concrètes.

LEÇON 1.1Qu'est-ce qu'une base de données vectorielle et en quoi diffère-t-elle d'une base classique

Une base de données vectorielle est un système de stockage spécialisé, optimisé pour une opération que les bases de données classiques (relationnelles ou documents) ne savent pas faire efficacement : trouver les vecteurs les plus proches d'un vecteur donné, selon une mesure de similarité (cours embeddings, module 3), parmi potentiellement des millions d'entrées.

Une base relationnelle classique (PostgreSQL, MySQL) excelle à retrouver des lignes qui correspondent exactement à une condition (WHERE departement = 'RH') grâce à des index B-tree qui organisent les données de façon triée. Ce mécanisme ne s'applique pas à la recherche de similarité : il n'existe pas d'ordre total naturel entre des vecteurs à 768 dimensions qui permettrait un tri unique et un index B-tree classique. C'est pour résoudre ce problème spécifique que les index approximatifs comme HNSW (cours embeddings, module 5) ont été développés, et que des bases de données entières se sont construites autour d'eux.

Base relationnelle classique Base de données vectorielle ──────────────────────────── ─────────────────────────── Recherche par égalité/plage Recherche par similarité ("departement = RH", ("les 5 vecteurs les plus "prix BETWEEN 10 AND 50") proches de ce vecteur requête") Index B-tree (tri total possible) Index ANN : HNSW, IVF (cours embeddings, module 5) Résultat : exact, déterministe Résultat : approximatif par construction (compromis vitesse/précision assumé)

Cette spécialisation n'efface pas pour autant les besoins classiques : une base vectorielle de production doit aussi filtrer par métadonnées (cours métadonnées, module 3), gérer des mises à jour, assurer une disponibilité — les modules suivants montrent comment chaque solution (Chroma, Pinecone, Weaviate) combine ces deux exigences, recherche vectorielle et fonctionnalités de base de données classiques, dans une seule offre.

Piège courant Penser qu'une base de données vectorielle est "juste une base de données avec une colonne en plus". La différence est structurelle : l'intégralité du moteur de stockage et d'indexation est repensée pour l'opération de plus-proche-voisin, ce qui explique pourquoi ce ne sont pas de simples extensions triviales à ajouter à n'importe quel système existant (même si certaines, comme pgvector, prennent justement la forme d'une extension — cours embeddings, module 6).

LEÇON 1.2Anatomie d'une base vectorielle : collections, index, payload

Malgré leurs différences d'implémentation, la quasi-totalité des bases vectorielles partagent un même vocabulaire structurel de base — comprendre ces concepts communs permet de naviguer rapidement d'une solution à l'autre (modules 2 à 4) sans repartir de zéro à chaque fois.

Collection (ou index, selon la base)

Un regroupement logique de vecteurs qui partagent la même dimension et généralement le même schéma de métadonnées — l'équivalent d'une table dans une base relationnelle. Chroma et Weaviate parlent de "collection", Pinecone d'"index" — une terminologie qui varie mais un concept identique.

Vecteur (embedding)

La représentation numérique du chunk (cours embeddings, module 1), stockée sous forme de tableau de nombres flottants — généralement 384 à 3072 valeurs selon le modèle utilisé.

Payload (ou métadonnées)

Les informations structurées associées à chaque vecteur (source, date, catégorie — cours métadonnées) stockées à côté du vecteur lui-même, consultables et filtrables sans recalcul de similarité (cours embeddings, module 6 ; cours métadonnées, module 3).

Identifiant unique

Chaque vecteur est associé à un identifiant unique (rappel du cours métadonnées, module 2, leçon 1) permettant sa mise à jour ou sa suppression ciblée sans affecter les autres entrées.

        "source": "guide_rag.pdf",

Une collection peut aussi imposer un schéma plus ou moins strict sur son payload — une différence philosophique majeure entre les trois bases étudiées dans ce cours (Chroma et Pinecone restent schema-less ou peu contraignants, Weaviate impose un schéma fort, approfondi au module 4).

Piège courant Créer une collection unique et fourre-tout pour l'ensemble d'un corpus hétérogène (documents RH, contrats juridiques, code source), avec des schémas de métadonnées incompatibles entre eux. Une collection devrait regrouper des vecteurs suffisamment homogènes en dimension ET en structure de métadonnées — l'hétérogénéité se gère plutôt via plusieurs collections ou un filtrage rigoureux (cours métadonnées, module 7).

La bonne pratique, comme pour le choix d'un modèle d'embedding (cours embeddings, module 4), n'est pas de mémoriser "la meilleure base du moment" mais de comprendre les critères de choix durables (module 5) qui restent valables au-delà des évolutions du marché.

Piège courant Suivre la popularité générale d'une base de données vectorielle sur les réseaux sociaux ou les classements génériques, sans la confronter aux besoins réels de son propre projet (volume, budget, équipe infra disponible) — un piège déjà rencontré à plusieurs reprises dans cette série (choix d'un modèle d'embedding, d'une stratégie de chunking).

LEÇON 1.4Où une base vectorielle s'insère dans un pipeline RAG

Cette série de cours a construit, module après module, un pipeline complet : extraction et nettoyage (cours nettoyage), chunking (cours chunking), embedding (cours embeddings), enrichissement de métadonnées (cours métadonnées). La base de données vectorielle est l'endroit où tout ce travail converge et se matérialise — le point de stockage qui rend ce travail réellement interrogeable.

Extraction/nettoyage → Chunking → Embedding → Enrichissement métadonnées (cours nettoyage) (cours (cours (cours métadonnées) chunking) embeddings) │ │ │ │ └──────────────────┴────────────┴────────────────┘ │ ▼ ┌──────────────────────────────┐ │ BASE DE DONNÉES VECTORIELLE │ ← CE COURS │ (Chroma, Pinecone, Weaviate) │ └──────────────────────────────┘ │ ▼ Recherche au moment de la question utilisateur (vectorielle + filtrage + hybride, cours embeddings module 7) │ ▼ Génération (LLM)

Ce positionnement en aval de tout le pipeline a une conséquence importante : la base de données vectorielle doit être capable d'accueillir fidèlement tout ce qui a été produit en amont — les dimensions du modèle d'embedding choisi (cours embeddings, module 4), la richesse du schéma de métadonnées défini (cours métadonnées, module 2 et 7), les besoins de filtrage identifiés (cours métadonnées, module 3). Un choix de base de données qui ne supporterait pas, par exemple, un filtrage suffisamment riche annulerait une partie du travail d'enrichissement de métadonnées effectué en amont.

# Le pipeline complet des 5 cours de cette série, jusqu'à l'indexation
texte_brut = extraire_et_nettoyer(document)               # cours nettoyage
chunks = chunker(texte_brut)                                # cours chunking
chunks_enrichis = enrichir_metadonnees(chunks)               # cours métadonnées
vecteurs = [embed(c["texte_pour_embedding"]) for c in chunks_enrichis]  # cours embeddings

# CE COURS : le point d'arrivée qui rend tout ce travail interrogeable
base_vectorielle.upsert(
    ids=[c["id"] for c in chunks_enrichis],
    vectors=vecteurs,
    payloads=[c["metadata"] for c in chunks_enrichis],
)
Piège courant Choisir une base de données vectorielle avant d'avoir stabilisé les décisions des cours précédents (stratégie de chunking, modèle d'embedding, schéma de métadonnées). Le choix de base devrait être informé par ces décisions en amont (dimension du vecteur, richesse du filtrage nécessaire), pas l'inverse — même si en pratique, une itération dans les deux sens reste possible et normale.

LEÇON 1.5Choisir entre managé, auto-hébergé et embarqué : les grandes familles

Avant d'étudier chaque base en détail, cette dernière leçon du module fondateur pose le cadre de décision le plus structurant : le mode de déploiement. Cette dimension, orthogonale au choix de la base elle-même, détermine une grande partie de l'expérience opérationnelle au quotidien.

Embarquée (embedded)

La base tourne directement dans le processus de l'application, sans serveur séparé à gérer — Chroma en mode par défaut en est l'exemple archétypal (module 2). Idéal pour le prototypage, les tests, ou des applications à faible volume qui ne justifient pas d'infrastructure dédiée.

Managée (fully managed / serverless)

Un fournisseur héberge et opère entièrement l'infrastructure — l'utilisateur n'interagit qu'avec une API, sans jamais se soucier de serveurs, de scaling ou de maintenance. Pinecone en est l'exemple le plus pur (module 3), mais Weaviate Cloud et Qdrant Cloud proposent des offres similaires.

Auto-hébergée (self-hosted)

L'utilisateur déploie et opère lui-même la base (souvent via Docker ou Kubernetes), avec un contrôle total sur l'infrastructure, les données, et les coûts — au prix d'une charge opérationnelle réelle. Weaviate, Qdrant et Milvus proposent tous des versions open-source auto-hébergeables (module 4, leçon 5 pour Weaviate spécifiquement).

Cette classification recoupe directement celle déjà vue dans le cours embeddings (module 4, leçon 2) pour le choix d'un modèle d'embedding propriétaire vs open-source — le même arbitrage coût/contrôle/opération s'applique, appliqué ici au stockage plutôt qu'au calcul des vecteurs. Un projet peut d'ailleurs très bien combiner les deux dimensions différemment : un modèle d'embedding open-source auto-hébergé avec une base de données managée, ou l'inverse.

Piège courant Choisir le mode de déploiement une fois pour toutes au lancement du projet sans anticiper qu'il puisse évoluer. Une trajectoire courante et parfaitement saine : commencer en embarqué (Chroma) pour prototyper rapidement, puis migrer vers managé ou auto-hébergé une fois le besoin de production confirmé (approfondi au module 7, leçon 1, sur la migration entre bases).

MODULE 02 / 08

Chroma : la base embarquée pour prototyper vite

Chroma incarne la philosophie "zéro friction" : une base vectorielle que l'on installe en une commande et que l'on utilise immédiatement, sans serveur à configurer. Ce module en détaille l'usage complet, du prototype jusqu'aux limites qui appellent une autre solution.

LEÇON 2.1Philosophie de Chroma : simplicité et usage local/embarqué

Chroma (souvent appelée ChromaDB) a été conçue autour d'un principe directeur : réduire au minimum la friction entre "j'ai des embeddings" et "je peux les interroger". Par défaut, Chroma tourne dans le même processus que votre application Python, sans serveur séparé à démarrer, sans configuration réseau, sans compte à créer — une expérience proche de celle de SQLite pour les bases relationnelles.

import chromadb

# Aucune installation de serveur, aucune configuration réseau :
# la base démarre directement dans le processus Python
client = chromadb.Client()   # en mémoire, pour un usage éphémère (tests, prototypage)
collection = client.create_collection(name="mes_chunks")

Cette simplicité a un prix assumé par ses concepteurs : Chroma cible explicitement le prototypage, les applications à volume modeste, et les cas où l'infrastructure dédiée d'une base managée (module 3) ou auto-hébergée (module 4) serait disproportionnée par rapport au besoin réel. Ce n'est pas une limitation accidentelle mais un choix de conception cohérent avec son positionnement dans le paysage esquissé au module 1, leçon 3.

Cette rapidité de démarrage explique la popularité de Chroma pour l'apprentissage, les preuves de concept, et les projets personnels — exactement le contexte dans lequel les exemples de code des cours précédents de cette série (chunking, embeddings) auraient pu être testés de bout en bout sans aucune friction d'infrastructure.

Piège courant Confondre la simplicité de démarrage de Chroma avec une garantie de performance ou de scalabilité équivalente aux bases managées ou vector-native. Chroma reste un excellent choix pour son cas d'usage cible (module 2, leçon 5 pour ses limites précises) — la simplicité d'usage ne doit pas faire oublier d'évaluer si le volume et les contraintes réelles du projet restent dans son domaine de compétence.

LEÇON 2.2Installation, collections et opérations CRUD de base

Cette leçon couvre le cycle complet des opérations de base : création d'une collection, ajout de vecteurs, recherche, mise à jour et suppression — le socle opérationnel commun à toute base vectorielle (rappel du module 1, leçon 2), illustré concrètement avec l'API de Chroma.

import chromadb

client = chromadb.Client()
collection = client.create_collection(name="documentation_interne")

# CREATE : ajouter des chunks (avec leurs embeddings déjà calculés, cours embeddings)
collection.add(
    ids=["chunk_001", "chunk_002"],
    embeddings=[[0.021, -0.184, ...], [0.045, 0.102, ...]],
    documents=["Le chunking est une étape essentielle...", "L'overlap recommandé..."],
    metadatas=[
        {"source": "guide_rag.pdf", "departement": "technique"},
        {"source": "guide_rag.pdf", "departement": "technique"},
    ],
)

# READ : rechercher les vecteurs les plus proches d'une requête
resultats = collection.query(
    query_embeddings=[[0.019, -0.180, ...]],
    n_results=5,
)
print(resultats["documents"])   # les textes des chunks les plus proches
print(resultats["distances"])   # leurs distances/scores de similarité

# UPDATE : mettre à jour un chunk existant (identifié par son id, cours métadonnées module 2)
collection.update(
    ids=["chunk_001"],
    metadatas=[{"source": "guide_rag.pdf", "departement": "technique", "statut": "actuel"}],
)

# DELETE : supprimer un chunk (rappel cours embeddings, module 6, cycle de vie des vecteurs)
collection.delete(ids=["chunk_002"])

Chroma peut aussi calculer les embeddings à votre place, via une fonction d'embedding intégrée, plutôt que de recevoir des vecteurs déjà calculés — pratique pour prototyper rapidement, mais à utiliser avec discernement si le modèle d'embedding a déjà été choisi et validé dans le cadre du cours embeddings (module 4).

from chromadb.utils import embedding_functions

fonction_embedding = embedding_functions.SentenceTransformerEmbeddingFunction(
    model_name="BAAI/bge-base-en-v1.5"
)
collection_auto = client.create_collection(
    name="avec_embedding_auto",
    embedding_function=fonction_embedding,
)

# Ici, on fournit directement le texte : Chroma calcule l'embedding lui-même
collection_auto.add(ids=["c1"], documents=["Le chunking est essentiel..."])
Piège courant Laisser Chroma calculer les embeddings automatiquement avec sa fonction par défaut (souvent un modèle léger générique) sans vérifier qu'elle correspond au modèle réellement validé et choisi au terme du cours embeddings (module 4). Une divergence entre le modèle utilisé à l'ingestion et celui utilisé pour la requête rend les vecteurs incomparables (rappel cours embeddings, module 1, leçon 4).

LEÇON 2.3Filtrage par métadonnées et requêtes avancées avec Chroma

Rappel du cours métadonnées (module 3) : le filtrage par métadonnées est le bénéfice le plus direct d'un enrichissement de chunk. Chroma expose ce filtrage via le paramètre where, avec une syntaxe proche de celle déjà rencontrée pour d'autres bases dans le cours embeddings.

# Filtrage simple par égalité
resultats = collection.query(
    query_embeddings=[vecteur_question],
    n_results=5,
    where={"departement": "RH"},
)

# Filtrage combiné (rappel cours métadonnées, module 3, leçon 4)
resultats_combines = collection.query(
    query_embeddings=[vecteur_question],
    n_results=5,
    where={
        "$and": [
            {"departement": {"$eq": "RH"}},
            {"statut": {"$eq": "actuel"}},
        ]
    },
)

# Filtrage sur le contenu textuel lui-même (recherche de sous-chaîne, complémentaire
# au filtrage sémantique — utile pour des identifiants exacts, rappel cours embeddings
# module 7 sur les limites du tout-vectoriel)
resultats_texte = collection.query(
    query_embeddings=[vecteur_question],
    n_results=5,
    where_document={"$contains": "REF-2025"},
)

Récupérer sans recherche vectorielle (accès direct par métadonnée ou id)

Chroma permet aussi de récupérer des entrées sans passer par une recherche de similarité — utile pour des opérations de maintenance (vérifier le contenu d'un chunk précis, auditer les valeurs d'un champ de métadonnée comme évoqué dans le cours métadonnées, module 7, leçon 3).

# Récupération directe par id, sans recherche vectorielle
chunk_precis = collection.get(ids=["chunk_001"])

# Récupération de tous les chunks correspondant à un filtre, sans requête vectorielle
tous_les_chunks_rh = collection.get(where={"departement": "RH"})
print(f"{len(tous_les_chunks_rh['ids'])} chunks dans le département RH")

Piège courant Utiliser exclusivement query() même pour des opérations qui ne nécessitent aucune recherche de similarité (comme auditer toutes les valeurs d'un champ de métadonnée). La méthode get() est plus appropriée et généralement plus rapide pour ces cas, puisqu'elle évite un calcul de similarité inutile.

LEÇON 2.4Persistance et migration vers un mode serveur

Le mode par défaut de Chroma (chromadb.Client()) est éphémère : les données disparaissent à la fin du processus. Pour un usage réel au-delà du simple test, Chroma propose deux évolutions : la persistance sur disque, et un mode serveur/client qui rapproche Chroma d'une base de données plus classique.

Persistance locale sur disque

import chromadb

# Les données sont écrites sur disque et rechargées automatiquement
# au redémarrage du processus — toujours dans le même processus applicatif
client_persistant = chromadb.PersistentClient(path="./ma_base_chroma")
collection = client_persistant.get_or_create_collection(name="documentation_interne")

Mode serveur : séparer Chroma de l'application

Pour partager une même base entre plusieurs processus ou applications (un cas qui dépasse le prototypage local pur), Chroma peut être lancé comme un serveur indépendant, interrogé ensuite via un client réseau — un pas vers l'architecture des bases managées ou auto-hébergées des modules suivants.

# Démarrer Chroma en mode serveur (dans un terminal séparé, ou via Docker)
chroma run --host localhost --port 8000 --path ./ma_base_chroma

# Se connecter au serveur Chroma depuis l'application
import chromadb

client_reseau = chromadb.HttpClient(host="localhost", port=8000)
collection = client_reseau.get_or_create_collection(name="documentation_interne")
# Le reste du code (add, query, delete) reste IDENTIQUE au mode embarqué

Ce point est important : l'API de Chroma reste la même que l'on soit en mode embarqué, persistant, ou serveur — seule la façon d'instancier le client change. Cette continuité facilite une migration progressive : commencer en mode éphémère pour tester, passer en persistant pour un développement local sérieux, puis en mode serveur pour un partage entre plusieurs services, sans réécrire la logique métier d'ingestion et de recherche.

LEÇON 2.5Limites de Chroma et quand en sortir

Cette dernière leçon du module trace les limites concrètes de Chroma — non pas pour la disqualifier, mais pour identifier objectivement le moment où un projet devrait envisager une des solutions des modules suivants (Pinecone, Weaviate, ou une autre base vector-native).

Limites de scalabilité

Même en mode serveur, Chroma reste conçue davantage pour des volumes modérés (de l'ordre de quelques millions de vecteurs au grand maximum dans des conditions favorables) que pour les très grands volumes où des bases spécifiquement optimisées pour la distribution (Milvus) ou le managé serverless (Pinecone) prennent l'avantage.

Absence de recherche hybride native avancée

Contrairement à Weaviate (module 4) qui intègre nativement la recherche hybride (cours embeddings, module 7), Chroma se concentre sur la recherche vectorielle pure — une recherche hybride BM25 + vectorielle nécessite une implémentation applicative supplémentaire plutôt qu'une fonctionnalité native clé en main.

Fonctionnalités de production limitées

La réplication, la haute disponibilité, le sharding automatique (module 6-7) sont peu ou pas nativement gérés par Chroma dans sa configuration standard — des besoins qui apparaissent typiquement à mesure qu'un projet mûrit vers une production critique à fort trafic.

Signal indiquant qu'il est temps de dépasser Chroma : [ ] Le volume de vecteurs dépasse quelques millions [ ] Un besoin de recherche hybride native, sans développement applicatif supplémentaire, est identifié [ ] La haute disponibilité et la réplication deviennent des exigences de production non négociables [ ] Plusieurs équipes ou services doivent interroger la même base à fort trafic simultané

Ce module clôt l'étude de Chroma. Le module suivant explore Pinecone, à l'opposé du spectre "opération" : une base entièrement managée où la question de la scalabilité et de la haute disponibilité est déléguée au fournisseur plutôt que gérée par l'équipe projet.

Piège courant Continuer à utiliser Chroma en production bien au-delà de ses cas d'usage cibles, par habitude ou pour éviter une migration, plutôt que de reconnaître objectivement que les besoins du projet ont dépassé ce que cette solution a été conçue pour offrir — une migration planifiée tôt (module 7, leçon 1) coûte toujours moins cher qu'une migration d'urgence sous contrainte de production dégradée.

MODULE 03 / 08

Pinecone : la base managée serverless

À l'opposé du spectre opérationnel de Chroma : Pinecone ne propose aucune version auto-hébergeable. Toute l'infrastructure — scaling, réplication, disponibilité — est déléguée au fournisseur. Ce module explore ce que cela signifie concrètement, en pratique et en coût.

LEÇON 3.1Philosophie de Pinecone : full-managé, scalabilité sans opération

Pinecone a fait un choix architectural radical par rapport à Chroma (module 2) et Weaviate (module 4) : il n'existe aucune version open-source ou auto-hébergeable. Pinecone est disponible uniquement comme service cloud managé — un choix qui élimine complètement la question "comment dimensionner et opérer mon infrastructure de base vectorielle" en la transférant entièrement au fournisseur.

from pinecone import Pinecone

# Aucune installation locale, aucun serveur à lancer :
# la connexion se fait directement à l'infrastructure Pinecone
pc = Pinecone(api_key="votre_cle_api")

index = pc.Index("documentation-interne")   # l'index existe déjà côté Pinecone,
                                              # créé via l'interface web ou l'API

Ce choix a une conséquence directe sur l'expérience développeur : il n'y a littéralement rien à installer, configurer ou maintenir côté infrastructure — seulement une clé API à obtenir et un index à créer via l'interface Pinecone ou un appel d'API. En contrepartie, cette simplicité opérationnelle a toujours un coût financier récurrent, proportionnel à l'usage (approfondi en leçon 3.4) — contrairement à Chroma où le "coût" se traduit en effort de gestion plutôt qu'en facture directe.

Chroma (module 2) Pinecone (ce module) ──────────────────── ──────────────────── Vous gérez l'infrastructure Pinecone gère l'infrastructure (ou son absence, en mode intégralement — vous n'avez embarqué) jamais accès au serveur sous-jacent Coût : votre temps d'opération Coût : facturation d'usage (ou zéro, en mode embarqué récurrente (leçon 3.4) local) Pas de SLA de disponibilité SLA de disponibilité contractuel formel (vous êtes responsable) (le fournisseur s'engage)

Ce positionnement rend Pinecone particulièrement adapté aux équipes qui veulent consacrer leur temps d'ingénierie au produit RAG lui-même (chunking, prompt engineering, expérience utilisateur) plutôt qu'à l'opération d'une infrastructure de base de données — un arbitrage similaire à celui déjà rencontré dans le cours embeddings (module 4, leçon 2) entre modèle d'embedding propriétaire (API) et open-source auto-hébergé.

Piège courant Choisir Pinecone en pensant pouvoir un jour "rapatrier" l'infrastructure en interne pour réduire les coûts, en oubliant qu'aucune version auto-hébergeable n'existe. Une décision pour Pinecone est structurellement différente d'un choix pour Weaviate ou Qdrant (module 4-5) : elle engage durablement vers un modèle de coût récurrent sans option de repli vers l'auto-hébergement, sauf migration complète vers une autre base (module 7, leçon 1).

LEÇON 3.2Namespaces, index et organisation des données

Pinecone organise les données selon une hiérarchie à deux niveaux : l'index (l'unité principale, comparable à la "collection" de Chroma — rappel du module 1, leçon 2) et le namespace (une subdivision à l'intérieur d'un même index), un concept propre à Pinecone qui mérite d'être bien compris pour organiser efficacement un corpus multi-tenant ou multi-source.

L'index : l'unité de dimension et de configuration

Un index Pinecone est lié à une dimension de vecteur fixe (rappel cours embeddings, module 1, leçon 3) et une métrique de similarité (cosinus, produit scalaire — cours embeddings, module 3) définies à sa création, et ne peuvent plus changer ensuite. Changer de modèle d'embedding avec une dimension différente nécessite systématiquement un nouvel index.

from pinecone import Pinecone, ServerlessSpec

pc = Pinecone(api_key="votre_cle_api")

pc.create_index(
    name="documentation-interne",
    dimension=768,               # doit correspondre exactement au modèle d'embedding utilisé
    metric="cosine",              # cours embeddings, module 3
    spec=ServerlessSpec(cloud="aws", region="us-east-1"),
)

Le namespace : subdiviser un index sans le multiplier

À l'intérieur d'un même index, des namespaces permettent de séparer logiquement des sous-ensembles de données (par exemple, un namespace par client dans un contexte multi-tenant, ou par langue) sans payer le coût de créer un index entièrement séparé pour chacun. Une requête peut cibler un namespace spécifique, agissant comme un filtre implicite très efficace.

# Insertion dans un namespace spécifique
index.upsert(
    vectors=[{"id": "chunk_001", "values": vecteur, "metadata": {"departement": "RH"}}],
    namespace="client_acme_corp",
)

# Requête restreinte à ce namespace uniquement
resultats = index.query(
    vector=vecteur_question,
    namespace="client_acme_corp",
    top_k=5,
)
Index "documentation-interne" (dimension 768, cosinus) ┌─────────────────────────────────────────────────┐ │ Namespace "client_acme_corp" │ │ chunk_001, chunk_002, ... │ ├─────────────────────────────────────────────────┤ │ Namespace "client_beta_sarl" │ │ chunk_101, chunk_102, ... │ ├─────────────────────────────────────────────────┤ │ Namespace "" (par défaut, si non spécifié) │ └─────────────────────────────────────────────────┘ → Chaque namespace est isolé pour la recherche, mais partage la même configuration d'index (dimension, métrique).

Cette organisation par namespace rejoint directement la problématique du multi-tenant abordée dans le cours métadonnées (module 3, leçon 2, permissions et filtrage) — le namespace offre une isolation plus forte et potentiellement plus performante qu'un simple filtre de métadonnée, car la recherche ne considère jamais les vecteurs des autres namespaces.

Piège courant Créer un index séparé pour chaque client ou chaque source de données par réflexe, alors qu'un namespace unique à l'intérieur d'un même index suffirait largement et éviterait la prolifération d'index à gérer et à facturer séparément. Les namespaces sont l'outil natif de Pinecone pour cette subdivision, à privilégier sur la multiplication d'index sauf besoin réel de dimensions ou métriques différentes.

LEÇON 3.3Upsert, requêtes et filtrage de métadonnées avec l'API Pinecone

Cette leçon couvre les opérations CRUD de Pinecone, en miroir de celles déjà vues pour Chroma (module 2, leçon 2) — l'occasion de comparer directement les deux API sur des opérations équivalentes.

# UPSERT : Pinecone combine création et mise à jour en une seule opération
# (contrairement à Chroma qui distingue add() et update())
index.upsert(
    vectors=[
        {
            "id": "chunk_001",
            "values": [0.021, -0.184, 0.093, ...],
            "metadata": {
                "texte": "Le chunking est une étape essentielle...",   # le texte lui-même
                                                                          # est souvent stocké
                                                                          # comme une métadonnée
                "source": "guide_rag.pdf",
                "departement": "technique",
            },
        },
    ],
    namespace="production",
)

# QUERY : recherche vectorielle avec filtrage de métadonnées (cours métadonnées, module 3)
resultats = index.query(
    vector=vecteur_question,
    top_k=5,
    namespace="production",
    filter={
        "departement": {"$eq": "technique"},
        "statut": {"$eq": "actuel"},
    },
    include_metadata=True,
)

for match in resultats["matches"]:
    print(match["id"], match["score"], match["metadata"]["texte"])

# DELETE : suppression ciblée (rappel cours embeddings, module 6, cycle de vie)
index.delete(ids=["chunk_001"], namespace="production")

Une particularité notable de Pinecone : contrairement à Chroma qui distingue le paramètre documents (le texte brut) des metadatas, Pinecone ne stocke que des vecteurs et des métadonnées — le texte du chunk doit être explicitement inclus dans le champ metadata s'il doit être récupéré directement depuis la base (comme illustré ci-dessus), plutôt que d'être un concept de premier ordre séparé.

Filtrage combiné et opérateurs disponibles

# Pinecone supporte des opérateurs de filtrage similaires à ceux déjà
# rencontrés (cours embeddings module 6, cours métadonnées module 3)
filtre_complexe = {
    "$and": [
        {"departement": {"$in": ["RH", "Juridique"]}},
        {"date_modification": {"$gte": "2025-01-01"}},
    ]

Sans cette inclusion explicite, une requête retourne uniquement des identifiants et des scores, sans jamais le contenu textuel du chunk — obligeant une récupération séparée depuis une autre source de vérité, ce qui complique inutilement le pipeline.

LEÇON 3.4Dimensionnement, pods vs serverless, et coûts

Pinecone propose deux modèles de tarification et de dimensionnement distincts, dont le choix a un impact direct sur les coûts et la scalabilité — une compréhension nécessaire avant de committer un projet à long terme sur cette base.

Le modèle Pod-based (historique)

Dans ce modèle, on réserve à l'avance une capacité fixe (un ou plusieurs "pods", chacun avec une capacité déterminée en nombre de vecteurs et en débit de requêtes), facturée en continu que la capacité soit pleinement utilisée ou non — un modèle proche de la réservation d'instances cloud classiques.

Le modèle Serverless (recommandé pour la plupart des nouveaux projets)

Introduit plus récemment, ce modèle facture uniquement l'usage réel (volume de vecteurs stockés, nombre de requêtes effectuées) sans réservation de capacité à l'avance — un modèle bien plus adapté à des charges variables ou à des projets dont le volume est encore incertain, éliminant le risque de sur-provisionner (payer pour une capacité inutilisée) ou sous-provisionner (subir des ralentissements en cas de pic).

from pinecone import ServerlessSpec, PodSpec

# Configuration serverless : facturation à l'usage, pas de capacité réservée
spec_serverless = ServerlessSpec(cloud="aws", region="us-east-1")

# Configuration pod-based : capacité réservée à l'avance
spec_pod = PodSpec(environment="us-east-1-aws", pod_type="p1.x1", pods=1)
Pod-based Serverless ──────────────────── ──────────────────── Capacité réservée à l'avance Facturation à l'usage réel (risque de sur/sous-provisionnement) (pas de réservation) Coût prévisible et fixe Coût variable selon le trafic (bon pour un volume stable connu) (bon pour un volume incertain ou variable) Latence potentiellement plus stable Latence généralement excellente, (ressources dédiées) infrastructure partagée mais gérée automatiquement

Estimer le coût réel avant de s'engager

def estimer_cout_pinecone_serverless(nb_vecteurs: int, dimension: int,
                                       nb_requetes_par_mois: int,
                                       prix_stockage_par_go_mois: float = 0.33,
                                       prix_par_million_requetes: float = 4.0) -> float:
    octets_par_vecteur = dimension * 4  # float32
    go_stockage = (nb_vecteurs * octets_par_vecteur) / (1024 ** 3)
    cout_stockage = go_stockage * prix_stockage_par_go_mois
    cout_requetes = (nb_requetes_par_mois / 1_000_000) * prix_par_million_requetes
    return cout_stockage + cout_requetes

# Les tarifs exacts évoluent — toujours vérifier la grille tarifaire actuelle
# de Pinecone avant de committer un budget basé sur cette estimation
Piège courant Choisir le modèle pod-based par habitude ou parce que c'est historiquement l'offre la plus connue, sans comparer au modèle serverless qui convient mieux à la majorité des nouveaux projets dont le volume n'est pas encore stabilisé. Toujours recalculer le coût estimé des deux modèles pour son propre profil d'usage avant de trancher.

LEÇON 3.5Limites et cas où Pinecone n'est pas le bon choix

Cette dernière leçon du module identifie objectivement les situations où Pinecone, malgré sa simplicité opérationnelle, n'est pas le choix le plus adapté.

Contraintes de souveraineté ou de confidentialité stricte des données

Puisqu'aucune version auto-hébergeable n'existe (leçon 3.1), les données transitent nécessairement par l'infrastructure de Pinecone. Pour des organisations soumises à des contraintes réglementaires strictes de localisation ou de contrôle des données (secteur public, santé, défense dans certains pays), cette absence d'option d'auto-hébergement peut être structurellement bloquante, indépendamment de la qualité technique du produit.

Prototypage à très petit volume

Pour un simple prototype ou un projet personnel, la mise en place d'un compte Pinecone et la gestion d'une clé API représentent une friction supérieure à Chroma en mode embarqué (module 2) — sans bénéfice réel à cette échelle où les questions de scalabilité et de haute disponibilité ne se posent simplement pas encore.

Besoin de contrôle fin sur l'infrastructure sous-jacente

Pour des équipes avec une expertise infrastructure forte et un besoin de contrôle fin (choix précis du matériel, optimisations très spécifiques), une solution auto-hébergeable comme Weaviate ou Qdrant (modules 4-5) offre une latitude que le modèle entièrement managé de Pinecone ne permet pas par nature.

Signal indiquant que Pinecone n'est probablement pas le bon choix : [ ] Contraintes réglementaires empêchant toute donnée hébergée par un tiers externe [ ] Projet à un stade de prototype très précoce, sans besoin réel de scalabilité ou de disponibilité garantie [ ] Équipe avec une forte expertise infrastructure souhaitant un contrôle fin sur le déploiement [ ] Besoin de fonctionnalités très spécifiques (recherche hybride avancée, modules d'inférence intégrés — module 4) non couvertes nativement par Pinecone

Ce module clôt l'étude de Pinecone. Le module suivant explore Weaviate, une troisième philosophie qui combine capacité d'auto-hébergement (comme un contre-point à Pinecone) avec un schéma de données fort et des fonctionnalités de recherche hybride intégrées nativement.

Piège courant Écarter Pinecone uniquement sur la base d'une intuition de coût "les solutions managées sont toujours plus chères", sans avoir réellement chiffré le coût total de possession (module 5, leçon 3) d'une alternative auto-hébergée incluant le temps d'ingénierie nécessaire à son opération — un temps souvent sous-estimé dans les comparaisons superficielles.

MODULE 04 / 08

Weaviate : la base orientée schéma et recherche hybride

Troisième philosophie de ce cours : Weaviate impose une structure de données plus stricte que Chroma ou Pinecone, en échange de fonctionnalités intégrées puissantes — recherche hybride native, modules de vectorisation embarqués — et d'une capacité d'auto-hébergement que Pinecone n'offre pas.

LEÇON 4.1Philosophie de Weaviate : schéma fort et modules d'inférence intégrés

Weaviate se distingue de Chroma et Pinecone par une approche plus proche d'une base de données "classique" dans sa rigueur : avant d'insérer des données, on définit un schéma qui décrit précisément les classes d'objets et leurs propriétés typées — une discipline plus contraignante que le payload libre de Chroma ou Pinecone, mais qui apporte en retour une validation automatique et des fonctionnalités de requête plus riches.

L'autre trait distinctif de Weaviate : des modules intégrés qui peuvent calculer les embeddings directement au sein de la base (via des connecteurs vers OpenAI, Cohere, ou des modèles open-source), sans que l'application cliente n'ait besoin d'appeler elle-même un modèle d'embedding séparé (cours embeddings) avant l'insertion — Weaviate peut s'en charger nativement si configuré ainsi.

import weaviate
from weaviate.classes.init import Auth

client = weaviate.connect_to_weaviate_cloud(
    cluster_url="https://mon-cluster.weaviate.network",
    auth_credentials=Auth.api_key("votre_cle_api"),
)

# Le schéma définit explicitement la structure — contrairement au
# payload libre de Chroma (module 2) ou Pinecone (module 3)
collection = client.collections.create(
    name="DocumentationInterne",
    properties=[
        {"name": "texte", "data_type": "text"},
        {"name": "source", "data_type": "text"},
        {"name": "departement", "data_type": "text"},
    ],
)
Chroma / Pinecone Weaviate ──────────────────── ──────────────────── Payload libre, non typé Schéma fort, propriétés (n'importe quelle clé/valeur typées explicitement peut être ajoutée) (validation automatique) Vecteurs calculés en amont, Peut calculer les vecteurs côté application (cours nativement via des modules embeddings) intégrés (vectorizers) Plus flexible, moins de garanties Plus rigide, garanties de de structure cohérence de structure

Ce choix de conception rapproche Weaviate d'une base orientée documents avec typage (comme MongoDB avec validation de schéma) plutôt que d'un simple magasin clé-valeur de vecteurs — un compromis qui profite particulièrement aux projets avec des besoins de requêtes structurées riches (leçon 4.4) et de recherche hybride native (leçon 4.3).

Piège courant Aborder Weaviate avec la même désinvolture de schéma que Chroma ou Pinecone (ajouter des métadonnées librement sans schéma préalable), ce qui peut se heurter à des erreurs de validation ou à un typage incohérent. Weaviate demande un effort de conception de schéma en amont (leçon 4.2), un investissement différent de celui requis par les deux autres bases de ce cours.

Modules vectorizer : calculer les embeddings au sein de la base

Plutôt que de calculer les vecteurs en amont (comme illustré au module précédent avec Vectorizer.none()), Weaviate peut déléguer ce calcul à un module intégré connecté à un fournisseur externe (OpenAI, Cohere) ou à un modèle local — Weaviate appelle alors automatiquement le modèle configuré à chaque insertion et à chaque requête.

    name="DocumentationAvecVectorizerIntegre",
    vectorizer_config=Configure.Vectorizer.text2vec_openai(
        model="text-embedding-3-small"   # rappel cours embeddings, module 4
    ),
    properties=[Property(name="texte", data_type=DataType.TEXT)],
)

# Il suffit de fournir le texte : Weaviate calcule l'embedding lui-même
collection_avec_vectorizer.data.insert(properties={"texte": "L'overlap recommandé..."})

Ce choix de déléguer le calcul d'embedding à Weaviate simplifie le pipeline applicatif, mais couple plus étroitement l'infrastructure de stockage au choix du modèle d'embedding — un arbitrage à mettre en balance avec la flexibilité de calculer les vecteurs séparément (comme dans les modules 2 et 3 de ce cours), qui permet de changer de modèle d'embedding sans dépendre de la disponibilité d'un module Weaviate correspondant.

Piège courant Activer un vectorizer intégré par simplicité, sans avoir validé au préalable (cours embeddings, module 4, leçon 3) que ce modèle spécifique est le mieux adapté à son corpus. Le couplage entre la base et le calcul d'embedding rend un changement de modèle ultérieur plus contraignant qu'avec des vecteurs calculés indépendamment.

LEÇON 5.2Performance et benchmarks : comment les lire sans se faire tromper

Chaque fournisseur de base vectorielle publie régulièrement des benchmarks montrant sa solution sous un jour favorable — un phénomène similaire à celui déjà rencontré avec les classements de modèles d'embedding (cours embeddings, module 4, leçon 3, sur la lecture critique du benchmark MTEB). Cette leçon transpose cette même vigilance méthodologique aux benchmarks de bases vectorielles.

Vérifier les conditions exactes du benchmark

Un benchmark qui annonce "10x plus rapide" mérite d'être examiné en détail : quel volume de vecteurs, quelle dimension, quels paramètres d'index (rappel cours embeddings, module 5 — un HNSW mal paramétré sur la base concurrente fausserait la comparaison), quel matériel, quelle charge de requêtes simultanées ? Un benchmark favorable sur des paramètres non représentatifs de votre cas d'usage réel n'apporte aucune information utile à votre décision.

Reproduire un mini-benchmark sur son propre cas d'usage

import time

def mesurer_latence_recherche(base_vectorielle, requetes_test: list, k: int = 5) -> dict:
    latences = []
    for requete in requetes_test:
        debut = time.perf_counter()
        base_vectorielle.query(vector=requete, top_k=k)
        latences.append(time.perf_counter() - debut)

    latences.sort()
    return {
        "latence_mediane_ms": latences[len(latences) // 2] * 1000,
        "latence_p95_ms": latences[int(len(latences) * 0.95)] * 1000,
    }

# À reproduire sur VOTRE volume réel de données et VOS requêtes
# représentatives, pas sur un jeu de données générique publié
# par un fournisseur

Une latence faible pour une requête isolée ne garantit pas un bon comportement sous charge (de nombreuses requêtes simultanées) — deux métriques distinctes qui peuvent évoluer différemment selon l'architecture de la base (rappel du cours embeddings, module 6, leçon 3, sur le dimensionnement et la scalabilité).

LEÇON 5.3Coût total de possession (TCO) selon le volume et l'usage

Comparer les bases uniquement sur leur tarif affiché (prix par Go, prix par million de requêtes) omet une part significative du coût réel — cette leçon élargit le calcul à un véritable coût total de possession (Total Cost of Ownership), incluant le temps d'ingénierie.

Les composantes du TCO souvent oubliées

  • Temps d'ingénierie d'opération : pour une base auto-hébergée (Chroma, Weaviate en self-hosted, module 4 leçon 5), le temps consacré à la surveillance, aux mises à jour, à la résolution d'incidents a un coût réel, même s'il n'apparaît sur aucune facture.
  • Coût de la migration future : si un changement de base s'avère nécessaire plus tard (module 7, leçon 1), ce coût de migration devrait être anticipé dans la décision initiale, en particulier si la portabilité est faible (leçon 5.4).
  • Coût des compétences : une solution auto-hébergée nécessite une expertise interne (Kubernetes pour Weaviate à grande échelle, module 4 leçon 5) qui a un coût de recrutement ou de formation.
def estimer_tco_annuel(cout_infrastructure_mensuel: float,
                        heures_ingenierie_operation_par_mois: float,
                        cout_horaire_ingenieur: float) -> dict:
    cout_infra_annuel = cout_infrastructure_mensuel * 12
    cout_operation_annuel = heures_ingenierie_operation_par_mois * 12 * cout_horaire_ingenieur
    return {
        "cout_infrastructure": cout_infra_annuel,
        "cout_operation_humaine": cout_operation_annuel,
        "tco_total": cout_infra_annuel + cout_operation_annuel,
    }

LEÇON 5.4Portabilité et risque de lock-in fournisseur

Le choix d'une base de données vectorielle engage un projet à plus ou moins long terme selon la difficulté à en changer ultérieurement — un risque de lock-in (dépendance excessive à un fournisseur) qu'il convient d'évaluer dès la conception, même si la décision initiale reste par ailleurs justifiée.

Facteurs qui augmentent le risque de lock-in

  • API propriétaire non standard : plus l'API d'une base diverge des standards du marché, plus le code applicatif qui l'utilise devra être réécrit lors d'une migration (rappel des différences déjà observées entre Chroma, Pinecone et Weaviate dans ce module).
  • Fonctionnalités propriétaires profondément intégrées : un module vectorizer intégré à Weaviate (module 4, leçon 3), ou une fonctionnalité spécifique à Pinecone, créent une dépendance fonctionnelle au-delà du simple stockage de vecteurs.
  • Absence d'export de données standard : la capacité à exporter l'intégralité des vecteurs et métadonnées dans un format ouvert (JSON, Parquet) conditionne directement la faisabilité d'une migration future.

Réduire le lock-in par une couche d'abstraction

Une pratique répandue : construire une fine couche d'abstraction applicative (une interface commune pour upsert, query, delete) qui isole la logique métier du SDK spécifique de la base choisie — un investissement modéré qui facilite grandement une migration future, au prix d'une petite couche de code supplémentaire à maintenir.

from abc import ABC, abstractmethod

class BaseVectorielleAbstraite(ABC):
    @abstractmethod
    def upsert(self, ids: list[str], vectors: list[list[float]], metadatas: list[dict]): ...

    @abstractmethod
    def query(self, vector: list[float], k: int, filtre: dict | None = None) -> list[dict]: ...

class AdaptateurChroma(BaseVectorielleAbstraite):
    def __init__(self, collection):
        self.collection = collection

    def upsert(self, ids, vectors, metadatas):
        self.collection.add(ids=ids, embeddings=vectors, metadatas=metadatas)

    def query(self, vector, k, filtre=None):
        return self.collection.query(query_embeddings=[vector], n_results=k, where=filtre)

# Le reste de l'application n'appelle QUE l'interface abstraite,
# jamais directement l'API spécifique de Chroma, Pinecone ou Weaviate

Cette couche d'abstraction a un coût (complexité additionnelle, et impossibilité d'exploiter certaines fonctionnalités très spécifiques à une base sans casser l'abstraction) qui doit être mis en balance avec le bénéfice réel attendu — un projet expérimental de courte durée n'a probablement pas besoin de cet investissement, contrairement à un système destiné à vivre plusieurs années dans une infrastructure évolutive.

Piège courant Construire une couche d'abstraction complète et générique dès le premier jour d'un projet, avant même d'avoir validé le choix de base de données — un sur-engineering similaire à ceux déjà rencontrés dans les cours précédents de cette série, qui retarde la mise en production pour un bénéfice hypothétique de portabilité jamais concrétisé.

Rappel du cours embeddings (module 7) : combiner recherche vectorielle et lexicale (BM25), puis reranker les meilleurs candidats, améliore significativement la pertinence. Cette leçon montre comment cette architecture se met en œuvre concrètement selon la base choisie.

Recherche hybride native (Weaviate) vs applicative (Chroma, Pinecone)

Rappel du module 4, leçon 3 : Weaviate propose la recherche hybride nativement. Pour Chroma et Pinecone, qui n'offrent pas cette fonctionnalité intégrée au même niveau, la recherche hybride nécessite d'orchestrer soi-même deux recherches (vectorielle via la base, lexicale via une librairie comme rank_bm25, déjà vue dans le cours embeddings module 7) puis de fusionner les résultats.

# Recherche hybride applicative avec Chroma ou Pinecone
# (rappel de la fusion RRF, cours embeddings module 7, leçon 4)
def recherche_hybride_applicative(question: str, base_vectorielle, index_bm25, k: int = 5):
    resultats_vectoriels = base_vectorielle.query(vector=embed(question), top_k=30)
    scores_bm25 = index_bm25.get_scores(question.lower().split())

    rang_vectoriel = [r["id"] for r in resultats_vectoriels]
    rang_bm25 = classer_par_score(scores_bm25)

    return reciprocal_rank_fusion([rang_vectoriel, rang_bm25])[:k]

# Avec Weaviate : la même logique est native, en une seule requête (module 4, leçon 3)
resultats = collection.query.hybrid(query=question, vector=embed(question), alpha=0.5, limit=k)

Ajouter un reranking après la recherche, quelle que soit la base

Le reranking par cross-encoder (cours embeddings, module 7, leçon 3) s'applique de façon identique après la recherche initiale, indépendamment de la base vectorielle utilisée — c'est une étape applicative qui reçoit simplement les k candidats de la base et les reclasse, sans dépendre des spécificités de Chroma, Pinecone ou Weaviate.

from sentence_transformers import CrossEncoder

reranker = CrossEncoder("cross-encoder/ms-marco-MiniLM-L-6-v2")

def rechercher_avec_reranking(question: str, base_vectorielle, k_candidats: int = 30, k_final: int = 5):
    candidats = base_vectorielle.query(vector=embed(question), top_k=k_candidats)
    paires = [(question, c["texte"]) for c in candidats]
    scores = reranker.predict(paires)
    return [c for c, s in sorted(zip(candidats, scores), key=lambda x: x[1], reverse=True)][:k_final]

def mettre_a_jour_en_masse_chroma(collection, chunks: list[dict], taille_lot: int = 500):

def migrer_par_lots(donnees: list[dict], nouvelle_base, taille_lot: int = 500) -> dict:
    reussies, echouees = 0, 0

LEÇON 7.3Monitoring et observabilité d'une base vectorielle en production

Rappel du principe déjà établi dans le cours nettoyage (module 7, leçon 4) et le cours métadonnées (module 7, leçon 3) : une confiance aveugle en l'absence d'erreur ne garantit pas la qualité d'un système. Cette leçon transpose cette vigilance au monitoring opérationnel d'une base vectorielle.

Métriques essentielles à surveiller

  • Latence de recherche (médiane et p95/p99, rappel leçon 5.2) — une dégradation progressive peut signaler un index qui grossit sans réoptimisation, ou une charge croissante non anticipée.
  • Taux d'erreur des requêtes — distinct de la latence, révèle des pannes partielles ou des dépassements de capacité.
  • Volume de vecteurs et croissance dans le temps — alimente directement le dimensionnement prévisionnel (leçon 7.5).
  • Fraîcheur de l'index (rappel cours embeddings, module 6, leçon 4, sur l'index périmé) — délai entre la publication d'un document et sa disponibilité effective dans les résultats de recherche.
import time
from dataclasses import dataclass, field

@dataclass
class MetriquesBaseVectorielle:
    latences_ms: list = field(default_factory=list)
    erreurs: int = 0
    requetes_totales: int = 0

    def enregistrer_requete(self, fonction_recherche, *args, **kwargs):
        self.requetes_totales += 1
        debut = time.perf_counter()
        try:
            resultat = fonction_recherche(*args, **kwargs)
            self.latences_ms.append((time.perf_counter() - debut) * 1000)
            return resultat
        except Exception:
            self.erreurs += 1
            raise

    def rapport(self) -> dict:
        latences_triees = sorted(self.latences_ms)
        return {
            "taux_erreur": self.erreurs / max(self.requetes_totales, 1),
            "latence_p95_ms": latences_triees[int(len(latences_triees) * 0.95)] if latences_triees else None,
        }

Alertes automatiques sur seuils

Comme pour les métriques de qualité de texte (cours nettoyage, module 7, leçon 3), définir des seuils d'alerte automatiques sur ces métriques (latence p95 au-delà d'un seuil, taux d'erreur anormal) permet de détecter une dégradation avant qu'elle ne soit signalée par des utilisateurs mécontents.

Piège courant Ne surveiller que la disponibilité binaire de la base (up/down) sans suivre l'évolution de la latence ou du volume dans le temps. Une base "techniquement disponible" mais dont la latence se dégrade progressivement sur plusieurs semaines peut passer inaperçue jusqu'à un point de rupture soudain, alors qu'un monitoring continu aurait révélé la tendance bien plus tôt.

LEÇON 7.4Optimiser les coûts à grande échelle

Rappel de la leçon 5.3 sur le TCO : au-delà de l'estimation initiale, les coûts d'une base vectorielle en production évoluent et méritent une optimisation continue à mesure que le volume et le trafic grandissent.

Réduire la dimension des vecteurs (Matryoshka embeddings)

Rappel du cours embeddings (module 4, leçon 1) : certains modèles récents permettent de tronquer un vecteur à une dimension plus faible avec une perte de qualité limitée. Réduire la dimension diminue directement le coût de stockage et accélère la recherche — un levier d'optimisation à évaluer avant d'investir dans du scaling matériel plus coûteux.

def evaluer_impact_reduction_dimension(dimension_originale: int, dimension_reduite: int,
                                        nb_vecteurs: int) -> dict:
    octets_par_dim = 4  # float32
    stockage_original_go = (nb_vecteurs * dimension_originale * octets_par_dim) / (1024**3)
    stockage_reduit_go = (nb_vecteurs * dimension_reduite * octets_par_dim) / (1024**3)
    return {
        "reduction_stockage_pourcent": (1 - stockage_reduit_go / stockage_original_go) * 100,
        "stockage_original_go": stockage_original_go,
        "stockage_reduit_go": stockage_reduit_go,
    }

Rappel du cours métadonnées (module 2, leçon 4 ; module 7, leçon 5) : les chunks marqués "obsolete" ou dont la fraîcheur dépasse un seuil peuvent être déplacés vers un stockage moins coûteux (voire supprimés selon la politique de conservation), plutôt que de rester indéfiniment dans l'index actif le plus coûteux et le plus rapide.

Ajuster le mode de tarification à l'usage réel

Rappel de la leçon 3.4 (pods vs serverless chez Pinecone) : revisiter périodiquement le choix entre capacité réservée et facturation à l'usage, à mesure que le profil de trafic se stabilise ou change, pour rester aligné avec le modèle de tarification le plus économique pour l'usage réel observé.

        volume = int(volume * (1 + taux_croissance_mensuel))
        projection.append(volume)
    return projection

LEÇON 8.1Pipeline complet : du chunk enrichi à la base vectorielle en production

Voici le pipeline complet qui relie les cinq cours de cette série de préparation de données pour RAG, de l'extraction d'un document brut jusqu'à son indexation interrogeable en production.

def pipeline_complet_vers_indexation(chemin_document: str, base_vectorielle) -> dict:
    # 1. Extraction et nettoyage (cours nettoyage de texte non structuré)
    texte_brut = extraire_selon_format(chemin_document)
    texte_propre = nettoyer_texte_complet(texte_brut)

    # 2. Chunking (cours chunking de documents pour RAG)
    chunks = pipeline_chunking(texte_propre)

    # 3. Enrichissement de métadonnées (cours enrichissement de métadonnées)
    chunks_enrichis = [enrichir_chunk_complet(c, texte_propre, None) for c in chunks]

    # 4. Embedding (cours embeddings et recherche vectorielle)
    vecteurs = [embed(c["texte_pour_embedding"]) for c in chunks_enrichis]

    # 5. Indexation dans la base vectorielle (CE COURS)
    base_vectorielle.upsert(
        ids=[c["id"] for c in chunks_enrichis],
        vectors=vecteurs,
        metadatas=[c["metadata"] for c in chunks_enrichis],
    )

    return {
        "nb_chunks_indexes": len(chunks_enrichis),
        "alertes_qualite": [c for c in chunks_enrichis if c.get("alertes")],
    }

Ce pipeline en cinq étapes est l'aboutissement concret de toute cette série : chaque cours a résolu un problème spécifique (extraire un texte propre, le découper intelligemment, le vectoriser, l'enrichir de contexte) et ce dernier cours fournit le contenant qui rend tout ce travail interrogeable en production, avec les garanties de scalabilité, de coût maîtrisé et de sécurité étudiées dans les modules précédents.

Piège courant Traiter ces cinq étapes comme des silos indépendants développés séparément sans jamais valider leur intégration bout en bout. Un pipeline complet devrait être testé de bout en bout sur un échantillon réel avant d'être déployé à l'échelle de tout un corpus — une erreur à n'importe quelle étape (mauvais encodage, mauvais modèle d'embedding, schéma de métadonnées incompatible avec la base choisie) peut se propager silencieusement jusqu'au bout.

Quelques pistes de réflexion pour vous guider (à consulter après avoir tenté l'exercice vous-même) :

Piste pour le choix de base

Avec une équipe sans expertise infrastructure profonde et un budget mensuel modeste mais réel, une base managée (Pinecone, module 3) ou l'offre cloud de Weaviate serait cohérente avec la méthode de décision du module 5, leçon 5 — l'auto-hébergement demanderait un temps d'ingénierie (leçon 5.3, TCO) que l'équipe de deux développeurs ne peut probablement pas absorber en plus du développement produit.

Piste pour l'isolation multi-tenant

Avec seulement trois clients aux données non partageables, une isolation par namespace (Pinecone, module 3, leçon 2) ou par collection séparée (Weaviate) offre une garantie plus forte qu'un simple filtrage par métadonnées, pour un coût de gestion encore raisonnable à cette échelle de trois tenants.

Piste pour la migration

Suivre la méthode en 4 étapes du module 7, leçon 1 : exporter les 20 000 chunks de Chroma, valider la compatibilité de dimension avec la nouvelle base, réimporter par lots, et valider avec le jeu d'évaluation avant de basculer le trafic — une migration à ce volume reste rapide et peu risquée si methodique.

Piste pour le dimensionnement

Avec une croissance de 15% par mois sur 20 000 chunks, la projection (module 7, leçon 5) atteint environ 46 000 chunks à 6 mois — un volume qui reste dans le domaine confortable de la plupart des bases managées, sans besoin de sharding actif à ce stade, mais à surveiller si la croissance se maintient au-delà de 12-18 mois.

Piège courant Recommander la solution la plus sophistiquée techniquement (auto-hébergement Kubernetes multi-shard) plutôt que celle réellement adaptée aux contraintes de l'équipe (deux développeurs, budget modeste) — un rappel du principe transversal de toute cette série : la meilleure solution est celle qui correspond aux contraintes réelles du projet, pas celle qui démontre la plus grande sophistication technique.
