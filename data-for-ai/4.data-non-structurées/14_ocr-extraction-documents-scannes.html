MODULE 01 / 08

Fondamentaux de l'OCR

Le cours sur le nettoyage de texte non structuré avait laissé un cas de côté : le PDF scanné, qui ne contient aucun texte réel — seulement des pixels. Ce module comble ce vide en posant les bases de l'OCR (Reconnaissance Optique de Caractères), la technologie qui transforme une image de texte en texte exploitable.

LEÇON 1.1Qu'est-ce que l'OCR et pourquoi les PDF scannés bloquent tout pipeline RAG

L'OCR (Optical Character Recognition, reconnaissance optique de caractères) est une technologie qui analyse une image contenant du texte — un scan, une photo de document, une capture d'écran — pour en extraire les caractères réellement présents, sous forme de texte numérique exploitable. Sans OCR, une image de texte reste, pour un ordinateur, une simple grille de pixels colorés : aucune notion de "lettre A" ou de "mot" n'existe intrinsèquement dans ce type de fichier.

Ce cours fait suite directe au cours sur le nettoyage de texte non structuré, qui avait identifié ce problème sans le résoudre : un PDF "scanné" — capturé depuis un document papier, ou exporté comme image plutôt que comme texte natif — ne contient aucun texte réel, seulement une image encapsulée dans un conteneur PDF. Tenter d'en extraire du texte avec les outils déjà vus (pypdf, pdfplumber, PyMuPDF) renvoie systématiquement un résultat vide, car il n'y a tout simplement rien à extraire par ces méthodes.

Rappel du cours nettoyage (module 2, leçon 4) : def detecter_pdf_scanne(chemin_pdf: str, seuil_caracteres_par_page: int = 50) -> bool: document = fitz.open(chemin_pdf) texte_total = "".join(page.get_text() for page in document) return len(texte_total) / len(document) < seuil_caracteres_par_page → Ce cours répondait "il faut de l'OCR" sans expliquer comment. CE COURS comble précisément ce manque.

L'enjeu n'est pas anecdotique : dans de nombreux corpus d'entreprise, une part significative des documents (archives papier numérisées, formulaires remplis à la main, factures scannées, contrats anciens) n'existe que sous cette forme. Sans une étape d'OCR fiable, ces documents entiers restent structurellement invisibles à un système RAG — quelle que soit la qualité du chunking, de l'embedding ou de l'enrichissement de métadonnées appliqués en aval, aucun de ces traitements ne peut s'exercer sur du texte qui n'a jamais été extrait.

Document papier Scan (image) Après OCR (ce cours) ───────────────── ───────────────── ───────────────────── Texte physique, Grille de pixels, Texte numérique réel, lisible par un AUCUNE notion de exploitable par le humain caractère ou de mot reste du pipeline RAG pour un ordinateur (cours chunking, embeddings...)

L'OCR occupe donc une place particulière dans la série de cours consacrée à la préparation de données pour RAG : ce n'est pas une étape systématique (un document avec du texte natif n'en a pas besoin, cours nettoyage module 2), mais une étape conditionnelle et incontournable pour toute la portion d'un corpus qui se présente sous forme d'image plutôt que de texte structuré.

Piège courant Découvrir l'existence de documents scannés seulement après avoir constaté des résultats d'extraction vides ou anormalement courts en production, plutôt que d'auditer le corpus dès le départ pour quantifier la proportion de documents nécessitant de l'OCR (rappel de la détection systématique du cours nettoyage, module 2, leçon 4).

LEÇON 1.2Comment fonctionne un moteur OCR : des pixels au texte

Comprendre les grandes étapes internes d'un moteur OCR aide à interpréter ses erreurs et à savoir où intervenir pour les corriger — un moteur OCR n'est pas une boîte magique, mais un pipeline de traitement d'image et de reconnaissance de motifs avec ses propres étapes identifiables.

Étape 1 — Prétraitement de l'image

Avant toute reconnaissance, l'image est généralement convertie en niveaux de gris, puis souvent binarisée (chaque pixel devient noir ou blanc, sans nuance) pour maximiser le contraste entre le texte et le fond. Cette étape, approfondie au module 3, conditionne fortement la qualité de tout ce qui suit.

Étape 2 — Segmentation de la page

Le moteur identifie les zones de la page qui contiennent du texte (par opposition aux images, aux marges, aux zones vides), puis découpe ces zones en lignes, puis en mots, puis en caractères individuels — une hiérarchie de segmentation similaire, dans son principe, aux étapes de chunking déjà vues dans le cours dédié, mais appliquée ici à une image plutôt qu'à du texte déjà existant.

Étape 3 — Reconnaissance de caractères

Chaque caractère segmenté est comparé à des motifs appris (historiquement, une comparaison de formes ; dans les moteurs modernes comme Tesseract 4+, un réseau de neurones récurrent, approfondi au module 2) pour déterminer quelle lettre ou quel symbole il représente le plus probablement.

Étape 4 — Post-traitement linguistique

De nombreux moteurs OCR appliquent une correction basée sur un modèle de langue (dictionnaire, fréquences de mots) pour corriger des caractères mal reconnus individuellement mais incohérents dans leur contexte — une étape qui explique pourquoi l'OCR se trompe différemment selon la langue configurée (approfondi au module 2, leçon 3).

Image brute (scan) │ ▼ ┌─────────────────────┐ │ 1. Prétraitement │ ← niveaux de gris, binarisation (module 3) └─────────────────────┘ │ ▼ ┌─────────────────────┐ │ 2. Segmentation │ ← zones de texte → lignes → mots → caractères └─────────────────────┘ │ ▼ ┌─────────────────────┐ │ 3. Reconnaissance │ ← réseau de neurones ou comparaison de motifs └─────────────────────┘ │ ▼ ┌─────────────────────┐ │ 4. Post-traitement │ ← correction via dictionnaire/modèle de langue │ linguistique │ └─────────────────────┘ │ ▼ Texte numérique final

Cette décomposition en quatre étapes est directement utile pour le débogage (module 7, leçon 2) : une erreur d'OCR peut avoir son origine à n'importe laquelle de ces étapes — une mauvaise segmentation (deux colonnes fusionnées) produit un symptôme très différent d'une mauvaise reconnaissance de caractère isolé (un "0" confondu avec un "O"), et appelle une correction différente.

Piège courant Traiter l'OCR comme un processus atomique et indivisible ("ça marche" ou "ça ne marche pas"), sans identifier à quelle étape précise un problème survient. Un texte OCR de mauvaise qualité peut être dû à un prétraitement insuffisant (module 3), une mauvaise configuration de segmentation (module 2, leçon 2), ou une langue mal configurée (module 2, leçon 3) — trois causes qui appellent des corrections complètement différentes.

LEÇON 1.3Qualité d'un scan : résolution, contraste, bruit — ce qui détermine le résultat

La qualité de l'image source est, de loin, le facteur le plus déterminant de la qualité finale d'une extraction OCR — bien avant le choix du moteur ou de ses paramètres (modules 2 et 4). Cette leçon détaille les trois caractéristiques d'image qui comptent le plus.

Résolution

Mesurée en DPI (dots per inch, points par pouce), la résolution détermine combien de pixels représentent chaque caractère. En dessous d'un seuil (généralement autour de 200-300 DPI pour du texte de taille standard), les caractères deviennent flous ou pixelisés au point de devenir ambigus même pour un œil humain — un moteur OCR ne peut pas deviner ce qui n'est plus visuellement distinguable.

Résolution insuffisante (~100 DPI) Résolution correcte (~300 DPI) ▓▓░░▓▓ ▓▓░░░░▓▓ ░░▓▓░░ (caractère "e" flou, ░░▓▓▓▓░░ (caractère "e" net, ▓▓░░▓▓ confondu avec "c" ░░▓▓▓▓░░ facilement reconnu) ou "o" possible) ▓▓░░░░▓▓

Contraste

L'écart de luminosité entre le texte et son arrière-plan. Un scan avec un contraste faible (texte gris clair sur fond blanc cassé, papier jauni, encre pâlie) réduit la capacité du moteur à distinguer nettement les contours des caractères — un problème partiellement corrigible par le prétraitement (module 3, leçon 2), mais avec des limites si le contraste d'origine est trop faible.

Bruit

Les artefacts visuels indésirables : grain de numérisation, taches, plis du papier, ombres de reliure sur un livre scanné. Ce bruit peut être interprété à tort comme des caractères ou perturber la segmentation — un problème également adressé par le prétraitement (module 3, leçon 3, débruitage).

FacteurSeuil problématique typiqueCorrection possible
RésolutionEn dessous de ~200 DPILimitée — dépend du scan d'origine
ContrasteTexte pâle, fond non uniformePrétraitement (module 3, leçon 2)
BruitGrain, taches, ombresPrétraitement (module 3, leçon 3)

Un principe à retenir dès ce premier module : contrairement à un problème de configuration logicielle (qui se corrige en changeant un paramètre), un problème de résolution insuffisante à la source est souvent irrécupérable — aucun prétraitement ni aucun moteur OCR, aussi sophistiqué soit-il, ne peut reconstituer une information visuelle qui n'a jamais été capturée. Quand c'est possible, la meilleure optimisation reste en amont : re-numériser le document source à une résolution suffisante plutôt que de compenser après coup.

Piège courant Consacrer beaucoup d'effort à optimiser les paramètres du moteur OCR ou du prétraitement sur des scans dont la résolution d'origine est structurellement insuffisante. Si le document source original (papier ou fichier numérique haute résolution) reste accessible, une re-numérisation à une résolution adéquate résout souvent le problème plus efficacement que n'importe quelle optimisation logicielle en aval.

LEÇON 1.4Où l'OCR s'insère dans le pipeline RAG

Cette leçon situe précisément l'OCR par rapport au pipeline complet déjà construit dans la série de cours sur la préparation de données pour RAG — une étape supplémentaire, conditionnelle, qui s'insère avant même l'extraction/nettoyage déjà étudiée.

Document source │ ▼ Est-ce un format avec texte natif (DOCX, HTML, PDF non scanné) ? │ ├── OUI ──► Extraction directe (cours nettoyage, modules 2-4) │ └── NON (image, PDF scanné) ──► OCR (CE COURS) │ ▼ Texte numérique brut │ ▼ Nettoyage transversal (cours nettoyage, module 5 : encodage, artefacts, boilerplate) │ ▼ Chunking (cours chunking) │ ▼ Embedding (cours embeddings) │ ▼ Enrichissement de métadonnées (cours métadonnées) │ ▼ Indexation (cours bases de données vectorielles)

Un point important, déjà évoqué au cours nettoyage (module 6, leçon 5, sur les documents hybrides) : la décision "extraction directe ou OCR" ne se prend pas nécessairement au niveau du document entier, mais parfois page par page — un même PDF pouvant mélanger des pages avec texte natif et des pages scannées (une annexe ajoutée par scan, par exemple). Ce cours détaille précisément ce que ce cours précédent laissait de côté : comment exécuter concrètement cette étape d'OCR une fois le besoin détecté.

Le texte produit par l'OCR n'est jamais directement prêt pour le chunking — il nécessite généralement un passage par les techniques de nettoyage transversal déjà vues (correction d'encodage, suppression d'artefacts), car l'OCR introduit ses propres catégories de bruit spécifiques (erreurs de caractères, mots mal segmentés) qui s'ajoutent à celles déjà cataloguées dans le cours nettoyage.

# Le pipeline complet, OCR inclus
def traiter_document(chemin_fichier: str) -> str:
    if necessite_ocr(chemin_fichier):          # rappel cours nettoyage, module 2, leçon 4
        texte_brut = executer_ocr(chemin_fichier)   # CE COURS
    else:
        texte_brut = extraire_texte_natif(chemin_fichier)   # cours nettoyage, modules 2-4

    texte_propre = nettoyer_texte_complet(texte_brut)   # cours nettoyage, module 5

Piège courant Traiter la sortie de l'OCR comme un texte déjà propre, prêt à être directement chunké, en oubliant qu'elle nécessite le même passage par les techniques de nettoyage transversal que n'importe quel autre texte extrait — avec, en plus, des catégories de bruit spécifiques à l'OCR (approfondies au module 7) qui n'existent pas dans une extraction de texte natif.

LEÇON 1.5Erreurs courantes et limites structurelles de l'OCR

Cette dernière leçon du module fondateur rassemble les erreurs typiques de l'OCR et ses limites structurelles — à connaître avant d'aborder les modules techniques suivants, pour calibrer des attentes réalistes.

Confusions de caractères visuellement proches

Certaines paires de caractères sont structurellement ambiguës visuellement : "0" et "O", "1", "l" et "I", "rn" et "m". Ces confusions sont une source d'erreur quasi incompressible, particulièrement sur des polices ou des résolutions qui accentuent ces ressemblances.

Mauvaise segmentation de mise en page

Un document à colonnes multiples, mal segmenté, peut voir son texte lu dans le mauvais ordre (rappel du problème déjà rencontré pour les PDF natifs dans le cours nettoyage, module 2, leçon 5 — mais ici sans le recours aux positions de texte natif, uniquement à partir de l'analyse visuelle de l'image).

Écriture manuscrite

Les moteurs OCR classiques (Tesseract, module 2) sont conçus et entraînés principalement pour du texte imprimé — leur performance sur de l'écriture manuscrite est généralement très dégradée, un cas qui bénéficie davantage des solutions API spécialisées (module 4) ou des modèles de vision multimodaux (module 5).

Tableaux et mises en page complexes

Un moteur OCR de base extrait généralement le texte sans préserver la structure tabulaire (lignes, colonnes) — un problème similaire à celui déjà rencontré pour les tableaux PDF natifs, mais qui nécessite ici des outils de détection de mise en page spécifiques (approfondi au module 6).

Type de contenu Performance OCR classique typique ────────────────────────────────────────────────────────────────────── Texte imprimé net, une colonne Excellente (souvent >98% de précision caractère par caractère) Texte imprimé, mise en page Bonne à moyenne (dépend de la complexe (colonnes, tableaux) qualité de segmentation, module 6) Écriture manuscrite Faible à moyenne (module 4-5 pour de meilleures alternatives) Scan de mauvaise qualité Variable, souvent dégradée (résolution/contraste/bruit (rappel leçon 1.3) faibles)

Ces limites ne signifient pas que l'OCR est peu fiable en général — pour son cas d'usage central (texte imprimé de qualité raisonnable), la précision est aujourd'hui excellente. Elles rappellent simplement qu'il faut calibrer ses attentes et sa stratégie (choix du moteur, prétraitement, validation) selon la nature réelle du corpus à traiter, un principe qui structure l'ensemble des modules suivants.

Piège courant Attendre une précision uniforme et proche de 100% de l'OCR quel que soit le type de contenu, puis être surpris par une dégradation significative sur de l'écriture manuscrite ou des scans de mauvaise qualité. Calibrer ses attentes selon la nature réelle du contenu (leçon 1.3 et ce tableau) évite des déceptions coûteuses en production.

Tesseract : le moteur OCR open-source de référence

Tesseract est le moteur OCR open-source le plus utilisé au monde, maintenu aujourd'hui par Google. Ce module en détaille l'usage complet, des premiers pas jusqu'à la configuration avancée, en comprenant bien ce qui se cache derrière chaque paramètre.

LEÇON 2.1Installation et premiers pas avec Tesseract

Tesseract est un moteur OCR open-source, initialement développé par HP puis maintenu par Google depuis 2006. Contrairement aux solutions API du module 4, Tesseract s'exécute entièrement en local — aucune donnée ne quitte votre machine, un avantage direct pour des documents confidentiels (thème approfondi en leçon 4.5).

Cette simplicité de mise en route (deux commandes d'installation, quelques lignes de code) cache une réalité importante : la qualité du résultat obtenu dépend beaucoup moins de cette configuration minimale que de la qualité de l'image source (rappel du module 1, leçon 3) et de la configuration fine des paramètres de segmentation (leçon 2.2) et de langue (leçon 2.3) qui suivent dans ce module.

LEÇON 2.2Comprendre les modes de segmentation de page (PSM)

Rappel de l'étape 2 du pipeline OCR générique (module 1, leçon 2) : la segmentation détermine comment le moteur découpe la page en zones de texte. Tesseract expose ce choix explicitement via le paramètre PSM (Page Segmentation Mode) — l'un des réglages les plus impactants et les plus mal compris de l'outil.

Les modes PSM les plus utiles en pratique

PSMComportementCas d'usage typique
3 (défaut)Segmentation automatique complète de la page, sans orientation présuméeDocument standard, mise en page inconnue
4Suppose une seule colonne de texte de tailles variablesDocument à une colonne avec titres de tailles différentes
6Suppose un unique bloc de texte uniformeParagraphe isolé, capture d'écran de texte simple
7Traite l'image comme une seule ligne de texteLigne de texte isolée (champ de formulaire scanné)
11Texte épars, sans ordre particulier à préserverTexte disséminé sur l'image sans structure de paragraphe
 
import pytesseract
from PIL import Image

image = Image.open("formulaire_scanne.png")

# PSM 6 : traiter comme un bloc de texte uniforme
texte_bloc = pytesseract.image_to_string(image, config="--psm 6", lang="fra")

# PSM 7 : traiter comme une seule ligne (utile pour un champ isolé)
texte_ligne = pytesseract.image_to_string(image, config="--psm 7", lang="fra")

Le choix du bon PSM peut faire une différence radicale sur la qualité du résultat — un document à mise en page complexe traité avec un PSM inadapté (par exemple, PSM 6 sur une page à deux colonnes) produira un texte où les deux colonnes sont fusionnées de façon incohérente, un problème similaire à celui déjà rencontré pour les PDF natifs à colonnes multiples (cours nettoyage, module 2, leçon 5), mais ici sans les informations de position qu'un PDF natif expose.

Document à 2 colonnes, mauvais PSM (PSM 6, bloc uniforme) : ┌─────────┬─────────┐ Résultat : "Le texte de la colonne │ Colonne │ Colonne │ gauche mélangé avec │ gauche │ droite │ la colonne droite de │ ligne 1 │ ligne 1 │ façon incohérente..." │ ligne 2 │ ligne 2 │ └─────────┴─────────┘ → PSM 3 (automatique) ou une segmentation manuelle préalable des colonnes serait nécessaire
Piège courant Garder le PSM par défaut (3, segmentation automatique) pour tous les documents, sans tester d'autres modes sur des documents à la mise en page atypique (champ de formulaire isolé, ligne unique, mise en page multi-colonnes). Le PSM par défaut est un bon point de départ généraliste, mais rarement optimal pour des cas spécifiques.

LEÇON 2.3Langues, données d'entraînement et modèles Tesseract

Rappel de l'étape 4 du pipeline OCR générique (module 1, leçon 2) : le post-traitement linguistique s'appuie sur des données spécifiques à chaque langue. Tesseract fonctionne avec des fichiers de données de langue (.traineddata) téléchargeables séparément — sans le bon fichier, la reconnaissance se dégrade significativement, un piège similaire à celui déjà rencontré pour les modèles d'embedding monolingues (cours embeddings, module 4, leçon 4).

import pytesseract

# Une seule langue
texte = pytesseract.image_to_string(image, lang="fra")

# Plusieurs langues combinées (document bilingue, rappel cours métadonnées
# module 6, leçon 1, sur le contenu multilingue)
texte_bilingue = pytesseract.image_to_string(image, lang="fra+eng")

Les deux familles de modèles de langue Tesseract

Depuis Tesseract 4, deux familles de modèles coexistent, avec un compromis vitesse/précision différent :

  • Modèles "fast" — plus rapides, basés sur l'ancien moteur de reconnaissance par motifs, une précision légèrement inférieure.
  • Modèles "best" (LSTM) — basés sur un réseau de neurones récurrent (LSTM, Long Short-Term Memory), plus précis mais plus lents, recommandés par défaut sauf contrainte de performance forte.

LEÇON 2.4Configuration avancée et paramètres de reconnaissance

Au-delà du PSM (leçon 2.2) et de la langue (leçon 2.3), Tesseract expose de nombreux autres paramètres de configuration qui permettent d'affiner la reconnaissance pour des cas spécifiques.

Restreindre les caractères attendus (whitelist)

Pour des documents à contenu prévisible (numéros de téléphone, codes postaux, références alphanumériques), restreindre l'ensemble des caractères que Tesseract peut reconnaître élimine une source d'ambiguïté et améliore souvent significativement la précision.

config_chiffres_uniquement = "--psm 7 -c tessedit_char_whitelist=0123456789"

Récupérer des informations de confiance par mot

Au-delà du texte brut, Tesseract peut retourner un score de confiance pour chaque mot reconnu — une information précieuse pour la validation automatique (approfondie au module 7, leçon 2), permettant d'identifier quels mots sont probablement mal reconnus sans validation humaine.

donnees_detaillees = pytesseract.image_to_data(image, lang="fra", output_type=pytesseract.Output.DICT)

for i, mot in enumerate(donnees_detaillees["text"]):
    confiance = donnees_detaillees["conf"][i]
    if mot.strip() and int(confiance) < 60:   # seuil de confiance à calibrer empiriquement
        print(f"Mot potentiellement mal reconnu : '{mot}' (confiance: {confiance})")

Récupérer les positions des mots (bounding boxes)

Tesseract peut aussi retourner la position exacte (coordonnées) de chaque mot détecté sur l'image — une information utile pour reconstituer une mise en page (module 6) ou pour surligner visuellement les zones de faible confiance dans une interface de validation humaine.

for i, mot in enumerate(donnees_detaillees["text"]):
    if mot.strip():
        x, y, largeur, hauteur = (donnees_detaillees[cle][i] for cle in ("left", "top", "width", "height"))
        print(f"'{mot}' à la position ({x}, {y}), taille {largeur}x{hauteur}")

LEÇON 2.5Limites de Tesseract et cas où il échoue

Cette dernière leçon du module trace les limites concrètes de Tesseract — non pour le disqualifier (c'est un outil excellent dans son domaine de compétence) mais pour identifier objectivement les cas où les modules suivants (API cloud, module 4 ; LLM multimodaux, module 5) deviennent nécessaires.

Écriture manuscrite

Rappel du module 1, leçon 5 : Tesseract est entraîné principalement sur du texte imprimé. Sur de l'écriture manuscrite, même soignée, sa précision chute généralement de façon spectaculaire — un cas où les API cloud spécialisées (module 4) ou les modèles de vision multimodaux (module 5) offrent une bien meilleure performance.

Mises en page très complexes sans prétraitement

Malgré les modes PSM (leçon 2.2), Tesseract reste limité face à des mises en page très irrégulières (magazines avec texte qui suit des formes non rectangulaires, documents avec de nombreux encadrés imbriqués) sans un prétraitement de segmentation préalable plus sophistiqué (module 6).

Polices exotiques ou très stylisées

Les modèles de langue de Tesseract sont entraînés sur des polices courantes — une police très stylisée, calligraphique, ou un texte avec une mise en forme artistique inhabituelle dégrade significativement la reconnaissance, même à haute résolution.

Documents avec un fort mélange de contenu (texte + tableaux + images)

Rappel du module 1, leçon 5 : sans détection de mise en page dédiée (module 6), Tesseract traite un document dense en éléments hétérogènes de façon uniforme, ce qui peut mélanger dans le résultat final du texte de légende, du contenu de tableau et du texte narratif sans distinction claire.

MODULE 03 / 08

Prétraitement d'image pour améliorer l'OCR

Rappel du module 2 (leçon 2.5) : beaucoup de "limites de Tesseract" sont en réalité des limites d'une image mal préparée. Ce module détaille les techniques de prétraitement qui améliorent le plus significativement les résultats OCR, souvent avant même d'envisager un changement d'outil.

LEÇON 3.1Pourquoi le prétraitement change tout : principe et impact mesurable

Rappel de l'étape 1 du pipeline OCR générique (module 1, leçon 2) : le prétraitement intervient avant toute reconnaissance de caractères, et conditionne directement la qualité de tout ce qui suit. Cette leçon explique pourquoi cet impact est souvent plus déterminant que le choix du moteur OCR lui-même ou de ses paramètres fins.

Un moteur OCR, quel qu'il soit (Tesseract, module 2 ; API cloud, module 4), a été entraîné sur des images relativement "propres" — texte net, contraste suffisant, orientation correcte. Un scan réel s'écarte souvent de ces conditions idéales : ombres de reliure, légère rotation lors de la numérisation, papier jauni, grain de capteur. Le prétraitement vise à rapprocher l'image réelle des conditions d'entraînement du moteur, plutôt que de demander au moteur de compenser lui-même ces écarts.

Sans prétraitement Avec prétraitement adapté ────────────────────── ────────────────────────── Image brute, contraste faible, Image binarisée, redressée, légèrement inclinée, bruitée contraste maximisé, bruit réduit │ │ ▼ ▼ Moteur OCR (Tesseract, etc.) Moteur OCR (MÊME moteur) │ │ ▼ ▼ Texte avec de nombreuses erreurs Texte nettement plus fidèle, de caractères et de segmentation avec le MÊME moteur, la MÊME configuration

Un point empirique largement observé dans la pratique de l'OCR : améliorer le prétraitement d'image apporte souvent un gain de précision plus important et plus fiable qu'ajuster finement les paramètres du moteur OCR (module 2) ou changer de moteur entièrement (module 4). C'est pourquoi ce module intervient avant les modules sur les solutions API et les LLM multimodaux — un prétraitement soigné peut suffire à résoudre une part significative des problèmes de qualité, quel que soit le moteur utilisé ensuite.

Les quatre familles de traitement de ce module

  • Binarisation et contraste (leçon 3.2) — maximiser la distinction texte/fond.
  • Débruitage et redressement (leçon 3.3) — éliminer les artefacts, corriger une légère rotation.
  • Correction de perspective (leçon 3.4) — pour des photos de documents plutôt que des scans plats.
  • Assemblage en pipeline (leçon 3.5) — combiner ces traitements dans le bon ordre.
Piège courant Passer directement à un moteur OCR plus coûteux (API cloud, module 4) dès qu'un résultat est décevant, sans avoir d'abord exploré si un prétraitement d'image adapté résoudrait le problème à moindre coût. Le prétraitement devrait systématiquement être la première piste d'amélioration testée, avant d'envisager un changement d'outil plus onéreux.

LEÇON 3.2Binarisation, seuillage et amélioration du contraste

La binarisation convertit une image en niveaux de gris ou en couleur vers une image strictement noir et blanc, chaque pixel étant classé comme "texte" (noir) ou "fond" (blanc) — l'une des transformations les plus impactantes du prétraitement OCR.

Seuillage global simple

import cv2

image = cv2.imread("document_scanne.png", cv2.IMREAD_GRAYSCALE)

# Seuillage global : tout pixel en dessous de 127 devient noir, au-dessus devient blanc
_, image_binarisee = cv2.threshold(image, 127, 255, cv2.THRESH_BINARY)

Ce seuillage global fonctionne bien sur des scans à éclairage uniforme, mais échoue sur des documents dont l'éclairage varie d'une zone à l'autre (une photo de document avec une ombre partielle, par exemple) — un seuil unique ne peut pas s'adapter à ces variations locales.

Seuillage adaptatif : s'ajuster localement

# Le seuillage adaptatif calcule un seuil DIFFÉRENT pour chaque région
# de l'image, en fonction de son voisinage local — robuste aux
# variations d'éclairage
image_binarisee_adaptative = cv2.adaptiveThreshold(
    image, 255, cv2.ADAPTIVE_THRESH_GAUSSIAN_C, cv2.THRESH_BINARY, 11, 2
)

La méthode d'Otsu : trouver le seuil optimal automatiquement

Plutôt que de choisir arbitrairement une valeur de seuil (127 dans l'exemple ci-dessus), la méthode d'Otsu calcule automatiquement le seuil optimal en analysant la distribution des niveaux de gris de l'image — une approche particulièrement utile quand on traite un grand nombre de documents avec des caractéristiques de contraste variables.

_, image_otsu = cv2.threshold(image, 0, 255, cv2.THRESH_BINARY + cv2.THRESH_OTSU)
Seuillage global Seuillage adaptatif Méthode d'Otsu ───────────────────── ───────────────────── ───────────────────── Un seuil fixe pour toute Un seuil par région locale Seuil calculé l'image (robuste aux éclairages automatiquement à irréguliers) partir de l'histogramme Rapide, simple Plus robuste, légèrement Pas de valeur à deviner plus coûteux en calcul manuellement
Piège courant Utiliser un seuillage global fixe sur un corpus de scans dont l'éclairage ou le contraste varie significativement d'un document à l'autre, produisant de bons résultats sur certains documents et des résultats médiocres sur d'autres. Le seuillage adaptatif ou la méthode d'Otsu offrent une robustesse bien supérieure face à cette hétérogénéité, au prix d'un coût de calcul très modéré.

LEÇON 3.3Débruitage, désinclinaison (deskew) et correction de rotation

Au-delà du contraste (leçon 3.2), deux autres défauts fréquents des scans réels méritent un traitement dédié : le bruit visuel (rappel module 1, leçon 3) et l'inclinaison du document lors de la numérisation.

Débruitage

import cv2

# Débruitage par filtre médian : remplace chaque pixel par la médiane
# de son voisinage, efficace contre le bruit "poivre et sel" (points
# isolés aberrants) sans trop flouter les contours du texte
image_debruitee = cv2.medianBlur(image_binarisee, 3)

# Alternative : débruitage non-local means, plus sophistiqué mais
# plus coûteux en calcul, pour des images avec un bruit plus complexe
image_debruitee_nlm = cv2.fastNlMeansDenoising(image, h=10)

Détecter l'angle d'inclinaison (skew)

Une numérisation manuelle (scanner à plat, photo de document) introduit souvent une légère rotation involontaire du document par rapport aux bords de l'image — même quelques degrés d'inclinaison peuvent significativement perturber la segmentation en lignes (rappel module 1, leçon 2).

import cv2
import numpy as np

def detecter_angle_inclinaison(image_binaire: np.ndarray) -> float:
    coordonnees = np.column_stack(np.where(image_binaire == 0))   # pixels de texte (noirs)
    angle = cv2.minAreaRect(coordonnees)[-1]
    if angle < -45:
        angle = -(90 + angle)
    else:
        angle = -angle
    return angle

angle_detecte = detecter_angle_inclinaison(image_binarisee)
print(f"Angle d'inclinaison détecté : {angle_detecte:.2f} degrés")

Corriger la rotation (deskew)

def redresser_image(image: np.ndarray, angle: float) -> np.ndarray:
    hauteur, largeur = image.shape[:2]
    centre = (largeur // 2, hauteur // 2)
    matrice_rotation = cv2.getRotationMatrix2D(centre, angle, 1.0)
    return cv2.warpAffine(image, matrice_rotation, (largeur, hauteur),
                            flags=cv2.INTER_CUBIC, borderMode=cv2.BORDER_REPLICATE)

image_redressee = redresser_image(image_binarisee, angle_detecte)

Le débruitage doit être calibré pour éliminer le bruit visuel réel sans sacrifier la netteté des caractères — un compromis à valider visuellement, pas à appliquer systématiquement au maximum.

LEÇON 3.4Détection et correction de la perspective / redressement

Au-delà de la simple inclinaison (rotation dans le plan, leçon 3.3), une photo de document prise avec un smartphone (plutôt qu'un scanner à plat) introduit souvent une déformation de perspective : le document apparaît comme un quadrilatère non rectangulaire, avec des bords qui convergent selon l'angle de prise de vue.

Détecter les quatre coins du document

import cv2
import numpy as np

def detecter_contour_document(image: np.ndarray) -> np.ndarray:
    gris = cv2.cvtColor(image, cv2.COLOR_BGR2GRAY)
    flou = cv2.GaussianBlur(gris, (5, 5), 0)
    bords = cv2.Canny(flou, 75, 200)

    contours, _ = cv2.findContours(bords, cv2.RETR_LIST, cv2.CHAIN_APPROX_SIMPLE)
    plus_grand_contour = max(contours, key=cv2.contourArea)

    perimetre = cv2.arcLength(plus_grand_contour, True)
    approximation = cv2.approxPolyDP(plus_grand_contour, 0.02 * perimetre, True)

    if len(approximation) == 4:
        return approximation.reshape(4, 2)
    raise ValueError("Impossible de détecter un quadrilatère à 4 coins")

Appliquer une transformation de perspective pour redresser le document

def redresser_perspective(image: np.ndarray, coins: np.ndarray) -> np.ndarray:
    largeur_cible, hauteur_cible = 1000, 1400   # dimensions du document redressé
    points_cibles = np.array([
        [0, 0], [largeur_cible, 0], [largeur_cible, hauteur_cible], [0, hauteur_cible]
    ], dtype="float32")

    matrice_transformation = cv2.getPerspectiveTransform(coins.astype("float32"), points_cibles)
    return cv2.warpPerspective(image, matrice_transformation, (largeur_cible, hauteur_cible))
Photo avec perspective déformée : Après correction de perspective : ╱────────────╲ ┌──────────────┐ ╱ Document ╲ │ Document │ ╱ (trapèze, ╲ │ (rectangle │ ╱ pris de biais) ╲ │ redressé) │ ╱──────────────────────╲ └──────────────┘ → Les lignes de texte convergent selon → Lignes de texte l'angle de prise de vue, une distorsion parallèles, mise en que le simple redressement de rotation page rectangulaire (leçon 3.3) ne corrige pas restaurée

Cette correction est particulièrement pertinente pour des corpus alimentés par des photos de documents prises au smartphone (factures photographiées par des utilisateurs, par exemple) plutôt que par des scanners professionnels à plat, où ce type de déformation ne se produit généralement pas.

Piège courant Confondre la correction de rotation simple (deskew, leçon 3.3) avec la correction de perspective — la première suffit pour un scan légèrement de travers mais à plat, la seconde est nécessaire pour une photo prise en angle, un cas bien plus fréquent avec des captures au smartphone qu'avec des scanners dédiés.

LEÇON 3.5Construire un pipeline de prétraitement avec OpenCV et Pillow

Cette dernière leçon du module assemble les techniques précédentes (binarisation, débruitage, redressement, correction de perspective) en un pipeline modulaire complet, dans l'ordre logique qui maximise la qualité du résultat final.

import cv2
import numpy as np

def pipeline_pretraitement_complet(chemin_image: str) -> np.ndarray:
    image = cv2.imread(chemin_image)

    # 1. Correction de perspective si le document n'est pas déjà rectangulaire
    #    (pertinent pour des photos smartphone, leçon 3.4 — peut être ignoré
    #    pour des scans déjà plats et rectangulaires)
    try:
        coins = detecter_contour_document(image)
        image = redresser_perspective(image, coins)
    except ValueError:
        pass   # pas de quadrilatère net détecté, on continue sans cette étape

    # 2. Conversion en niveaux de gris
    gris = cv2.cvtColor(image, cv2.COLOR_BGR2GRAY)

    # 3. Débruitage (leçon 3.3)
    debruite = cv2.fastNlMeansDenoising(gris, h=10)

    # 4. Binarisation par la méthode d'Otsu (leçon 3.2)
    _, binaire = cv2.threshold(debruite, 0, 255, cv2.THRESH_BINARY + cv2.THRESH_OTSU)

    # 5. Correction de l'inclinaison résiduelle (leçon 3.3)
    angle = detecter_angle_inclinaison(binaire)
    image_finale = redresser_image(binaire, angle)

    return image_finale

# Utilisation avec Tesseract (module 2)
image_pretraitee = pipeline_pretraitement_complet("document_scanne.jpg")
texte = pytesseract.image_to_string(image_pretraitee, lang="fra")

Pourquoi cet ordre précis des étapes

L'ordre choisi n'est pas arbitraire : la correction de perspective (étape 1) doit intervenir sur l'image couleur ou en niveaux de gris originale, avant toute binarisation, car elle a besoin de détecter des contours qui seraient déjà perdus après binarisation. Le débruitage (étape 3) intervient avant la binarisation (étape 4) pour éviter que du bruit ne soit interprété à tort comme des pixels de texte lors du seuillage. La correction d'inclinaison finale (étape 5) s'applique en dernier, sur l'image déjà binarisée et débruitée, pour une détection d'angle plus fiable.

Ordre recommandé du pipeline de prétraitement : 1. Correction de perspective (sur image originale, AVANT binarisation) 2. Niveaux de gris 3. Débruitage (AVANT binarisation, pour ne pas figer le bruit) 4. Binarisation (Otsu) 5. Correction d'inclinaison (sur image déjà binarisée, la plus fiable à ce stade) → Inverser cet ordre (par exemple, binariser avant de débruiter) dégrade généralement la qualité du résultat final.

Ce module clôt la partie "amélioration de l'image source" du cours. Les modules suivants explorent des alternatives et compléments à Tesseract — les solutions API cloud (module 4) et les modèles de vision multimodaux (module 5) — qui peuvent parfois se dispenser d'un prétraitement aussi poussé grâce à leur propre robustesse intégrée, un compromis à évaluer au cas par cas.

Piège courant Appliquer systématiquement l'intégralité de ce pipeline de prétraitement à cinq étapes sur tous les documents, y compris ceux qui sont déjà de bonne qualité (scan net, bien aligné), ajoutant un coût de calcul inutile. Une détection préalable de la qualité de l'image (résolution, contraste, angle d'inclinaison) permet de n'appliquer que les corrections réellement nécessaires à chaque document.

LEÇON 5.1L'essor des modèles vision-langage pour l'OCR

Les modèles de langage les plus récents (GPT-4o, Claude, Gemini) intègrent nativement une capacité de vision : ils peuvent recevoir une image en entrée, au même titre qu'un texte, et raisonner dessus — y compris en extraire le texte qu'elle contient. Cette capacité change fondamentalement l'approche par rapport aux modules précédents : au lieu d'un pipeline dédié (segmentation, reconnaissance de caractères, post-traitement linguistique — rappel module 1, leçon 2), un unique modèle traite l'image de bout en bout, en s'appuyant sur la même compréhension contextuelle qui lui permet par ailleurs de raisonner sur du texte.

Pipeline OCR classique (Tesseract, API cloud) : Image ──► Prétraitement ──► Segmentation ──► Reconnaissance ──► Post-traitement (module 3) (module 1.2) caractère par linguistique caractère (module 1.2) Approche LLM multimodal (ce module) : Image ──► LLM multimodal (une seule requête, raisonnement de bout en bout) │ ▼ Texte extrait ET compris contextuellement en une seule étape

Cette différence n'est pas seulement technique — elle change la nature même de la tâche. Un moteur OCR classique reconnaît des caractères sans "comprendre" ce qu'il lit (rappel du cours embeddings, module 1, sur la distinction entre traitement statistique et compréhension). Un LLM multimodal, en revanche, mobilise sa capacité de compréhension du langage pour désambiguïser des caractères ambigus à partir du sens probable de la phrase — un avantage significatif sur des cas difficiles (approfondi en leçon 5.3), mais aussi une source de risques spécifiques (leçon 5.4).

Cette évolution ne rend pas les modules précédents obsolètes — elle ajoute une option supplémentaire dans l'arsenal, avec ses propres compromis coût/précision/latence à évaluer, exactement comme pour le choix entre Tesseract et les API cloud (module 4, leçon 5).

Piège courant Considérer les LLM multimodaux comme un remplacement universel et systématique de l'OCR classique, simplement parce qu'ils sont plus récents et plus sophistiqués en apparence. Comme pour tout choix technique de cette série de cours, la pertinence dépend du cas d'usage (leçon 5.3 et 5.4) — pas de la nouveauté de l'approche.

LEÇON 5.3Avantages : compréhension contextuelle, mise en page complexe

Cette leçon détaille les cas où un LLM multimodal apporte un avantage mesurable par rapport aux approches des modules précédents — des avantages qui découlent directement de sa capacité de compréhension contextuelle, absente des moteurs OCR classiques.

Désambiguïsation contextuelle de caractères incertains

Rappel du module 1, leçon 5 : certains caractères sont visuellement ambigus ("0" vs "O", "1" vs "l"). Un moteur OCR classique reconnaît chaque caractère indépendamment (ou avec un post-traitement linguistique limité, module 1 leçon 2) ; un LLM multimodal peut mobiliser le sens global de la phrase pour lever l'ambiguïté — par exemple, déduire qu'un caractère ambigu est un "0" plutôt qu'un "O" parce que le contexte immédiat est un numéro de téléphone plutôt qu'un mot.

Mise en page complexe et hétérogène

Rappel du module 1, leçon 5, et module 6 : les mises en page mêlant texte, tableaux, encadrés et légendes de façon dense posent un défi de segmentation aux moteurs OCR classiques. Un LLM multimodal, en "voyant" l'image dans son ensemble plutôt qu'en la segmentant mécaniquement, peut souvent mieux restituer les relations logiques entre ces éléments (quel texte se rapporte à quel encadré, par exemple).

Rappel du module 2, leçon 5 : Tesseract performe mal sur l'écriture manuscrite. Les modèles de vision multimodaux les plus récents montrent une performance sensiblement meilleure sur ce cas, bénéficiant d'un entraînement sur des volumes de données visuelles bien plus larges et variés que les moteurs OCR classiques.

LEÇON 5.4Limites : hallucination, coût, latence

Cette leçon détaille les limites spécifiques de l'approche par LLM multimodal — des risques qui n'existent pas, ou existent sous une forme différente, avec les moteurs OCR classiques des modules précédents.

Le risque d'hallucination : un LLM peut "inventer" du texte

C'est la limite la plus critique et la plus spécifique à cette approche : un LLM multimodal, en cas de doute sur un passage illisible ou ambigu, peut générer un texte plausible mais factuellement incorrect plutôt que de signaler une incertitude — un comportement fondamentalement différent d'un moteur OCR classique, qui produit généralement un score de confiance faible ou un caractère incorrect isolé (rappel module 2, leçon 4) plutôt qu'un mot entièrement inventé mais cohérent avec le contexte.

Face à un mot illisible/flou dans l'image : OCR classique (Tesseract) : LLM multimodal : "L'ang[?]ment recommandé" "L'alignement recommandé" → caractère incorrect isolé, → un mot COHÉRENT et PLAUSIBLE, signal de faible confiance mais peut-être complètement disponible (module 2, leçon 4) FAUX par rapport à l'original → Le risque du LLM est plus insidieux : le résultat SEMBLE cohérent, ce qui le rend plus difficile à détecter comme erroné qu'une erreur de caractère isolée et visible.

Coût significativement plus élevé par document

Rappel des ordres de grandeur déjà rencontrés dans le cours embeddings (module 4, leçon 5) pour l'enrichissement par LLM : un appel à un LLM multimodal coûte généralement bien plus cher par page qu'un appel Tesseract (gratuit) ou même une API OCR dédiée (module 4) — un facteur déterminant pour un traitement à grande échelle.

Latence plus élevée

Un LLM multimodal traite généralement une image plus lentement qu'un moteur OCR dédié optimisé spécifiquement pour cette tâche — un facteur à considérer pour un traitement en masse d'un grand corpus, où la latence cumulée peut devenir significative.

Piège courant Faire confiance aveuglément à une extraction par LLM multimodal parce que le résultat "a l'air cohérent", sans mécanisme de validation. Rappel du principe déjà établi tout au long de cette série (cours métadonnées, module 4, leçon 5, sur la validation des enrichissements LLM) : toute sortie de LLM devrait être validée sur un échantillon avant d'être généralisée, particulièrement ici où l'hallucination est plus difficile à détecter visuellement qu'une erreur OCR classique.

LEÇON 6.3Extraction de formulaires et de champs clé-valeur

Rappel du module 4 (leçon 4.3, AWS Textract) : de nombreux documents scannés sont des formulaires (factures, fiches administratives, questionnaires) où l'information utile se présente sous forme de paires "étiquette : valeur" plutôt que de texte continu — un cas qui mérite un traitement spécifique.

Le principe de la détection clé-valeur

Un formulaire scanné présente généralement des étiquettes fixes ("Nom :", "Date de naissance :", "Montant total :") suivies ou précédées de leur valeur associée, souvent séparées visuellement (deux points, espacement, alignement en colonne). La détection clé-valeur identifie ces paires en analysant la proximité spatiale et les motifs visuels typiques (deux-points, cases à remplir).

# Rappel du module 4 (AWS Textract), approfondi ici conceptuellement
def associer_cle_valeur_par_proximite(mots_avec_positions: list[dict]) -> list[dict]:
    """Approche heuristique simplifiée : une étiquette suivie d'un
    deux-points est probablement suivie de sa valeur sur la même ligne
    ou juste en dessous."""
    paires = []
    for i, mot in enumerate(mots_avec_positions):
        if mot["texte"].endswith(":"):
            candidats_valeur = [
                m for m in mots_avec_positions[i+1:i+4]
                if abs(m["y"] - mot["y"]) < 20   # même ligne approximativement
            ]
            if candidats_valeur:
                paires.append({
                    "cle": mot["texte"].rstrip(":"),
                    "valeur": " ".join(m["texte"] for m in candidats_valeur),
                })
    return paires

LEÇON 6.4Reconstituer l'ordre de lecture sur des mises en page complexes

Trier les blocs détectés selon leur position

Une fois les blocs de mise en page identifiés (leçon 6.2), les ordonner correctement nécessite de trier selon leur position verticale ET horizontale, en tenant compte de la structure en colonnes éventuelle — un tri naïf uniquement par coordonnée verticale (haut vers bas) mélangerait les colonnes de la même façon que déjà observé pour les PDF (cours nettoyage, module 2, leçon 5).

def trier_blocs_par_colonnes(blocs: list[dict], seuil_x_colonne: float) -> list[dict]:
    """Rappel direct de separer_colonnes du cours nettoyage (module 2,
    leçon 5), appliqué ici à des blocs détectés par layout detection
    plutôt qu'à des positions de texte natif PDF."""
    colonne_gauche = sorted(
        [b for b in blocs if b["x"] < seuil_x_colonne], key=lambda b: b["y"]
    )
    colonne_droite = sorted(
        [b for b in blocs if b["x"] >= seuil_x_colonne], key=lambda b: b["y"]
    )
    return colonne_gauche + colonne_droite

LEÇON 7.1Mesurer la qualité d'une extraction OCR (métriques CER/WER)

Deux métriques standard permettent de mesurer objectivement la qualité d'une extraction OCR, en la comparant à un texte de référence connu (vérité terrain) — un principe similaire aux métriques recall@k et MRR déjà utilisées pour évaluer le retrieval dans les cours précédents, mais adapté à la comparaison de deux textes plutôt qu'à un classement de résultats.

CER (Character Error Rate) : taux d'erreur au niveau caractère

Le CER mesure la proportion de caractères qui diffèrent entre le texte extrait et le texte de référence, en tenant compte des insertions, suppressions et substitutions nécessaires pour transformer l'un en l'autre (distance d'édition, déjà rencontrée dans le cours chunking pour la détection de similarité approximative de lignes).

import Levenshtein

def calculer_cer(texte_extrait: str, texte_reference: str) -> float:
    distance = Levenshtein.distance(texte_extrait, texte_reference)
    return distance / max(len(texte_reference), 1)

texte_ref = "Le chunking est une étape essentielle pour un bon système RAG."
texte_ocr = "Le chunklng est une étape essentielle pour un bon systeme RAG."

cer = calculer_cer(texte_ocr, texte_ref)
print(f"CER : {cer:.2%}")   # ex: 3.2% — proportion de caractères erronés

WER (Word Error Rate) : taux d'erreur au niveau mot

Le WER applique le même principe de distance d'édition, mais au niveau des mots plutôt que des caractères — une métrique parfois plus représentative de l'impact réel sur la compréhension, car un seul caractère erroné dans un mot le rend généralement tout aussi incompréhensible qu'un mot entièrement faux.

def calculer_wer(texte_extrait: str, texte_reference: str) -> float:
    mots_extraits = texte_extrait.split()
    mots_reference = texte_reference.split()
    distance = Levenshtein.distance(mots_extraits, mots_reference)   # distance sur des listes de mots
    return distance / max(len(mots_reference), 1)

wer = calculer_wer(texte_ocr, texte_ref)
print(f"WER : {wer:.2%}")

LEÇON 7.2Détecter automatiquement une extraction OCR de mauvaise qualité

Cette leçon détaille des heuristiques de détection de mauvaise qualité qui ne nécessitent pas de vérité terrain — un principe similaire aux métriques de qualité de texte déjà établies dans le cours nettoyage (module 7, leçon 3).

Score de confiance moyen du moteur OCR

Rappel du module 2, leçon 4 : Tesseract (et les API cloud, module 4) retournent généralement un score de confiance par mot ou par caractère. Un score de confiance moyen anormalement bas sur l'ensemble d'un document est un signal direct et peu coûteux à calculer.

def score_confiance_document(donnees_ocr: dict, seuil_alerte: float = 70) -> dict:
    confiances = [int(c) for c in donnees_ocr["conf"] if int(c) >= 0]
    confiance_moyenne = sum(confiances) / len(confiances) if confiances else 0
    return {
        "confiance_moyenne": confiance_moyenne,
        "alerte": confiance_moyenne < seuil_alerte,

Analyse de la plausibilité linguistique

Rappel du cours nettoyage (module 7, leçon 3) : un ratio anormalement élevé de "mots" qui ne correspondent à aucun mot reconnu d'un dictionnaire de la langue attendue est un signal fort de dégradation OCR — un texte de bonne qualité contient presque exclusivement des mots reconnaissables, alors qu'un texte OCR dégradé accumule des suites de caractères qui ne forment pas de mots réels.

import enchant   # bibliothèque de vérification orthographique

dictionnaire_fr = enchant.Dict("fr_FR")

def ratio_mots_reconnus(texte: str) -> float:
    mots = [m.strip(".,;:!?") for m in texte.split() if m.strip(".,;:!?")]
    if not mots:
        return 1.0
    mots_reconnus = sum(1 for m in mots if dictionnaire_fr.check(m))
    return mots_reconnus / len(mots)

LEÇON 7.3Correction post-OCR : dictionnaires, règles, modèles de langue

Une fois une zone de texte suspecte détectée (leçon 7.2), plusieurs techniques permettent de corriger automatiquement certaines erreurs OCR, sans nécessiter un retraitement complet de l'image ni un recours systématique à un LLM multimodal (module 5, coûteux à grande échelle).

Correction par distance au dictionnaire

import enchant

dictionnaire_fr = enchant.Dict("fr_FR")

def corriger_mot_par_dictionnaire(mot: str) -> str:
    if dictionnaire_fr.check(mot):
        return mot   # déjà un mot valide, rien à corriger

    suggestions = dictionnaire_fr.suggest(mot)
    return suggestions[0] if suggestions else mot   # meilleure suggestion, ou inchangé

texte_corrige = " ".join(corriger_mot_par_dictionnaire(m) for m in texte_ocr.split())

Règles de correction ciblées sur les confusions connues

Rappel du module 1, leçon 5 : certaines confusions de caractères sont particulièrement fréquentes et prévisibles (O/0, l/1/I, rn/m). Des règles de correction ciblées, appliquées uniquement dans des contextes où l'ambiguïté est probable (un chiffre au milieu d'une séquence de lettres, par exemple), peuvent corriger ces cas sans dictionnaire complet.

import re

def corriger_confusions_chiffres_lettres(mot: str) -> str:
    # Si le mot est composé presque entièrement de lettres mais contient
    # un "0" isolé au milieu, c'est probablement un "O" mal reconnu
    if re.match(r"^[A-Za-z]*0[A-Za-z]+$", mot):
        return mot.replace("0", "O")
    return mot

Correction via un modèle de langue contextuel

Une approche plus sophistiquée utilise un modèle de langue (qui prédit la probabilité d'une séquence de mots) pour identifier et corriger des mots peu probables dans leur contexte — une approche conceptuellement proche du post-traitement linguistique déjà intégré dans certains moteurs OCR (rappel module 1, leçon 2), mais appliquée ici comme une étape de correction externe et personnalisable, potentiellement avec un LLM léger utilisé uniquement pour cette tâche de correction ciblée (rappel module 5, leçon 5, sur l'usage du LLM en validation plutôt qu'en extraction complète).

Piège courant Appliquer une correction par dictionnaire de façon aveugle sur l'ensemble du texte, y compris sur des mots qui sont volontairement absents du dictionnaire standard (noms propres, termes techniques, références de contrat) — une "correction" qui remplacerait alors une donnée correcte mais rare par un mot du dictionnaire plus fréquent mais erroné. Toujours limiter la correction automatique aux zones identifiées comme suspectes (leçon 7.2), pas à l'ensemble du texte indistinctement.

LEÇON 8.1Pipeline complet : du scan brut au texte propre pour le chunking

Voici un pipeline complet qui relie la détection du besoin d'OCR (rappel cours nettoyage, module 2, leçon 4) au texte final propre, prêt pour le chunking — assemblant le prétraitement (module 3), le choix de moteur (modules 2, 4, 5), l'extraction de structure (module 6) et la validation (module 7).

def pipeline_ocr_complet(chemin_document: str) -> dict:
    # 1. Détection du besoin d'OCR (rappel cours nettoyage, module 2, leçon 4)
    if not necessite_ocr(chemin_document):
        return {"texte": extraire_texte_natif(chemin_document), "ocr_utilise": False}

    # 2. Détection de mise en page pour router chaque région (module 6, leçon 2)
    resultat_layout = detecter_mise_en_page(chemin_document)

    contenu = {"titres": [], "paragraphes": [], "tableaux": []}
    for bloc in resultat_layout:
        # 3. Prétraitement de la région avant OCR (module 3)
        region_pretraitee = pipeline_pretraitement_complet_region(bloc)

        if bloc.type == "Table":
            # 4a. Extraction de tableau structurée (module 6, leçon 1 et 3)
            contenu["tableaux"].append(extraire_tableau_structure(region_pretraitee))
        else:
            # 4b. Extraction hybride Tesseract/LLM selon la confiance (module 5, leçon 5)
            resultat_texte = extraire_texte_hybride(region_pretraitee)
            cle = "titres" if bloc.type == "Title" else "paragraphes"
            contenu[cle].append(resultat_texte["texte"])

    # 5. Validation de qualité globale (module 7, leçon 2)
    texte_assemble = assembler_contenu_ordonne(contenu, resultat_layout)   # module 6, leçon 4
    diagnostics = diagnostiquer_extraction(texte_assemble)

    # 6. Nettoyage transversal (rappel cours nettoyage, module 5) avant le chunking
    texte_final = nettoyer_texte_complet(texte_assemble)

    return {
        "texte": texte_final,
        "ocr_utilise": True,
        "tableaux_detectes": len(contenu["tableaux"]),
        "alertes_qualite": diagnostics,
    }

Ce pipeline illustre la continuité entre ce cours et la série complète de préparation de données pour RAG : l'OCR résout un problème d'accès à l'information (un document image devient du texte), tandis que le chunking, l'embedding, l'enrichissement de métadonnées et l'indexation (cours précédents de la série) prennent le relais une fois ce texte disponible — l'OCR n'étant qu'une étape d'entrée supplémentaire dans un pipeline déjà bien établi.

Piège courant Traiter le texte issu de l'OCR comme équivalent en qualité à un texte extrait nativement (rappel cours nettoyage), en lui appliquant exactement le même chunking sans tenir compte du fait qu'il peut contenir des erreurs de caractères résiduelles (module 7) qui n'existent pas dans un texte natif — une vigilance supplémentaire, notamment sur les métriques de qualité (module 7, leçon 2), reste de mise même après un pipeline OCR soigné.

Ces archives contiennent : des factures avec des tableaux de lignes de produits, des relevés bancaires scannés au smartphone par les clients (souvent en perspective légère), des notes manuscrites de commentaires d'audit, et des formulaires administratifs standardisés. Quelques pistes de réflexion pour vous guider (à consulter après avoir tenté l'exercice vous-même) :

Piste pour la contrainte de confidentialité

Des données financières clients avec une forte exigence de confidentialité orientent fortement vers Tesseract en local (module 2) plutôt que des API cloud ou LLM multimodaux qui transmettent les données à un tiers (rappel module 4, leçon 5) — sauf pour les cas les plus difficiles où le gain de précision justifierait une exception ponctuelle et documentée.

Piste pour les factures avec tableaux

Une détection de mise en page (module 6, leçon 2) et une extraction de tableau structurée (module 6, leçon 1) sont prioritaires ici — le contenu financier précis (montants, quantités) doit impérativement conserver sa structure ligne/colonne pour rester exploitable.

Piste pour les relevés photographiés en perspective

La correction de perspective (module 3, leçon 4) est une étape de prétraitement incontournable avant tout OCR sur ces documents, la déformation géométrique dégradant sinon fortement la qualité de reconnaissance.

Piste pour les notes manuscrites

Rappel du module 1 (leçon 5) et du module 5 (leçon 3) : l'écriture manuscrite est le point faible de Tesseract. Si la confidentialité stricte exclut les solutions cloud/LLM pour ce contenu, il faut accepter un taux d'erreur plus élevé sur ces notes spécifiques, ou envisager une validation humaine ciblée uniquement sur ce sous-ensemble (probablement un faible volume par rapport aux 80 000 pages totales).

Piste pour tenir le budget à ce volume

Une architecture hybride (module 5, leçon 5) où Tesseract avec prétraitement (module 3) traite la majorité des documents standards, avec un routage vers une validation humaine ciblée (plutôt qu'une API cloud coûteuse, compte tenu de la confidentialité) pour les cas de faible confiance (module 7, leçon 2), permettrait de maîtriser le coût tout en respectant la contrainte de confidentialité.

Piège courant Recommander systématiquement les LLM multimodaux ou les API cloud (module 4-5) pour leur précision supérieure, sans tenir compte de la contrainte de confidentialité stricte énoncée dans le cas — un rappel du principe transversal de toute cette série : la meilleure solution est celle qui respecte les contraintes réelles du projet, pas celle qui maximise un seul critère de qualité isolément.
