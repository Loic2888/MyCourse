Logs et Traces d'Agents IA

Nettoyage et structuration pour debug et amélioration — comment capturer, nettoyer, anonymiser et structurer les traces d'exécution d'un agent IA pour en faire un outil réel de diagnostic et d'amélioration continue. 8 modules, 40 leçons.

MODULE 01 / 08

Fondamentaux des logs et traces d'agents IA

Ce dernier cours du bloc "Préparation de Données pour Agents IA" traite une dimension qui referme la boucle des cours précédents : une fois qu'un agent utilise le function calling (cours 17) et gère des données statiques et temps réel (cours 18), comment observer ce qu'il fait réellement, diagnostiquer ses échecs, et transformer cette observation en amélioration continue.

LEÇON 1.1Log, trace, span : les distinctions de base

Trois termes reviennent constamment dans ce domaine, et sont souvent confondus alors qu'ils désignent des concepts précis et complémentaires.

LOG (journal) Un enregistrement ponctuel d'un événement, horodaté — "l'appel à la fonction obtenir_stock a échoué à 14h32:07". Un log est généralement une entrée isolée, sans structure hiérarchique intrinsèque avec d'autres logs. SPAN Une unité de travail avec un début et une fin mesurés — "la génération de la réponse par le LLM a duré de 14h32:05.100 à 14h32:06.850". Un span capture une DURÉE, pas seulement un instant. TRACE L'arborescence complète de spans qui représente le traitement d'une seule requête utilisateur de bout en bout — la question posée, la décision du LLM, l'appel de fonction, la validation, la réponse finale, chacun étant un span de cette même trace.

Cette hiérarchie n'est pas un détail terminologique : elle détermine directement ce qu'on peut faire avec les données collectées. Un simple log isolé ("erreur de validation") indique QU'un problème est survenu ; une trace complète permet de reconstituer POURQUOI — quelle question a mené à quelle décision, quels arguments ont été générés, à quelle étape précise la validation a échoué (rappel cours 17, module 4).

Relation entre les trois concepts : TRACE (une requête utilisateur complète) ├── SPAN : réception de la question [LOG : question reçue] ├── SPAN : décision du LLM (200ms) [LOG : outil choisi] ├── SPAN : appel de fonction (450ms) │ ├── SPAN : validation des arguments (5ms) [LOG : validation OK] │ └── SPAN : exécution de l'appel (445ms) [LOG : résultat reçu] └── SPAN : formulation de la réponse (800ms) [LOG : réponse envoyée] → Chaque LOG documente un ÉVÉNEMENT ponctuel ; chaque SPAN mesure une DURÉE ; la TRACE relie l'ensemble en une histoire complète
Piège courant Se contenter de logs isolés et non reliés entre eux (une pratique héritée du logging applicatif classique) pour un système agentique dont la valeur diagnostique réside précisément dans la capacité à reconstituer l'enchaînement complet des décisions — un agent qui échoue silencieusement après trois étapes de raisonnement est indiagnosticable si ces trois étapes ne sont pas reliées dans une même trace.

LEÇON 1.2Pourquoi les logs d'agents IA diffèrent des logs applicatifs classiques

Un système logiciel classique (une API REST, par exemple) a un comportement largement déterministe : une même requête, avec les mêmes paramètres, produit systématiquement le même chemin d'exécution. Un agent IA n'a pas cette propriété — le LLM peut choisir des chemins différents (quel outil appeler, avec quels arguments, dans quel ordre) pour des questions très similaires, voire identiques.

Logging applicatif classique Logging d'agent IA ──────────────────────────── ──────────────────────────── Chemin d'exécution largement Chemin d'exécution VARIABLE prévisible à l'avance d'une requête à l'autre, même pour des questions Le log sert principalement à similaires CONFIRMER que le chemin attendu s'est bien déroulé Le log doit capturer QUEL chemin a été emprunté, pas Les erreurs sont généralement seulement s'il a réussi des EXCEPTIONS clairement identifiables (stack trace) Les "erreurs" incluent des cas plus subtils : décision correcte mais réponse de mauvaise qualité, boucle agentique qui tourne en rond (rappel cours 17, module 6)

Cette différence de nature justifie un contenu de log spécifique : au-delà des informations techniques classiques (latence, code d'erreur), un log d'agent doit capturer le raisonnement — quelle décision a été prise, sur la base de quelles informations, avec quel degré de confiance apparent — pour permettre de comprendre non seulement "qu'est-ce qui a échoué" mais "pourquoi le modèle a-t-il choisi cette voie".

Piège courant Réutiliser telles quelles les pratiques de logging d'une application classique (uniquement les erreurs techniques, les codes de statut, la latence) pour un agent IA, en omettant l'information la plus précieuse pour le débogage d'un agent : la trace du raisonnement et des décisions qui ont mené au résultat observé.
Exercice Décrivez un scénario où un agent produirait une réponse techniquement "réussie" (aucune erreur, aucun crash) mais néanmoins incorrecte ou inadaptée — un cas que le logging classique ne détecterait pas.

LEÇON 1.4Où le logging s'insère dans l'architecture d'un agent

Cette leçon situe le logging dans le pipeline complet d'un agent, en reliant explicitement ce cours aux deux précédents (function calling, cours 17 ; gestion temps réel/statique, cours 18).

Le logging traverse TOUTES les étapes déjà vues dans ce bloc : Question utilisateur │ ▼ [LOG : requête reçue, horodatage, identifiant utilisateur] Décision du LLM (RAG ou function calling — cours 18, module 4) │ ▼ [LOG : source choisie, raisonnement apparent] Appel de fonction (cours 17) ou recherche RAG (cours 9-13) │ ▼ [LOG : arguments, résultat, validation — cours 17, module 4] Gestion de la fraîcheur, cache, repli éventuel (cours 18, module 5-7) │ ▼ [LOG : fraîcheur de la donnée, cache utilisé ou non, repli déclenché] Formulation de la réponse finale │ ▼ [LOG : réponse envoyée, latence totale, coût estimé]

Ce schéma illustre que le logging n'est pas une couche ajoutée après coup, mais un fil qui devrait accompagner chaque décision déjà prise dans les cours précédents : le mécanisme de journalisation d'audit du cours 17 (module 7, leçon 7.4) et le monitoring de fraîcheur du cours 18 (module 7, leçon 7.4) sont en réalité des instances particulières du sujet traité en profondeur dans ce cours 19.

Piège courant Considérer le logging comme une fonctionnalité indépendante à ajouter une fois l'agent construit, plutôt que comme une préoccupation transverse à intégrer dès la conception de chaque composant (function calling, gestion de fraîcheur, orchestration) — un logging ajouté après coup capture rarement les informations qui se sont révélées, après un incident, être les plus précieuses.
Exercice Pour l'architecture de l'agent de support des cours 17-18, identifiez à quelle étape précise vous ajouteriez un log si vous deviez n'en choisir qu'une seule, la plus critique pour le débogage.

LEÇON 1.5Erreurs courantes de logging

Cette dernière leçon du module recense les erreurs les plus fréquentes lors de la mise en place d'un système de logging pour un agent IA — des erreurs approfondies individuellement dans les modules suivants.

Erreur 1 : sous-logger

Ne capturer que le strict minimum technique (succès/échec, latence globale) sans le contenu du raisonnement — rendant tout débogage a posteriori impossible pour les cas les plus subtils (rappel leçon 1.2).

Erreur 2 : sur-logger sans structure

À l'inverse, tout capturer sans discipline de structuration (texte libre non structuré, formats incohérents entre composants) produit un volume de données inexploitable — un problème approfondi au module 3 de ce cours.

Erreur 3 : logger des données sensibles sans protection

Les prompts et réponses d'un agent contiennent fréquemment des informations personnelles (nom, email, numéro de commande relié à une identité) — les logger sans anonymisation crée un risque de conformité et de sécurité significatif, traité en détail au module 4.

Erreur 4 : ne jamais exploiter les logs collectés

Un système qui collecte scrupuleusement des logs volumineux, mais dont personne ne consulte ni n'analyse jamais le contenu, n'apporte aucune valeur réelle — le module 6 de ce cours traite spécifiquement comment transformer des logs en signaux d'amélioration concrets.

Les quatre erreurs à éviter, résumées : 1. SOUS-LOGGER → Débogage impossible pour les cas subtils 2. SUR-LOGGER sans structure → Volume inexploitable 3. Données sensibles NON PROTÉGÉES → Risque de conformité et sécurité 4. Logs jamais EXPLOITÉS → Investissement sans retour

Les modules suivants traitent chacune de ces erreurs : le module 2 détaille la structure technique d'une trace, le module 3 la discipline de nettoyage et normalisation, le module 4 la protection des données sensibles, et les modules 5-6 l'exploitation effective des logs pour le débogage et l'amélioration continue.

Piège courant Traiter ces quatre erreurs comme des choix indépendants les uns des autres, alors qu'elles s'équilibrent mutuellement : résoudre l'erreur 1 (sous-logger) en capturant davantage de contenu aggrave mécaniquement le risque de l'erreur 3 (données sensibles) si l'anonymisation n'est pas conçue en parallèle — la conception d'un système de logging doit traiter ces quatre dimensions simultanément, pas séquentiellement.
Exercice de synthèse Pour clore ce module : parmi les quatre erreurs listées, laquelle vous semble la plus probable dans un projet que vous avez connu ou pourriez rencontrer — et pourquoi ?
MODULE 02 / 08

Anatomie d'une trace d'agent

Ce module approfondit techniquement les concepts introduits à la leçon 1.1 : comment structurer concrètement une trace d'agent, la corréler entre composants, et s'appuyer sur des standards existants plutôt que de réinventer un format propriétaire.

LEÇON 2.1Trace, span et l'arborescence d'une exécution d'agent

Rappel de la leçon 1.1 : une trace est une arborescence de spans. Cette leçon détaille comment cette arborescence se construit concrètement pour un agent, en particulier quand plusieurs outils sont appelés en séquence ou en parallèle (rappel cours 17, module 6).

import uuid
from datetime import datetime

class Trace:
    def __init__(self):
        self.trace_id = str(uuid.uuid4())
        self.spans = []

    def demarrer_span(self, type_span: str, span_parent_id: str = None) -> str:
        span_id = str(uuid.uuid4())
        self.spans.append({
            "span_id": span_id, "parent_id": span_parent_id, "type": type_span,
            "debut": datetime.utcnow(), "fin": None, "donnees": {},
        })
        return span_id

    def terminer_span(self, span_id: str, donnees: dict) -> None:
        for span in self.spans:
            if span["span_id"] == span_id:
                span["fin"] = datetime.utcnow()
                span["donnees"] = donnees
Arborescence pour une requête utilisant deux outils en parallèle (rappel cours 17, module 6, leçon 6.2, sur les appels en parallèle) : TRACE (une requête utilisateur) │ ├── SPAN : décision du LLM │ └── parent_id: aucun (racine) │ ├── SPAN : appel fonction A (stock produit) │ └── parent_id: décision du LLM │ ├── SPAN : appel fonction B (délai de livraison) │ └── parent_id: décision du LLM │ (A et B partagent le MÊME parent, exécutés en parallèle │ — leurs horodatages peuvent se chevaucher) │ └── SPAN : formulation de la réponse finale └── parent_id: décision du LLM (attend la fin de A ET B avant de commencer)

Cette structure en arbre, plutôt qu'une simple liste chronologique de logs, permet de répondre à des questions de débogage précises : combien de temps chaque outil a-t-il pris individuellement, les appels étaient-ils réellement parallèles ou séquentiels malgré une intention de parallélisme, quel span exact a échoué au sein d'une chaîne complexe.

Piège courant Enregistrer les spans comme une simple liste chronologique plate, sans champ parent_id explicite reliant chaque span à son contexte d'origine — une liste plate rend impossible de distinguer des appels réellement parallèles d'appels séquentiels rapprochés, une distinction pourtant cruciale pour diagnostiquer un problème de performance.

LEÇON 2.2Tracer un appel LLM unique

Cette leçon détaille le contenu minimal d'un span représentant un seul appel à un LLM — le type de span le plus fréquent dans une trace d'agent, et souvent celui qui concentre l'essentiel du coût et de la latence (rappel cours 17, leçon 1.4).

def tracer_appel_llm(trace: Trace, parent_id: str, prompt: str, outils_disponibles: list) -> dict:
    span_id = trace.demarrer_span("appel_llm", parent_id)
    reponse = appeler_llm(prompt, outils=outils_disponibles)
    trace.terminer_span(span_id, {
        "prompt_complet": prompt,                          # rappel leçon 1.3
        "modele": reponse.modele,
        "nombre_tokens_entree": reponse.usage.tokens_entree,
        "nombre_tokens_sortie": reponse.usage.tokens_sortie,
        "cout_estime_usd": calculer_cout(reponse.usage, reponse.modele),
        "outil_choisi": reponse.appel_fonction.name if reponse.appel_fonction else None,
        "arguments_generes": reponse.appel_fonction.arguments if reponse.appel_fonction else None,
        "reponse_texte": reponse.texte if not reponse.appel_fonction else None,
    })
    return reponse
Pourquoi le coût et les tokens comptent autant que la latence : Un agent qui fonctionne correctement mais dont le COÛT par requête augmente progressivement (prompts de plus en plus longs, rappels cours RAG sur le nombre de chunks récupérés) est un problème tout aussi réel qu'une latence dégradée — un problème invisible sans ce champ dans la trace

Le champ prompt_complet mérite une attention particulière : il contient potentiellement le contenu intégral du contexte transmis au modèle, ce qui peut inclure des chunks RAG volumineux (cours 9-13) ou des données utilisateur sensibles — un point qui motive directement le module 4 de ce cours sur l'anonymisation.

Piège courant Logger uniquement la réponse du LLM sans le prompt complet qui lui a été soumis, par souci de réduire le volume de données stockées — un choix qui semble économiser de l'espace mais qui élimine précisément l'information la plus utile pour diagnostiquer pourquoi un modèle a mal interprété une situation.

LEÇON 2.3Tracer une boucle agentique multi-étapes

Rappel du cours 17, module 6, leçon 6.5 : un agent peut itérer plusieurs fois (appeler un outil, observer le résultat, décider d'un nouvel appel) avant de produire une réponse finale. Tracer correctement ce type de boucle est plus délicat qu'un appel unique, car le nombre d'itérations n'est pas connu à l'avance.

def tracer_boucle_agentique(trace: Trace, parent_id: str, question: str,
                              max_iterations: int = 5) -> dict:
    span_boucle_id = trace.demarrer_span("boucle_agentique", parent_id)
    iteration = 0
    contexte = [question]
    while iteration < max_iterations:
        span_iteration_id = trace.demarrer_span(f"iteration_{iteration}", span_boucle_id)
        reponse = tracer_appel_llm(trace, span_iteration_id, "\n".join(contexte), OUTILS)
        trace.terminer_span(span_iteration_id, {"numero_iteration": iteration})
        if not reponse.appel_fonction:
            break  # le LLM a produit une réponse finale, la boucle s'arrête
        contexte.append(executer_et_formater_resultat(reponse.appel_fonction))
        iteration += 1
    trace.terminer_span(span_boucle_id, {"nombre_iterations_total": iteration + 1})
    return reponse
Ce que la trace d'une boucle agentique doit permettre de répondre : "Combien d'itérations cette requête a-t-elle nécessité ?" → Un nombre anormalement élevé peut signaler un agent qui "tourne en rond" (rappel cours 17, module 6, leçon 6.5) "À quelle itération précise la réponse finale a-t-elle émergé ?" → Utile pour évaluer si le nombre max d'itérations configuré est bien calibré (ni trop bas, ni inutilement élevé) "Le contexte accumulé au fil des itérations est-il resté cohérent, ou a-t-il dérivé ?" → Nécessite de pouvoir consulter le prompt complet de CHAQUE itération, pas seulement de la dernière (rappel leçon 2.2)
Piège courant Ne tracer que l'itération finale d'une boucle agentique (celle qui produit la réponse envoyée à l'utilisateur), en perdant les itérations intermédiaires — cela empêche de diagnostiquer pourquoi la boucle a nécessité plusieurs itérations, ou de détecter un agent qui a exploré des chemins inutiles avant de converger vers la bonne réponse.

LEÇON 2.4Corrélation : trace_id, span_id, parent_id

Cette leçon formalise le mécanisme technique qui permet de reconstituer une trace complète à partir de spans potentiellement enregistrés par des composants différents (le service qui reçoit la requête, celui qui appelle le LLM, celui qui exécute les fonctions) — un enjeu qui devient critique dès qu'un agent repose sur une architecture distribuée plutôt qu'un unique processus.

Les trois identifiants de corrélation : TRACE_ID Identifiant unique pour l'ENSEMBLE d'une requête utilisateur, généré une seule fois au tout début et propagé à travers TOUS les composants impliqués dans son traitement SPAN_ID Identifiant unique pour CHAQUE unité de travail au sein de cette trace — généré à chaque nouvelle étape PARENT_ID Référence vers le span_id du span qui a déclenché ce span-ci — permet de reconstruire l'arborescence (rappel leçon 2.1) même si les spans sont enregistrés dans des systèmes de stockage séparés
def propager_contexte_trace(requete_http, trace_id: str, span_parent_id: str) -> dict:
    """Le trace_id et le span_id du span appelant doivent être
    transmis explicitement lors de tout appel entre composants
    (par exemple, via des en-têtes HTTP), pour que le composant
    receveur puisse créer ses propres spans avec le bon parent_id."""
    return {
        "headers": {
            "X-Trace-Id": trace_id,
            "X-Parent-Span-Id": span_parent_id,
        }
    }

Sans cette propagation explicite, chaque composant génère des logs isolés qu'il devient impossible de relier après coup — un problème particulièrement fréquent dans les architectures en microservices, où le composant qui reçoit la question utilisateur, celui qui appelle le LLM, et celui qui exécute les fonctions peuvent être trois services distincts avec des systèmes de logging indépendants.

Piège courant Générer un identifiant de trace différent à chaque composant plutôt que de propager le même trace_id de bout en bout — un oubli fréquent quand les composants ont été développés indépendamment, qui rend impossible la reconstitution d'une trace complète malgré un logging par ailleurs soigné à chaque étape individuelle.
Exercice Pour une architecture où le service qui reçoit les questions utilisateur et celui qui exécute les fonctions sont deux services séparés, à quel moment précis le trace_id doit-il être transmis de l'un à l'autre ?

LEÇON 2.5Le standard OpenTelemetry appliqué aux agents IA

Plutôt que de concevoir un format de trace entièrement propriétaire (comme illustré à des fins pédagogiques dans les leçons précédentes), la pratique de référence en production s'appuie sur OpenTelemetry, un standard ouvert pour la collecte de traces, largement adopté au-delà même du domaine des agents IA.

from opentelemetry import trace

tracer = trace.get_tracer("agent-ia-support-client")

def repondre_avec_otel(question: str) -> str:
    with tracer.start_as_current_span("decision_llm") as span_decision:
        span_decision.set_attribute("prompt", question)
        reponse = appeler_llm(question)
        span_decision.set_attribute("outil_choisi", reponse.outil or "aucun")

        if reponse.appel_fonction:
            with tracer.start_as_current_span("appel_fonction") as span_fonction:
                span_fonction.set_attribute("nom_fonction", reponse.appel_fonction.name)
                resultat = executer_fonction(reponse.appel_fonction)
                span_fonction.set_attribute("succes", resultat.succes)

        return reponse.texte

MODULE 03 / 08

Nettoyage et normalisation des logs bruts

Une fois les traces collectées (module 2), leur contenu brut est rarement directement exploitable. Ce module traite la discipline de nettoyage et de normalisation nécessaire pour transformer des logs bruts, hétérogènes et volumineux en données réellement analysables — en s'appuyant directement sur les techniques de nettoyage de texte déjà couvertes au cours 11.

LEÇON 3.1Pourquoi les logs bruts sont rarement exploitables tels quels

Un système agentique réel combine généralement plusieurs composants (service web, orchestrateur d'agent, fonctions appelées, éventuellement plusieurs fournisseurs de LLM) — chacun avec ses propres conventions de logging, produisant un ensemble hétérogène plutôt qu'un flux uniforme.

Exemple de logs bruts hétérogènes provenant de trois composants différents d'un même agent : Composant A (service web, format texte libre) : "2026-07-21 09:14:02 INFO Request received from user 4471" Composant B (orchestrateur, format JSON) : {"ts": 1753088042, "event": "llm_call", "model": "claude-x", "tokens_in": 1204, "tokens_out": 89} Composant C (fonction appelée, format JSON différent) : {"timestamp": "2026-07-21T09:14:03.500Z", "fn": "obtenir_stock", "status": "ok", "duration_ms": 340} → Trois horodatages dans trois FORMATS différents, trois structures de champs différentes, aucune clé de corrélation commune visible sans traitement (rappel module 2, leçon 2.4)

Sans un travail de normalisation, il est impossible de répondre à des questions simples comme "combien de temps s'est-il écoulé entre la réception de la requête et l'appel de fonction ?" — les données existent, mais dans des formats qui ne permettent pas de les combiner directement. Ce problème rejoint directement celui déjà traité au cours 11 (nettoyage de texte non structuré) et au cours 12 (enrichissement de métadonnées), appliqué ici aux logs plutôt qu'aux documents.

Piège courant Supposer que la simple collecte de logs suffit à en faire une ressource exploitable, sans investir dans une étape de normalisation dédiée — un ensemble de logs volumineux mais hétérogènes n'est pas plus exploitable qu'aucun log, il donne seulement une fausse impression de disposer de données utiles.

LEÇON 3.2Normaliser des formats hétérogènes

Cette leçon détaille une approche standard pour ramener des logs hétérogènes à un schéma commun — un principe similaire à celui de l'enrichissement de métadonnées déjà couvert au cours 12, appliqué ici à des événements de logs plutôt qu'à des chunks documentaires.

from datetime import datetime, timezone

def normaliser_log(log_brut: dict, source_composant: str) -> dict:
    """Ramène un log d'un format hétérogène vers un schéma commun,
    quel que soit le composant d'origine (rappel leçon 3.1)."""
    schema_commun = {
        "horodatage_iso": None,
        "composant_source": source_composant,
        "trace_id": log_brut.get("trace_id") or log_brut.get("traceId"),
        "type_evenement": None,
        "donnees": {},
    }
    if source_composant == "service_web":
        schema_commun["horodatage_iso"] = parser_horodatage_texte(log_brut["timestamp_texte"])
        schema_commun["type_evenement"] = "requete_recue"
    elif source_composant == "orchestrateur":
        schema_commun["horodatage_iso"] = datetime.fromtimestamp(
            log_brut["ts"], tz=timezone.utc).isoformat()
        schema_commun["type_evenement"] = log_brut["event"]
        schema_commun["donnees"] = {"tokens": log_brut.get("tokens_in", 0) + log_brut.get("tokens_out", 0)}

Principe de normalisation en deux temps : 1. IDENTIFIER LA SOURCE Déterminer de quel composant provient chaque log brut, pour appliquer la règle de transformation appropriée 2. TRANSFORMER VERS UN SCHÉMA COMMUN Format d'horodatage unifié (ISO 8601 recommandé), noms de champs cohérents entre composants, structure de données prévisible pour les traitements en aval (modules 5-6)

Le choix d'un format d'horodatage unifié (ISO 8601 dans l'exemple) mérite une attention particulière : rappel de la leçon 3.1, des horodatages dans des formats et fuseaux horaires différents rendent toute corrélation temporelle fragile et sujette à erreur — un piège approfondi à la leçon 3.5.

Piège courant Normaliser les champs de contenu (noms, structure) sans porter la même rigueur aux horodatages, en particulier leur fuseau horaire — un mélange d'horodatages en heure locale et en UTC au sein d'un même système de logs peut fausser silencieusement tous les calculs de latence et de séquencement d'événements.

LEÇON 3.3Extraire des champs structurés depuis un texte de log libre

Certains composants, en particulier des systèmes plus anciens ou des bibliothèques tierces, produisent des logs en texte libre plutôt qu'en JSON structuré. Rappel du cours 16 (NLP de base) : les techniques d'extraction d'entités (NER) et de reconnaissance de motifs s'appliquent directement à ce problème.

import re

def extraire_champs_log_texte(ligne_log: str) -> dict:
    """Applique des expressions régulières pour extraire des champs
    structurés d'un log en texte libre — une version simplifiée des
    techniques d'extraction d'entités du cours 16, appliquée à un
    format suffisamment régulier pour ne pas nécessiter un modèle NER
    complet."""
    motif = re.compile(
        r"(?P\d{4}-\d{2}-\d{2} \d{2}:\d{2}:\d{2}) "
        r"(?P\w+) (?P.+)"
    )
    correspondance = motif.match(ligne_log)
    if not correspondance:
        return {"erreur_parsing": True, "ligne_brute": ligne_log}
    champs = correspondance.groupdict()
    utilisateur_trouve = re.search(r"user (\d+)", champs["message"])
    if utilisateur_trouve:
        champs["utilisateur_id"] = utilisateur_trouve.group(1)
    return champs

Le champ erreur_parsing dans l'exemple ci-dessus est délibéré : plutôt que de faire échouer silencieusement l'extraction ou de lever une exception qui interromprait tout le traitement, marquer explicitement les lignes qui n'ont pas pu être parsées permet de les traiter séparément — et souvent de découvrir un nouveau format de log apparu après une mise à jour d'un composant, un signal précieux en soi.

Piège courant Écrire des expressions régulières trop rigides qui échouent silencieusement (sans marquage explicite de l'échec) dès qu'un composant modifie légèrement son format de log — sans un champ comme erreur_parsing, ces échecs passent inaperçus et une portion croissante des logs devient silencieusement non exploitée.

LEÇON 3.4Gérer le volume : échantillonnage et rétention

Un agent IA en production, surtout à volume élevé, peut générer un nombre de logs considérable — en particulier si les recommandations du module 1 (capturer le prompt complet, les décisions intermédiaires) sont suivies scrupuleusement. Cette leçon traite comment gérer ce volume sans perdre l'information la plus précieuse.

Stratégies de gestion du volume, du plus simple au plus sophistiqué : 1. RÉTENTION À DURÉE LIMITÉE Conserver les traces complètes pendant une période limitée (jours à semaines), puis les archiver ou les supprimer — similaire au principe de péremption déjà vu au cours 18 2. ÉCHANTILLONNAGE UNIFORME Ne conserver en détail qu'un pourcentage des traces (par exemple 10%), suffisant pour une analyse statistique (module 6) sans stocker l'intégralité du volume 3. ÉCHANTILLONNAGE CIBLÉ SUR LES CAS INTÉRESSANTS Toujours conserver les traces qui contiennent une ERREUR, une VALIDATION ÉCHOUÉE (rappel cours 17, module 4), ou une LATENCE ANORMALEMENT ÉLEVÉE — même si l'échantillonnage général est réduit pour les cas nominaux
import random

def decider_retention_trace(trace: dict, taux_echantillonnage: float = 0.1) -> bool:
    """Combine échantillonnage uniforme (stratégie 2) et ciblage
    des cas intéressants (stratégie 3) — l'approche la plus
    équilibrée en pratique."""
    a_une_erreur = any(span.get("erreur") for span in trace["spans"])

    return random.random() < taux_echantillonnage

Cette approche combinée résout une tension centrale : conserver 100% des traces devient rapidement coûteux et difficile à exploiter (rappel du piège du "sur-logger sans structure", leçon 1.5), tandis qu'un échantillonnage purement uniforme risque de manquer précisément les cas les plus utiles au débogage — les erreurs et anomalies, qui sont par nature statistiquement rares.

Piège courant Appliquer un échantillonnage purement uniforme sans jamais garantir la conservation des cas anormaux (erreurs, latence élevée, validation échouée) — cette pratique peut faire disparaître, par pur hasard statistique, les traces les plus utiles pour diagnostiquer les problèmes réels du système.

LEÇON 3.5Pièges courants de nettoyage

Cette dernière leçon du module recense des pièges spécifiques au nettoyage de logs, en complément des principes généraux déjà vus.

Piège 1 : troncature silencieuse des champs longs

De nombreux systèmes de stockage de logs tronquent automatiquement les champs dépassant une certaine longueur — un prompt complet volumineux (rappel module 1, leçon 1.3) peut ainsi être coupé sans avertissement, rendant le débogage a posteriori incomplet sans que rien ne le signale.

Piège 2 : problèmes d'encodage de caractères

Des logs contenant des caractères spéciaux ou multilingues (rappel cours 11, sur le nettoyage de texte extrait) peuvent être corrompus si l'encodage n'est pas géré uniformément à travers la chaîne de traitement — un problème qui peut rendre certains logs illisibles ou fausser une recherche textuelle ultérieure.

Piège 3 : incohérence de fuseaux horaires malgré la normalisation

Rappel de la leçon 3.2 : même après normalisation au format ISO 8601, une erreur de conversion de fuseau horaire à la source (un composant qui envoie une heure locale sans indiquer son décalage) peut introduire des incohérences silencieuses dans le séquencement des événements.

Piège 4 : perte de la relation trace_id/span_id lors du nettoyage

Un traitement de nettoyage trop agressif (déduplication, filtrage) peut par erreur retirer ou modifier les champs de corrélation (rappel module 2, leçon 2.4), rendant les traces orphelines ou incomplètes une fois "nettoyées".

Ce module clôt la partie "nettoyage" du cours. Le module suivant aborde un sujet qui recoupe directement le nettoyage mais avec un objectif différent : protéger les données personnelles qui peuvent apparaître dans le contenu des logs, plutôt que d'en assurer la seule exploitabilité technique.
Piège courant Considérer le nettoyage des logs comme terminé une fois le pipeline de normalisation mis en place, sans processus de vérification continue (échantillons audités périodiquement) pour détecter ces pièges silencieux (troncature, encodage, fuseaux horaires) qui peuvent apparaître ou s'aggraver avec le temps, notamment après une mise à jour d'un composant source.

Anonymisation et gestion des données sensibles

Rappel de la leçon 1.5 (erreur 3) : les logs d'un agent conversationnel contiennent souvent, par nature, des informations personnelles. Ce module traite comment les détecter et les protéger sans sacrifier la valeur diagnostique établie aux modules précédents.

LEÇON 4.1Pourquoi les logs d'agents contiennent souvent des données sensibles

Contrairement à un système logiciel classique où les données personnelles transitent généralement par des champs identifiés (un formulaire avec un champ "email"), un agent conversationnel reçoit des données personnelles de façon non structurée, noyées dans le texte libre des questions utilisateur — rendant leur présence moins évidente à détecter.

Exemple de données personnelles noyées dans un prompt libre : "Bonjour, je m'appelle Marie Dubois, mon email est marie.dubois@exemple.fr, pouvez-vous vérifier le statut de ma commande CMD-789012 ? Mon numéro de téléphone est le 06 12 34 56 78 si vous avez besoin de me rappeler." → Ce SEUL message, s'il est loggé intégralement (rappel module 1, leçon 1.3, sur l'importance de capturer le prompt complet), contient : un nom complet, un email, un numéro de téléphone, et un identifiant de commande reliant potentiellement le tout à un compte client précis

Cette tension est directe avec les principes du module 1 : capturer le prompt exact (leçon 1.3) est précieux pour le débogage, mais ce même prompt peut contenir des informations qu'il ne faudrait pas conserver telles quelles indéfiniment, ni exposer à quiconque a accès aux logs. Ce module ne remet pas en cause la nécessité de capturer ce contenu, mais impose de le protéger correctement.

Piège courant Considérer que le risque de données personnelles ne concerne que des champs explicitement nommés (comme "email" ou "téléphone" dans une base de données classique), en sous-estimant leur présence fréquente et non structurée dans le texte libre échangé avec un agent conversationnel.

LEÇON 4.2Détecter les PII dans les prompts et réponses

Rappel direct du cours 16 (NLP de base, module 5, Named Entity Recognition) : la détection d'informations personnelles identifiables (PII — Personally Identifiable Information) s'appuie sur les mêmes techniques d'extraction d'entités déjà couvertes, appliquées ici spécifiquement à la détection de contenu sensible plutôt qu'à l'enrichissement de métadonnées.

import re

PATTERNS_PII = {
    "email": re.compile(r"[\w.+-]+@[\w-]+\.[a-z]{2,}"),
    "telephone_fr": re.compile(r"0[1-9](?:[\s.-]?\d{2}){4}"),
    "numero_carte": re.compile(r"\b(?:\d{4}[\s-]?){3}\d{4}\b"),
}

def detecter_pii(texte: str) -> dict:
    """Combine des expressions régulières pour les motifs très
    réguliers (email, téléphone) avec un modèle NER (rappel
    cours 16) pour les entités moins structurées comme les
    noms propres, plus difficiles à capturer par des règles."""
    detections = {}
    for type_pii, motif in PATTERNS_PII.items():
        correspondances = motif.findall(texte)
        if correspondances:
            detections[type_pii] = correspondances
    entites_nommees = modele_ner(texte)  # rappel cours 16, module 5
    noms_detectes = [e.texte for e in entites_nommees if e.type == "PERSONNE"]
    if noms_detectes:
        detections["noms_propres"] = noms_detectes
    return detections
Répartition des techniques de détection selon le type de PII : Motif RÉGULIER (email, téléphone, Motif IRRÉGULIER (noms propres, numéro de carte, IBAN...) adresses complètes...) ──────────────────────────────── ──────────────────────────────── Expressions régulières suffisent Nécessite un modèle NER généralement — même principe que (rappel cours 16) capable de la leçon 3.3 sur l'extraction de reconnaître un nom dans son champs de logs contexte, sans motif fixe

Cette détection doit s'appliquer aussi bien aux prompts (ce que l'utilisateur écrit) qu'aux réponses générées par le LLM — un modèle peut, par exemple, répéter dans sa réponse une information personnelle fournie plus tôt dans la conversation, ce qui multiplie les occurrences à protéger dans une même trace.

Piège courant Détecter les PII uniquement dans les messages de l'utilisateur en supposant que les réponses générées par le LLM n'en contiennent jamais — un modèle qui répète ou reformule une information personnelle fournie par l'utilisateur (par exemple, en confirmant "je vérifie donc pour Marie Dubois...") introduit cette même donnée sensible dans un contenu que la détection ne couvrirait pas si elle ne cible que l'entrée utilisateur.

LEÇON 4.3Techniques de masquage et de rédaction

Une fois les PII détectées (leçon 4.2), plusieurs techniques permettent de les protéger dans les logs, chacune avec un compromis différent entre protection et utilité diagnostique conservée.

TechniquePrincipeUtilité diagnostique conservée
Suppression totaleRetirer entièrement la donnée sensible du logFaible — perd même l'indice qu'une PII était présente à cet endroit
Masquage (redaction)Remplacer par un jeton générique, ex : [EMAIL]Moyenne — préserve la structure et le contexte de la phrase sans exposer la valeur
HachageRemplacer par une empreinte non réversibleÉlevée — permet de vérifier que deux logs concernent le même utilisateur sans révéler qui il est

import hashlib

def masquer_pii(texte: str, detections: dict) -> str:
    for type_pii, valeurs in detections.items():
        for valeur in valeurs:
            if type_pii == "email":
                texte = texte.replace(valeur, "[EMAIL]")  # masquage simple
            elif type_pii == "noms_propres":
                empreinte = hashlib.sha256(valeur.encode()).hexdigest()[:8]
                texte = texte.replace(valeur, f"[PERSONNE_{empreinte}]")  # hachage
    return texte

# "je m'appelle Marie Dubois, mon email est marie.dubois@exemple.fr"
#   → "je m'appelle [PERSONNE_a3f9c21b], mon email est [EMAIL]"

La tokenisation réversible avec hachage (comme illustré pour les noms propres ci-dessus) offre un compromis particulièrement utile pour le débogage : elle permet de repérer que deux traces différentes concernent le même utilisateur (même empreinte de hachage) — précieux pour identifier des problèmes récurrents pour une personne donnée — sans jamais exposer son identité réelle dans les logs eux-mêmes.

Piège courant Choisir systématiquement la suppression totale par excès de prudence, en perdant ainsi la capacité de repérer des patterns liés à un même utilisateur à travers plusieurs traces — un compromis souvent plus protecteur qu'utile, alors que le hachage (leçon suivante) offre une protection équivalente tout en conservant cette capacité de corrélation.

LEÇON 4.4Conformité et durée de rétention

Au-delà des techniques de masquage, la gestion des logs contenant des données personnelles est encadrée par des exigences réglementaires (comme le RGPD en Europe) qui imposent des principes précis sur leur conservation.

Principes réglementaires clés applicables aux logs d'agents IA : MINIMISATION DES DONNÉES Ne collecter et conserver que ce qui est réellement nécessaire au débogage et à l'amélioration — rappel du piège "sur-logger" (leçon 1.5), qui rejoint ici une obligation réglementaire et pas seulement une bonne pratique LIMITATION DE LA DURÉE DE CONSERVATION Les logs contenant des PII ne devraient pas être conservés indéfiniment — une durée de rétention définie et justifiée (rappel module 3, leçon 3.4, sur la rétention à durée limitée) devient ici une exigence de conformité DROIT À L'EFFACEMENT Un utilisateur peut demander la suppression de ses données personnelles — un système de logs doit permettre de retrouver et supprimer les entrées le concernant, ce qui suppose une capacité de recherche par identifiant utilisateur (rappel des champs de corrélation, module 2, leçon 2.4)

Le principe de minimisation rejoint directement une tension déjà identifiée au module 1 : capturer davantage de contenu améliore la capacité de débogage (leçon 1.2), mais chaque donnée supplémentaire capturée, si elle est personnelle, doit être justifiée par ce même besoin de débogage — une conservation "par défaut, au cas où" de données personnelles non nécessaires n'est ni une bonne pratique ni, dans de nombreuses juridictions, conforme aux exigences réglementaires.

Piège courant Conserver indéfiniment l'intégralité des logs contenant des données personnelles "au cas où ils seraient utiles un jour", sans politique de rétention définie ni processus de suppression — une pratique qui expose à un risque de conformité croissant avec le temps, sans bénéfice diagnostique proportionné au-delà d'une fenêtre de quelques semaines à quelques mois dans la plupart des cas.

Structurer les logs pour le débogage

Ce module revient sur l'objectif initial de ce cours en s'appuyant sur des traces désormais bien structurées (module 2), nettoyées (module 3) et protégées (module 4) : comment les organiser et les consulter pour réellement diagnostiquer un problème d'agent en production.

LEÇON 5.1Ce qui rend un log réellement débogable

Un log techniquement bien structuré (module 2-3) n'est pas automatiquement un log débogable — la différence tient à la présence d'un contexte suffisant pour comprendre non seulement CE qui s'est passé, mais POURQUOI, sans avoir à deviner ou à reproduire le problème.

Log techniquement correct mais peu débogable : {"trace_id": "abc123", "type": "erreur_validation", "horodatage": "2026-07-21T09:14:03Z"} → Confirme QU'une erreur de validation s'est produite, mais ne dit RIEN sur la fonction concernée, les arguments générés, ni la raison du rejet — un débogage nécessiterait de retrouver séparément les autres spans de cette même trace (rappel module 2, leçon 2.1) pour reconstituer le contexte Log structuré pour le débogage : {"trace_id": "abc123", "type": "erreur_validation", "horodatage": "2026-07-21T09:14:03Z", "fonction": "obtenir_statut_commande", "arguments_recus": {"numero_commande": "CMD-78901X"}, "regle_violee": "pattern ^CMD-\\d{6}$ non respecté", "prompt_utilisateur_associe": "où en est ma commande CMD-78901X ?"} → Permet de comprendre IMMÉDIATEMENT que l'utilisateur a fourni un numéro de commande mal formé (probablement une faute de frappe), sans reconstruction ni investigation supplémentaire

Le principe général : un log débogable anticipe les questions qu'une personne se poserait en l'examinant, et y répond directement dans sa structure plutôt que de forcer une reconstruction manuelle à partir de fragments épars — un principe qui rejoint directement l'esprit du module 1 (capturer le raisonnement, pas seulement le résultat).

Piège courant Considérer qu'un log est suffisant dès lors qu'il est techniquement bien formé et structuré (rappel modules 2-3), sans vérifier explicitement qu'il contient assez de contexte pour être compris isolément, sans nécessiter de reconstituer manuellement l'ensemble de la trace à chaque investigation.

LEÇON 5.2Logger les décisions intermédiaires de l'agent

Rappel du cours 18 (module 4, leçon 4.2) : un agent hybride décide, à chaque requête, quelle source consulter (RAG statique ou function calling temps réel). Cette décision elle-même — pas seulement son résultat — mérite d'être loggée explicitement, car elle constitue souvent la clé pour comprendre un comportement inattendu.

def logger_decision_routage(trace: Trace, parent_id: str, question: str,
                              outils_proposes: list, outil_choisi: str) -> None:

Piège courant Logger uniquement l'outil finalement choisi par le modèle sans conserver la liste des outils qui lui étaient proposés à ce moment précis — sans cette information, il devient impossible de distinguer un choix évident (un seul outil pertinent) d'un choix ambigu (plusieurs outils plausibles), une distinction pourtant essentielle pour améliorer les descriptions de schéma (rappel cours 17, module 3).

LEÇON 5.3Reconstituer une session complète à partir des logs

Une seule requête utilisateur (une trace, rappel module 2) constitue rarement toute l'histoire : la plupart des interactions avec un agent conversationnel s'étalent sur plusieurs échanges successifs au sein d'une même session. Cette leçon traite comment relier plusieurs traces entre elles pour reconstituer le fil complet d'une conversation.

def rassembler_session(session_id: str, magasin_traces) -> list[dict]:
    """Une session regroupe PLUSIEURS traces (une par message
    utilisateur), reliées par un identifiant de session commun
    — distinct du trace_id qui identifie une seule requête
    (rappel module 2, leçon 2.4)."""
    traces_de_la_session = magasin_traces.rechercher(session_id=session_id)
    return sorted(traces_de_la_session, key=lambda t: t["horodatage_debut"])
Hiérarchie complète de corrélation dans ce cours : SESSION_ID Regroupe toutes les traces d'une même conversation │ ├── TRACE_ID (message utilisateur n°1) │ └── spans (décision, appel de fonction, réponse...) │ ├── TRACE_ID (message utilisateur n°2) │ └── spans (...) │ └── TRACE_ID (message utilisateur n°3) └── spans (...) → Reconstituer la SESSION complète permet de répondre à des questions qu'une trace isolée ne peut pas éclairer : "l'agent a-t-il bien tenu compte du contexte des messages précédents ?" "la conversation a-t-elle dérivé progressivement vers une réponse incorrecte au fil des échanges ?"

Cette reconstitution de session est particulièrement précieuse pour diagnostiquer des problèmes qui n'apparaissent qu'après plusieurs échanges — un agent qui, par exemple, "oublie" progressivement une contrainte mentionnée au début de la conversation, un problème invisible si l'analyse se limite à une seule trace isolée.

Piège courant Analyser systématiquement les traces de façon isolée, une par une, sans jamais les regrouper par session — cette pratique manque les problèmes qui n'émergent qu'au fil d'une conversation multi-tours, un mode d'échec fréquent pour les agents conversationnels mais invisible à l'échelle d'une seule requête.

MODULE 06 / 08

Extraire des métriques et signaux d'amélioration

Au-delà du débogage ponctuel d'incidents individuels (module 5), les logs collectés constituent une ressource précieuse pour identifier des tendances et orienter l'amélioration continue du système. Ce module traite comment transformer un volume de traces en métriques exploitables.

LEÇON 6.1Des logs bruts aux métriques agrégées

Une trace individuelle répond à la question "que s'est-il passé pour CETTE requête ?" ; une métrique agrégée répond à "comment le système se comporte-t-il globalement ?" — deux perspectives complémentaires, la seconde nécessitant un traitement d'agrégation sur l'ensemble des traces collectées.

from collections import defaultdict

def calculer_metriques_periode(traces: list[dict]) -> dict:
    """Transforme un ensemble de traces individuelles en
    métriques agrégées — rappel du principe de fenêtrage déjà
    couvert au cours 18, module 6, leçon 6.4, appliqué ici aux
    traces d'agent plutôt qu'aux événements métier."""
    total = len(traces)
    erreurs = sum(1 for t in traces if t.get("a_une_erreur"))
    latences = [t["latence_totale_ms"] for t in traces]
    outils_utilises = defaultdict(int)
    for t in traces:
        for span in t["spans"]:
            if span["type"] == "appel_fonction":
                outils_utilises[span["donnees"]["nom_fonction"]] += 1
    return {
        "nombre_requetes": total,
        "taux_erreur": erreurs / total if total else 0,
        "latence_p50_ms": percentile(latences, 50),
        "latence_p95_ms": percentile(latences, 95),
        "repartition_outils": dict(outils_utilises),
    }
Pourquoi les percentiles (p50, p95) plutôt qu'une simple moyenne : Moyenne SEULE Percentiles (p50, p95) ──────────────────────── ──────────────────────── Peut masquer une minorité de Le p50 (médiane) montre requêtes très lentes derrière l'expérience TYPIQUE une majorité rapide Le p95 montre l'expérience des 5% de requêtes les Une moyenne de 500ms peut PLUS LENTES — souvent celles cacher un mélange de requêtes qui génèrent le plus de à 100ms et d'autres à 3000ms plaintes utilisateur

Cette distinction entre moyenne et percentiles rejoint un principe déjà présent implicitement au cours 18 (leçon 3.4, sur la latence) : les cas les plus lents ne sont pas de simples anomalies statistiques à ignorer, ils représentent souvent l'expérience réelle d'une portion significative des utilisateurs, et méritent d'être surveillés spécifiquement plutôt que noyés dans une moyenne globale rassurante.

Piège courant Ne surveiller que la latence moyenne d'un système, sans jamais examiner les percentiles élevés (p95, p99) — un système avec une moyenne excellente peut malgré tout offrir une expérience très dégradée à une portion non négligeable de ses utilisateurs, un problème invisible sans cette décomposition.

Une métrique nécessaire mais rappel de la leçon 1.2 : insuffisante seule, car elle ne capture pas la QUALITÉ de la réponse, seulement son achèvement technique Taux d'ERREUR DE VALIDATION Rappel direct du cours 17, module 4 : quelle proportion des appels de fonction générés par le LLM échouent la validation structurelle ? def calculer_taux_erreur_validation_par_fonction(traces: list[dict]) -> dict:
    """Décomposer le taux d'erreur PAR FONCTION, plutôt que
    globalement, permet d'identifier précisément QUEL schéma
    (rappel cours 17, module 3) nécessite une révision."""
    tentatives_par_fonction = defaultdict(lambda: {"total": 0, "erreurs": 0})
    for trace in traces:
        for span in trace["spans"]:
            if span["type"] == "validation":
                nom = span["donnees"]["nom_fonction"]
                tentatives_par_fonction[nom]["total"] += 1
                if not span["donnees"]["valide"]:
                    tentatives_par_fonction[nom]["erreurs"] += 1
    return {nom: v["erreurs"] / v["total"] for nom, v in tentatives_par_fonction.items() if v["total"]}

Décomposer une métrique par composant spécifique (ici, par fonction) plutôt que de la calculer uniquement de façon globale est un principe qui reviendra à la leçon 6.4 : une moyenne agrégée sur l'ensemble du système masque souvent un problème localisé à un seul composant, qu'une décomposition plus fine révèle immédiatement.

Piège courant Calculer un taux d'erreur de validation global pour l'ensemble du système sans le décomposer par fonction individuelle — un taux global de 2% peut sembler acceptable, alors qu'il pourrait en réalité cacher une fonction spécifique avec un taux d'échec de 40%, noyée statistiquement parmi d'autres fonctions qui fonctionnent parfaitement.

LEÇON 6.3Détecter les patterns d'échec récurrents

def regrouper_erreurs_par_similarite(traces_en_erreur: list[dict], seuil: float = 0.85) -> list[list]:
    """Rappel cours 18, module 5, leçon 5.3 (cache sémantique) —
    la même technique d'embeddings s'applique ici pour regrouper
    des questions utilisateur différentes en formulation mais
    similaires dans leur intention, qui ont toutes échoué."""
    groupes = []
    for trace in traces_en_erreur:
        embedding = calculer_embedding(trace["question_utilisateur"])
        groupe_trouve = False
        for groupe in groupes:
            if similarite_cosinus(embedding, groupe["embedding_moyen"]) >= seuil:
                groupe["traces"].append(trace)
                groupe_trouve = True
                break
        if not groupe_trouve:
            groupes.append({"embedding_moyen": embedding, "traces": [trace]})
    return sorted(groupes, key=lambda g: len(g["traces"]), reverse=True)
Pourquoi regrouper plutôt qu'examiner chaque échec isolément : 10 échecs isolés et non regroupés 10 échecs regroupés en 1 pattern ──────────────────────────────── ──────────────────────────────── Chacun semble être un incident Révèle qu'un SEUL problème ponctuel et distinct sous-jacent (par exemple, une formulation ambiguë d'un Investigation dispersée, effort schéma) explique 10 échecs répété pour des cas qui apparemment différents partagent en réalité la même cause racine Une SEULE correction (rappel cours 17, module 3) résout potentiellement l'ensemble du groupe

Cette approche de regroupement change fondamentalement la priorisation du travail de débogage : plutôt que de traiter les échecs dans l'ordre chronologique de leur apparition, elle permet de s'attaquer en priorité aux patterns qui regroupent le plus grand nombre d'occurrences — le principe classique consistant à traiter d'abord les problèmes ayant le plus d'impact cumulé.

Piège courant Traiter chaque trace en erreur individuellement, dans l'ordre où elle est rencontrée, sans jamais chercher à regrouper les échecs similaires — cette approche disperse l'effort de débogage et peut faire manquer un pattern systémique qui, une fois identifié, se résoudrait par une seule correction plutôt que par de nombreux ajustements ponctuels.

LEÇON 6.5La boucle de feedback vers l'amélioration continue

Cette dernière leçon du module formalise l'ensemble du cycle décrit dans ce module en une boucle continue, qui referme la logique de ce cours sur elle-même : les logs alimentent les métriques, qui orientent les corrections, qui elles-mêmes génèrent de nouveaux logs à analyser.

LEÇON 7.3Traitement en continu vs en batch

Rappel direct du cours 18 (module 6) : le nettoyage, le masquage et l'agrégation des logs peuvent s'exécuter selon deux modes différents, avec les mêmes compromis déjà établis pour les pipelines de données temps réel.

Traitement EN CONTINU (streaming) Traitement EN BATCH (rappel cours 18, module 6) (traitement périodique) ──────────────────────────────── ──────────────────────────── Chaque trace est nettoyée, masquée Les traces s'accumulent, puis et indexée au fil de l'eau, dès sont traitées ensemble à sa réception intervalle régulier (toutes les heures, chaque nuit) Métriques quasi temps réel — utile pour l'ALERTING (leçon 7.4) Traitement souvent plus efficace en volume (moins Infrastructure plus complexe de surcharge par trace (similaire aux pipelines de traitée individuellement) streaming du cours 18) Délai avant que les métriques (module 6) soient à jour

Le choix entre ces deux modes suit le même principe déjà établi à plusieurs reprises dans cette série : le traitement en continu se justifie quand une réaction rapide est nécessaire (détecter un pic de taux d'erreur pour déclencher une alerte, leçon 7.4), tandis que le traitement en batch suffit largement pour des analyses moins urgentes (rapports hebdomadaires de tendances, module 6).

LEÇON 7.4Alerting basé sur les logs

Cette leçon relie le pipeline de traitement à une action proactive : plutôt que d'attendre qu'une personne consulte manuellement les métriques (module 6), un système d'alerting notifie automatiquement une équipe dès qu'un seuil anormal est détecté.

def verifier_seuils_alerte(metriques_recentes: dict, metriques_seuils: dict) -> list[str]:
    alertes = []
    if metriques_recentes["taux_erreur"] > metriques_seuils["taux_erreur_max"]:
        alertes.append(f"Taux d'erreur anormalement élevé : "
                        f"{metriques_recentes['taux_erreur']:.1%}")
    if metriques_recentes["latence_p95_ms"] > metriques_seuils["latence_p95_max_ms"]:
        alertes.append(f"Latence p95 dégradée : {metriques_recentes['latence_p95_ms']}ms")
    for nom_fonction, taux in metriques_recentes.get("taux_erreur_validation_par_fonction", {}).items():
        if taux > metriques_seuils["taux_erreur_validation_max"]:
            alertes.append(f"Fonction '{nom_fonction}' : taux d'erreur de validation "
                            f"élevé ({taux:.1%}) — rappel cours 17, module 3")
    return alertes
Principes pour un alerting efficace, évitant la "fatigue d'alerte" : SEUILS CALIBRÉS SUR UNE BASELINE RÉELLE Un seuil arbitraire ("alerter si le taux d'erreur dépasse 5%") sans référence à un comportement normal observé génère souvent trop de faux positifs ou, à l'inverse, manque de vraies anomalies ALERTES ACTIONNABLES Chaque alerte devrait pointer vers une action possible (rappel module 6, leçon 6.4) plutôt que se contenter de signaler un chiffre sans contexte DIFFÉRENCIATION DE SÉVÉRITÉ Toutes les anomalies ne méritent pas un réveil en pleine nuit — une dégradation mineure de latence n'a pas la même urgence qu'un système d'agent totalement défaillant
Piège courant Configurer des seuils d'alerte arbitraires, non calibrés sur le comportement normal réel du système, ce qui génère soit une fatigue d'alerte (trop de fausses alertes ignorées à force d'habitude), soit un silence dangereux face à de vraies anomalies (seuils trop larges pour être jamais déclenchés).
Exercice Pour l'alerte de taux d'erreur de validation par fonction (rappel cours 17, module 3), à quelle équipe ou personne cette alerte devrait-elle être adressée en priorité, et quelle action concrète attendriez-vous en réponse ?

LEÇON 7.5Sécuriser l'accès aux logs

Cette dernière leçon du module referme une boucle de sécurité déjà entamée au cours 17 (module 7, sur la sécurité du function calling) : les logs eux-mêmes, une fois collectés et stockés, deviennent une ressource sensible à protéger, en particulier ceux qui contiennent des données personnelles malgré le masquage du module 4.

Pourquoi les logs constituent une surface de risque à part entière : Même APRÈS masquage des PII (module 4), les logs peuvent contenir des informations sensibles sur le fonctionnement interne du système : la structure exacte des prompts système, les schémas complets des fonctions internes (rappel cours 17), des détails d'architecture qui ne devraient pas être exposés à quiconque n'en a pas l'usage légitime

Rappel direct du principe de moindre privilège déjà établi au cours 17 (module 7, leçon 7.3) : l'accès aux logs devrait suivre la même discipline que l'accès aux outils d'un agent — accès en lecture accordé selon un besoin réel, pas ouvert par défaut à l'ensemble d'une équipe technique.

LEÇON 8.3Étude de cas : déboguer un agent à partir de ses logs

Contexte

L'agent de support client développé au fil des cours 17 et 18 reçoit des plaintes utilisateur : certains clients rapportent que l'agent leur donne parfois une information de stock incorrecte pour certains produits. L'équipe dispose du système de logging complet décrit dans ce cours et doit diagnostiquer la cause.

Démarche de diagnostic, mobilisant les modules de ce cours : 1. RECHERCHER les traces concernant les produits mentionnés dans les plaintes (module 5, leçon 5.4 — recherche et filtrage) 2. EXAMINER le contenu détaillé de ces traces (module 1, leçon 1.3) : → Le prompt reçu contenait-il bien le bon identifiant produit ? → L'outil "obtenir_stock_produit" a-t-il été appelé, ou l'agent a-t-il répondu depuis une source statique par erreur (rappel cours 18, module 4, sur le routage) ? → Si l'outil a été appelé, la réponse provenait-elle du cache (rappel cours 18, module 5) ou d'un appel direct ? Quel était l'âge de la donnée servie (rappel module 5, leçon 5.4) ? 3. REGROUPER les traces similaires (module 6, leçon 6.3) pour vérifier si le problème concerne UN produit spécifique ou un pattern plus large (par exemple, tous les produits d'une même catégorie, ou toutes les requêtes passées par le cache) 4. Une fois la cause identifiée (hypothèse : un TTL de cache trop long pour des produits à forte rotation de stock, rappel cours 18, module 5, leçon 5.1), appliquer la CORRECTION et VÉRIFIER via de nouvelles métriques (module 6, leçon 6.5) que le taux de plaintes diminue effectivement

Cette étude de cas illustre concrètement pourquoi ce cours a insisté, à travers tous ses modules, sur la nécessité de capturer un contexte riche (prompt complet, source utilisée, fraîcheur de la donnée, cache ou appel direct) : sans ces informations, l'équipe n'aurait pu que constater le symptôme (une plainte utilisateur) sans jamais remonter à sa cause précise, une confusion entre péremption de cache et disponibilité réelle du stock déjà anticipée au cours 18 (module 5, leçon 5.5).

Piège courant Face à une plainte utilisateur vague ("l'agent m'a donné une mauvaise information"), tenter de reproduire manuellement le problème plutôt que de d'abord consulter les traces réelles de l'incident signalé — la reproduction manuelle risque de manquer les conditions exactes (timing, état du cache) qui ont mené à l'erreur initiale, alors que la trace originale les contient déjà.
