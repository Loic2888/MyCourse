Formatage de Datasets d'Entraînement

Format instruction/réponse et JSONL — comment transformer des données brutes en un dataset structuré, propre et exploitable pour le fine-tuning d'un modèle de langage. 8 modules, 40 leçons.

MODULE 01 / 08

Fondamentaux du fine-tuning et du formatage de données

Ce cours ouvre un nouveau bloc de la série, consacré à la préparation de données pour le fine-tuning — l'entraînement complémentaire d'un modèle de langage sur un jeu de données spécifique. Contrairement aux blocs précédents (RAG, agents IA), où la donnée est consultée au moment de l'inférence, ici la donnée devient une partie du modèle lui-même : sa qualité et son format déterminent directement le comportement final.

LEÇON 1.1Qu'est-ce que le fine-tuning et pourquoi le format des données est critique

Le fine-tuning consiste à poursuivre l'entraînement d'un modèle de langage déjà pré-entraîné, sur un jeu de données plus restreint et spécifique, pour adapter son comportement — un ton particulier, un domaine spécialisé, un format de réponse précis, ou une capacité que le modèle de base ne maîtrise pas suffisamment bien.

Contrairement au RAG (cours 9-13) ou au function calling (cours 17), où l'information reste externe au modèle et est injectée au moment de la question, le fine-tuning modifie les poids internes du modèle lui-même. Cette différence de nature a une conséquence directe sur ce cours : alors qu'un chunk RAG mal formaté produit une mauvaise réponse ponctuelle, un exemple d'entraînement mal formaté influence durablement le comportement du modèle sur l'ensemble de ses réponses futures.

Cette différence de coût de correction justifie l'exigence de rigueur de ce cours : une erreur de formatage détectée après l'entraînement ne se corrige pas par un simple ajustement, mais nécessite de reprendre le dataset et de relancer un cycle d'entraînement complet — un argument fort en faveur d'une validation systématique du format avant l'entraînement plutôt qu'après.

Piège courant Considérer la préparation d'un dataset de fine-tuning comme une tâche similaire à la préparation de données pour du RAG (cours 9-13), avec un niveau d'exigence comparable — alors que le coût d'une erreur de format est structurellement plus élevé pour le fine-tuning, puisqu'elle se propage dans le modèle lui-même plutôt que de rester isolée à une consultation ponctuelle.
Exercice Pour un projet de fine-tuning que vous imaginez (un assistant spécialisé dans un domaine précis, par exemple), décrivez ce qui se passerait concrètement si 10% des exemples de votre dataset contenaient une erreur de formatage systématique, non détectée avant l'entraînement.

LEÇON 1.2Fine-tuning vs prompting, RAG, function calling : quand fine-tuner

Cette leçon situe le fine-tuning parmi les techniques déjà couvertes dans cette série, pour clarifier quand cette approche, plus coûteuse à mettre en œuvre, se justifie réellement par rapport aux alternatives.

TechniqueModifieSe justifie quand
Prompting / ingénierie de promptRien dans le modèle, seulement l'entréeLe comportement souhaité peut être obtenu par des instructions claires dans le prompt
RAG (cours 9-13)Rien dans le modèle, ajoute du contexte externeLe modèle a besoin d'accéder à des connaissances spécifiques et évolutives
Function calling (cours 17)Rien dans le modèle, ajoute une capacité d'actionLe modèle doit déclencher des actions ou récupérer des données externes précises
Fine-tuning (ce cours)Les poids internes du modèleLe comportement souhaité (ton, format, capacité spécialisée) résiste aux approches ci-dessus, ou doit être fiable sans dépendre d'un prompt répété à chaque requête

En pratique, le fine-tuning n'est presque jamais une alternative exclusive aux techniques précédentes : un agent réel combine fréquemment un modèle fine-tuné (pour un ton ou un format spécifique) avec du RAG (pour des connaissances à jour, cours 9-13) et du function calling (pour des actions, cours 17) — les blocs de cette série ne s'excluent pas mutuellement, ils s'assemblent selon le besoin.

Piège courant Se tourner vers le fine-tuning comme première solution face à un comportement de modèle insatisfaisant, sans avoir d'abord épuisé les possibilités du prompting ou du RAG — des techniques nettement moins coûteuses à itérer, et qui suffisent à résoudre la majorité des problèmes de comportement de modèle rencontrés en pratique.
Exercice Pour un agent qui doit systématiquement répondre dans un format très particulier (par exemple, toujours structurer sa réponse en trois sections précises), le fine-tuning serait-il justifié plutôt qu'un prompt système bien conçu ? Discutez les deux options.

LEÇON 1.3Le rôle du dataset dans la qualité du modèle final

Le principe fondateur de ce cours, souvent résumé par l'expression "garbage in, garbage out" : la qualité d'un modèle après fine-tuning ne peut pas dépasser la qualité du dataset utilisé pour l'entraîner. Un modèle de base excellent, fine-tuné sur des exemples médiocres, produira un résultat médiocre.

Ce qui détermine la qualité du modèle fine-tuné : QUALITÉ DES EXEMPLES INDIVIDUELS Chaque paire instruction/réponse doit être correcte, cohérente et représentative du comportement souhaité (approfondi module 2) COHÉRENCE DU FORMAT À TRAVERS LE DATASET Rappel leçon 1.1 : une incohérence de format n'affecte pas un seul exemple, elle brouille le signal d'apprentissage pour l'ensemble du dataset (approfondi modules 3, 5) REPRÉSENTATIVITÉ DE LA DISTRIBUTION Le dataset doit couvrir la variété des cas que le modèle rencontrera en production, sans sur-représenter certains types de requêtes au détriment d'autres (approfondi module 7) VOLUME SUFFISANT MAIS PAS EXCESSIF Un dataset trop petit ne permet pas au modèle d'apprendre le comportement voulu ; un dataset trop volumineux mais de mauvaise qualité peut être pire qu'un dataset plus restreint mais rigoureusement contrôlé

Ce dernier point mérite d'être souligné dès ce premier module : contrairement à une intuition répandue, un dataset plus petit mais soigneusement construit produit souvent un meilleur résultat qu'un dataset volumineux mais bâclé — un principe qui justifie l'investissement en temps que ce cours consacre au nettoyage (module 5) et à la validation (module 7) plutôt qu'à la seule accumulation de volume.

Piège courant Prioriser le volume du dataset ("plus il y a d'exemples, mieux c'est") au détriment de sa qualité et de sa cohérence — une conviction intuitive mais souvent contredite en pratique, où un dataset plus restreint et rigoureusement contrôlé produit fréquemment de meilleurs résultats qu'un dataset large mais bruité.
Exercice Pour un projet de fine-tuning, comment arbitreriez-vous entre "collecter davantage d'exemples rapidement" et "vérifier soigneusement moins d'exemples" si votre temps est limité ?

LEÇON 1.5Erreurs courantes de conception de dataset

Cette dernière leçon du module recense les erreurs les plus fréquentes observées lors de la conception d'un dataset de fine-tuning, approfondies individuellement dans les modules suivants.

Erreur 1 : incohérence de format à travers le dataset

Mélanger différentes conventions de structuration (certains exemples avec un champ "input" vide, d'autres non ; des styles de formulation d'instruction incohérents) sans standardisation préalable — approfondi au module 2.

Erreur 2 : ne pas valider la conformité JSONL avant l'entraînement

Soumettre un fichier contenant des lignes malformées ou des erreurs d'encodage à un pipeline d'entraînement, découvrant le problème seulement après l'échec du job — approfondi au module 3.

Erreur 3 : dataset non représentatif de l'usage réel

Construire un dataset à partir d'une source unique et biaisée (par exemple, uniquement des conversations "faciles" bien résolues), sans représenter la diversité des cas rencontrés en production — approfondi au module 4.

Erreur 4 : négliger la validation avant de lancer l'entraînement

Passer directement de la construction du dataset à l'entraînement, sans étape de vérification systématique de la distribution, du format et de la couverture — approfondi au module 7.

Les quatre erreurs à éviter, résumées : 1. INCOHÉRENCE DE FORMAT → Signal d'apprentissage brouillé 2. JSONL NON VALIDÉ → Échec tardif et coûteux du job d'entraînement 3. DATASET NON REPRÉSENTATIF → Modèle qui généralise mal en production 4. VALIDATION NÉGLIGÉE → Problèmes découverts trop tard, après un cycle d'entraînement complet

Les modules suivants traitent chacune de ces erreurs en détail : le module 2 établit la structure du format instruction/réponse, le module 3 la rigueur du format JSONL, le module 4 la construction représentative du dataset, et le module 7 la validation systématique avant l'entraînement final.

Piège courant Traiter ces quatre erreurs comme des vérifications ponctuelles à effectuer une seule fois en fin de projet, plutôt que comme des principes à intégrer dès la conception initiale du pipeline de préparation — une erreur de format découverte après avoir collecté des milliers d'exemples est bien plus coûteuse à corriger qu'une convention établie clairement dès le départ.

MODULE 02 / 08

Le format instruction/réponse

Ce module détaille la structure de base d'un exemple d'entraînement pour le fine-tuning : le format instruction/réponse, ses variantes courantes, et comment choisir la bonne convention selon le modèle et la tâche visés.

LEÇON 2.1Anatomie d'un exemple instruction/réponse

La forme la plus simple d'un exemple d'entraînement pour le fine-tuning comporte trois composantes, dont une est optionnelle selon les cas.

{
  "instruction": "Résume ce texte en une phrase.",
  "input": "Le chat s'est assis sur le tapis rouge près de la fenêtre "
           "ensoleillée, observant les oiseaux dans le jardin voisin.",
  "output": "Un chat observe des oiseaux depuis un tapis près d'une fenêtre."
}
Les trois composantes et leur rôle : INSTRUCTION La consigne ou la tâche demandée — ce que l'utilisateur ou le système souhaite que le modèle accomplisse INPUT (optionnel) Le contenu sur lequel l'instruction doit s'appliquer — pour certaines tâches, l'instruction se suffit à elle-même et ce champ reste vide ("Explique la photosynthèse" n'a pas besoin d'un input séparé) OUTPUT La réponse attendue — c'est ce texte précis que le modèle apprend à produire face à cette instruction et cet input pendant l'entraînement

La séparation entre instruction et input permet de réutiliser une même instruction générique ("Résume ce texte") sur des contenus différents, tandis qu'une instruction auto-suffisante ("Explique la photosynthèse") peut laisser ce champ vide — un choix de conception qui a des implications directes sur la variété du dataset, approfondies au module 4.

Piège courant Toujours combiner l'instruction et l'input en un seul champ de texte libre, même quand une tâche générique et un contenu variable pourraient être clairement séparés — cette fusion réduit la capacité du modèle à généraliser la même instruction à des contenus différents, en la traitant à chaque fois comme un exemple entièrement nouveau et distinct.
Exercice Pour la tâche "traduire un texte en anglais", formulez un exemple avec les trois champs (instruction, input, output) distincts.

LEÇON 2.2Formats courants : Alpaca, ShareGPT, chat/messages

Plusieurs conventions de formatage se sont établies comme standards de facto dans l'écosystème du fine-tuning, chacune héritée d'un projet ou d'un usage particulier — connaître ces conventions permet de choisir celle la mieux supportée par l'outillage d'entraînement utilisé.

// Format "Alpaca" — hérité du projet Stanford Alpaca,
// la structure la plus simple, dérivée directement de la leçon 2.1
{"instruction": "Résume ce texte.", "input": "...", "output": "..."}

// Format "ShareGPT" — structuré comme une liste de tours de
// conversation, plus adapté au multi-turn (approfondi leçon 2.3)
{"conversations": [
  {"from": "human", "value": "Résume ce texte : ..."},
  {"from": "gpt", "value": "Un chat observe des oiseaux..."}
]}

// Format "chat / messages" — le plus proche des API de production
// actuelles (rappel cours 17, sur la structure des appels LLM)
{"messages": [
  {"role": "system", "content": "Tu es un assistant qui résume des textes."},
  {"role": "user", "content": "Résume ce texte : ..."},
  {"role": "assistant", "content": "Un chat observe des oiseaux..."}
]}
Comparaison rapide des trois formats : Format ALPACA Format CHAT/MESSAGES ──────────────────────── ──────────────────────── Simple, adapté aux tâches Représente nativement les single-turn (leçon 2.3) rôles (system/user/assistant) et les conversations multi-tours Pas de notion native de "rôle" ou de system prompt Format le plus proche de ce qu'un modèle rencontre déjà Historiquement le plus répandu en PRODUCTION (rappel cours 17, dans les premiers datasets structure des messages API) open-source de fine-tuning

Le format "chat/messages" tend aujourd'hui à devenir le standard le plus largement supporté, en particulier parce qu'il correspond exactement à la structure utilisée par les API de production (rappel cours 17) — un modèle entraîné avec ce même format n'a pas besoin d'apprendre une convention différente entre l'entraînement et l'usage réel.

Piège courant Choisir un format de dataset sans vérifier au préalable lequel est attendu par l'outil ou la plateforme d'entraînement utilisée — chaque outil a généralement une préférence ou une exigence stricte de format, et une conversion tardive entre formats peut introduire des erreurs subtiles si elle n'est pas effectuée avec soin (approfondi module 3).
Exercice Convertissez l'exemple Alpaca de la leçon 2.1 vers le format chat/messages, en ajoutant un system prompt pertinent pour la tâche de résumé.

LEÇON 2.3Single-turn vs multi-turn (conversations)

Un exemple single-turn représente un unique échange (une instruction, une réponse) ; un exemple multi-turn représente une conversation complète avec plusieurs échanges successifs — un choix qui dépend directement du comportement final souhaité pour le modèle.

// SINGLE-TURN : un échange isolé
{"messages": [
  {"role": "user", "content": "Quelle est la capitale de la France ?"},
  {"role": "assistant", "content": "La capitale de la France est Paris."}
]}

// MULTI-TURN : une conversation avec plusieurs échanges, où
// chaque réponse doit tenir compte du contexte des tours précédents
{"messages": [
  {"role": "user", "content": "Quelle est la capitale de la France ?"},
  {"role": "assistant", "content": "La capitale de la France est Paris."},
  {"role": "user", "content": "Et sa population ?"},
  {"role": "assistant", "content": "Paris compte environ 2,1 millions d'habitants."}
]}

Le second exemple illustre une compétence spécifique que seul un format multi-turn peut entraîner : comprendre que "sa population" fait référence à Paris, mentionné dans le tour précédent — une capacité de suivi de contexte qu'un agent conversationnel réel doit maîtriser, mais qu'un dataset uniquement single-turn ne peut pas lui enseigner directement.

Quand privilégier chaque approche : SINGLE-TURN MULTI-TURN ──────────────────────── ──────────────────────── Tâches ponctuelles et Comportement conversationnel indépendantes (résumé, traduction, réel, avec suivi de contexte classification d'un texte isolé) entre plusieurs échanges Plus simple à construire et Nécessaire pour un modèle à vérifier (module 5) destiné à un usage de chat multi-tours en production Risque : un modèle entraîné uniquement en single-turn peut Plus complexe à construire : mal gérer les références chaque tour doit rester implicites en conversation réelle cohérent avec les précédents
Piège courant Construire un dataset exclusivement single-turn pour un modèle destiné à un usage conversationnel multi-tours en production — un tel modèle peut alors échouer à comprendre les références implicites au contexte des tours précédents ("et sa population ?"), un mode d'échec qui n'apparaît qu'après le déploiement, dans des conversations réelles à plusieurs tours.
Exercice Pour un modèle destiné à un agent de support client (rappel cours 17-19), le dataset devrait-il être exclusivement multi-turn, exclusivement single-turn, ou un mélange des deux ? Justifiez.

LEÇON 2.4Le system prompt et son rôle dans le format d'entraînement

Rappel du cours 17 (module 1) : un system prompt définit le rôle, le ton et les contraintes générales d'un modèle. Dans un dataset de fine-tuning au format chat/messages (leçon 2.2), ce même mécanisme peut être utilisé pour entraîner le modèle à adopter un comportement cohérent à travers l'ensemble du dataset.

{"messages": [
  {"role": "system", "content": "Tu es un assistant de support client pour "
                                  "une boutique en ligne. Réponds toujours "
                                  "de façon concise et polie."},
  {"role": "user", "content": "Où en est ma commande ?"},
  {"role": "assistant", "content": "Je vais vérifier cela pour vous. Pouvez-vous "
                                    "me communiquer votre numéro de commande ?"}
]}
Deux stratégies possibles pour le system prompt dans un dataset : STRATÉGIE 1 : SYSTEM PROMPT IDENTIQUE PARTOUT Le même system prompt apparaît dans tous les exemples du dataset — renforce un comportement stable et cohérent, adapté à un modèle destiné à un usage unique et bien défini STRATÉGIE 2 : SYSTEM PROMPTS VARIÉS Différents system prompts selon les exemples — utile pour entraîner un modèle plus généraliste, capable de s'adapter à des instructions système différentes selon le contexte d'utilisation final

Un point souvent mal compris : le fine-tuning avec un system prompt cohérent ne rend pas ce prompt "inutile" au moment de l'inférence — au contraire, le modèle apprend à répondre de façon optimale en présence de ce prompt, qui doit donc continuer à être fourni lors de l'utilisation réelle du modèle fine-tuné, exactement comme il l'était pendant l'entraînement.

Piège courant Entraîner un modèle avec un system prompt cohérent dans le dataset, puis l'utiliser en production sans fournir ce même system prompt — le modèle a appris son comportement en présence de ce contexte précis, et son omission au moment de l'inférence peut dégrader significativement la qualité et la cohérence des réponses obtenues.
Exercice Pour un dataset destiné à entraîner un modèle à toujours répondre en une seule phrase concise, rédigez le system prompt qui devrait accompagner chaque exemple.

MODULE 03 / 08

JSONL en profondeur

Le module précédent a établi la structure logique d'un exemple d'entraînement (instruction/réponse, chat/messages). Ce module traite son encodage physique : le format JSONL, quasi universellement utilisé pour stocker et transmettre des datasets de fine-tuning.

LEÇON 3.1Qu'est-ce que JSONL et pourquoi ce format pour le fine-tuning

JSONL (JSON Lines) est un format où chaque ligne d'un fichier texte contient un objet JSON complet et valide, indépendant des autres lignes — par opposition à un unique fichier JSON contenant un tableau englobant tous les exemples.

// dataset.jsonl — chaque LIGNE est un objet JSON indépendant
{"messages": [{"role": "user", "content": "Q1 ?"}, {"role": "assistant", "content": "R1."}]}
{"messages": [{"role": "user", "content": "Q2 ?"}, {"role": "assistant", "content": "R2."}]}
{"messages": [{"role": "user", "content": "Q3 ?"}, {"role": "assistant", "content": "R3."}]}

LEÇON 3.2Structure ligne par ligne, encodage, streaming

Cette leçon détaille les règles précises du format JSONL et comment le lire ou l'écrire correctement en pratique, en particulier pour des fichiers trop volumineux pour être chargés entièrement en mémoire.

import json

def ecrire_jsonl(exemples: list[dict], chemin_fichier: str) -> None:
    """Chaque exemple est sérialisé sur SA PROPRE ligne, terminée
    par un retour à la ligne — jamais de tableau englobant, jamais
    de virgule entre les exemples (rappel leçon 3.1)."""
    with open(chemin_fichier, "w", encoding="utf-8") as f:
        for exemple in exemples:
            f.write(json.dumps(exemple, ensure_ascii=False) + "\n")

def lire_jsonl_en_streaming(chemin_fichier: str):
    """Lecture LIGNE PAR LIGNE — ne charge jamais l'intégralité
    du fichier en mémoire, contrairement à json.load() sur un
    fichier JSON classique."""
    with open(chemin_fichier, "r", encoding="utf-8") as f:
        for ligne in f:
            ligne = ligne.strip()
            if ligne:
                yield json.loads(ligne)
Points de rigueur essentiels pour un encodage JSONL correct : ENCODAGE UTF-8 EXPLICITE Toujours ouvrir le fichier avec encoding="utf-8" — un défaut d'encodage varie selon le système d'exploitation et peut corrompre silencieusement des caractères accentués ou spéciaux ensure_ascii=False Sans ce paramètre, json.dumps() échapperait tous les caractères non-ASCII (accents français, par exemple) en séquences \\uXXXX — techniquement valide mais moins lisible et parfois source de confusion lors d'un débogage manuel UN OBJET JSON PAR LIGNE, RIEN D'AUTRE Pas de virgule finale, pas de tableau englobant, pas de ligne vide au milieu du fichier (approfondi leçon 3.5)

La fonction de lecture en streaming illustrée ci-dessus (un générateur Python utilisant yield) matérialise concrètement l'avantage de la leçon 3.1 : chaque ligne est lue, parsée et traitée une à une, sans jamais retenir l'ensemble du fichier en mémoire — un pattern à privilégier systématiquement dès que le dataset dépasse quelques milliers d'exemples.

Piège courant Charger un fichier JSONL volumineux avec une simple boucle qui accumule tous les exemples dans une liste en mémoire avant de les traiter, perdant ainsi l'avantage principal du format — pour un traitement séquentiel (validation, nettoyage), le streaming ligne par ligne évite un pic de consommation mémoire inutile.

LEÇON 3.3Valider la conformité d'un fichier JSONL

Rappel de la leçon 1.5 (erreur 2) : soumettre un fichier JSONL non validé à un pipeline d'entraînement risque un échec tardif et coûteux. Cette leçon détaille une validation systématique à effectuer avant tout entraînement.

def valider_jsonl(chemin_fichier: str, schema_attendu: type) -> dict:
    """Valide chaque ligne individuellement, en isolant les
    erreurs plutôt que de faire échouer toute la validation
    au premier problème rencontré — rappel du principe déjà
    établi au cours 17 (module 4) pour la validation d'appels
    de fonction, appliqué ici à un dataset entier."""
    resultats = {"total": 0, "valides": 0, "erreurs": []}
    with open(chemin_fichier, "r", encoding="utf-8") as f:
        for numero_ligne, ligne in enumerate(f, start=1):
            resultats["total"] += 1
            ligne = ligne.strip()
            if not ligne:
                resultats["erreurs"].append({"ligne": numero_ligne, "erreur": "ligne vide"})
                continue
            try:
                donnees = json.loads(ligne)
                schema_attendu(**donnees)  # rappel cours 17, validation Pydantic
                resultats["valides"] += 1
            except json.JSONDecodeError as e:
                resultats["erreurs"].append({"ligne": numero_ligne, "erreur": f"JSON invalide: {e}"})
            except Exception as e:
                resultats["erreurs"].append({"ligne": numero_ligne, "erreur": f"schéma invalide: {e}"})
    return resultats
Pourquoi valider LIGNE PAR LIGNE avec isolation des erreurs : Validation qui s'arrête à la Validation qui ISOLE chaque PREMIÈRE erreur rencontrée erreur (comme ci-dessus) ──────────────────────────────── ──────────────────────────────── Une seule ligne corrompue sur Révèle l'INTÉGRALITÉ des 100 000 bloque la validation lignes problématiques en UNE complète — l'erreur suivante SEULE passe, avec leur numéro n'est découverte qu'après avoir de ligne exact — permet une corrigé la première correction ciblée et complète avant de relancer quoi que Cycle correction-revalidation ce soit

Cette approche d'isolation des erreurs, plutôt qu'un arrêt au premier problème, rejoint directement un principe déjà établi au cours 17 (module 4, leçon 4.5) sur la gestion des échecs de validation : révéler l'ensemble des problèmes en une seule passe permet une correction plus efficace qu'un cycle itératif de découverte-correction-relance.

Piège courant Valider un dataset en s'arrêtant à la première erreur rencontrée (par exemple, via une exception non gérée qui interrompt tout le script), forçant un cycle de correction ligne par ligne plutôt que de révéler l'ensemble des problèmes en une seule exécution de la validation.

def transformer_trace_en_exemple(trace: dict) -> dict:

LEÇON 5.1Nettoyer le texte des instructions et réponses

Rappel direct du cours 11 (nettoyage de texte non structuré) : les mêmes principes de nettoyage — suppression de caractères de contrôle, normalisation des espaces, correction d'artefacts d'extraction — s'appliquent au contenu d'un dataset de fine-tuning, avec un enjeu spécifique : ce nettoyage affecte directement ce que le modèle apprendra à reproduire.

import re
import unicodedata

def nettoyer_texte_exemple(texte: str) -> str:
    """Rappel cours 11 — les mêmes techniques de nettoyage de
    texte s'appliquent ici, avec un enjeu supplémentaire : tout
    artefact non nettoyé sera APPRIS par le modèle comme faisant
    partie du style de réponse normal."""
    texte = unicodedata.normalize("NFKC", texte)  # normalise les formes Unicode
    texte = re.sub(r"[\x00-\x08\x0b\x0c\x0e-\x1f]", "", texte)  # caractères de contrôle
    texte = re.sub(r" {2,}", " ", texte)  # espaces multiples
    texte = re.sub(r"\n{3,}", "\n\n", texte)  # sauts de ligne excessifs
    return texte.strip()
Pourquoi ce nettoyage compte davantage qu'en contexte RAG : Contexte RAG (cours 9-13) Contexte fine-tuning (ce module) ──────────────────────────────── ──────────────────────────────── Un artefact non nettoyé (espace Un artefact non nettoyé dans multiple, caractère de contrôle) une RÉPONSE d'entraînement dégrade légèrement la qualité enseigne au modèle à d'un chunk consulté ponctuellement REPRODUIRE ce même artefact dans ses réponses futures — un comportement appris, pas une consultation ponctuelle

Ce contraste avec le contexte RAG rejoint directement le principe déjà établi à la leçon 1.1 de ce cours : une imperfection dans une donnée de fine-tuning ne reste jamais isolée, elle se diffuse dans le comportement général du modèle une fois l'entraînement effectué.

Piège courant Appliquer le même niveau de nettoyage à un dataset de fine-tuning qu'à des chunks destinés à un système RAG, sans reconnaître que les artefacts non nettoyés ici seront appris et reproduits par le modèle, plutôt que simplement consultés une fois puis oubliés.

LEÇON 5.2Gérer la longueur : troncature, découpage, tokens

Rappel direct du cours 16 (NLP de base, tokenization) : un modèle de langage traite le texte sous forme de tokens, avec une limite de contexte maximale. Un exemple d'entraînement qui dépasse cette limite pose un problème spécifique à traiter avant l'entraînement.

def compter_tokens_exemple(exemple: dict, tokenizer) -> int:
    """Rappel cours 16 sur la tokenization — le compte de TOKENS,
    pas de caractères, détermine si un exemple dépasse la limite
    de contexte du modèle à entraîner."""
    texte_complet = "\n".join(m["content"] for m in exemple["messages"])
    return len(tokenizer.encode(texte_complet))

def gerer_exemple_trop_long(exemple: dict, tokenizer, limite_tokens: int) -> dict | None:
    nombre_tokens = compter_tokens_exemple(exemple, tokenizer)
    if nombre_tokens <= limite_tokens:
        return exemple
    return None  # rappel leçon suivante : rejeter plutôt que tronquer à l'aveugle
Stratégies face à un exemple dépassant la limite de tokens : REJETER L'EXEMPLE Le plus sûr par défaut — évite de tronquer arbitrairement une réponse, ce qui produirait un exemple d'entraînement INCOMPLET et potentiellement incohérent (une réponse coupée au milieu d'une phrase, enseignant au modèle à s'arrêter là) TRONQUER AVEC PRÉCAUTION Envisageable seulement si la troncature préserve un sens complet (par exemple, couper au dernier point final avant la limite) — jamais une troncature brutale au token exact DÉCOUPER EN PLUSIEURS EXEMPLES DISTINCTS Pour un contenu naturellement divisible (rappel cours 9, chunking), scinder en plusieurs exemples plus courts plutôt que d'en perdre le contenu intégralement

Le rejet reste l'option la plus sûre par défaut : rappel de la leçon 5.1, un exemple mal formé (ici, tronqué de façon incohérente) enseigne un comportement indésirable au modèle — mieux vaut un dataset légèrement plus restreint mais entièrement cohérent qu'un dataset plus volumineux contenant des exemples corrompus par une troncature mal maîtrisée.

Piège courant Tronquer systématiquement et sans discernement tout exemple dépassant la limite de tokens à un nombre fixe de caractères, sans vérifier que le résultat reste cohérent — une réponse coupée en plein milieu d'une phrase enseigne au modèle un comportement de troncature qu'il pourrait reproduire dans ses propres réponses futures.

LEÇON 5.3Normaliser les rôles et les balises spéciales

Rappel du module 2 (formats courants) : différentes sources peuvent utiliser des conventions différentes pour désigner les rôles d'une conversation (par exemple "human"/"gpt" en ShareGPT vs "user"/"assistant" en format chat/messages). Cette leçon traite la normalisation nécessaire quand un dataset combine plusieurs sources.

MAPPING_ROLES = {
    "human": "user", "gpt": "assistant", "bot": "assistant",
    "user": "user", "assistant": "assistant", "system": "system",
}

def normaliser_roles(exemple_brut: dict) -> dict:
    """Rappel cours 19, module 3, leçon 3.2 — même principe de
    normalisation de champs hétérogènes, appliqué ici aux rôles
    de conversation plutôt qu'aux champs de logs."""
    messages_normalises = []
    for message in exemple_brut.get("conversations", exemple_brut.get("messages", [])):
        role_brut = message.get("from", message.get("role"))
        contenu = message.get("value", message.get("content"))
        role_normalise = MAPPING_ROLES.get(role_brut)
        if role_normalise is None:
            raise ValueError(f"Rôle non reconnu : {role_brut}")
        messages_normalises.append({"role": role_normalise, "content": contenu})
    return {"messages": messages_normalises}
Pourquoi lever une exception sur un rôle NON RECONNU plutôt que de l'ignorer silencieusement : Un rôle non reconnu (une faute de frappe, une nouvelle convention introduite par une source récente) signale soit une ERREUR DE DONNÉES à corriger, soit un NOUVEAU FORMAT à intégrer explicitement au mapping — l'ignorer silencieusement risque de perdre ou de mal attribuer ce message dans l'exemple final

Ce principe rejoint directement celui déjà établi au cours 19 (module 3, leçon 3.3) sur le traitement des logs non reconnus : marquer explicitement un cas non anticipé, plutôt que de le traiter silencieusement par une valeur par défaut potentiellement incorrecte, permet de détecter et corriger les nouveaux formats au fur et à mesure qu'ils apparaissent.

Piège courant Assigner un rôle par défaut arbitraire (par exemple, toujours "user") à tout rôle non reconnu plutôt que de signaler explicitement l'anomalie — cette pratique peut silencieusement corrompre la structure de la conversation, par exemple en attribuant à tort le rôle "user" à un message qui provenait en réalité de l'assistant.

LEÇON 5.4Déduplication des exemples

Un dataset construit à partir de plusieurs sources (module 4) ou par génération synthétique (leçon 4.3) accumule fréquemment des doublons ou quasi-doublons — cette leçon traite une déduplication de base, qui sera approfondie à plus grande échelle au cours 21 de ce même bloc.

import hashlib

def dedupliquer_exemples_exacts(exemples: list[dict]) -> list[dict]:
    """Déduplication EXACTE — détecte les exemples strictement
    identiques via une empreinte de hachage (rappel cours 19,
    module 4, leçon 4.3, sur le même principe de hachage appliqué
    ici au contenu complet d'un exemple plutôt qu'à une PII)."""
    empreintes_vues = set()
    exemples_uniques = []
    for exemple in exemples:
        empreinte = hashlib.sha256(
            json.dumps(exemple, sort_keys=True).encode()
        ).hexdigest()
        if empreinte not in empreintes_vues:
            empreintes_vues.add(empreinte)
            exemples_uniques.append(exemple)
    return exemples_uniques
Deux niveaux de duplication à distinguer : DUPLICATION EXACTE (traitée ici) QUASI-DUPLICATION (cours 21) ──────────────────────────────── ──────────────────────────────── Deux exemples STRICTEMENT Deux exemples formulés identiques, caractère pour différemment mais transmettant caractère — détectable par un la même information ou simple hachage du contenu complet structure — nécessite une détection par SIMILARITÉ Fréquent quand une même source (embeddings, rappel cours 18, est traitée plusieurs fois par module 5, leçon 5.3) plutôt erreur, ou quand plusieurs pipelines qu'une correspondance exacte de collecte se recoupent partiellement

Pourquoi la duplication, même exacte, pose problème pour l'entraînement : un exemple répété plusieurs fois dans un dataset lui donne un poids disproportionné dans l'apprentissage du modèle par rapport aux exemples uniques — un déséquilibre qui peut biaiser le comportement final vers une sur-représentation involontaire de ce cas particulier.

Piège courant Se contenter d'une déduplication exacte (comme celle de cette leçon) en la considérant suffisante, sans anticiper que la quasi-duplication — des exemples formulés différemment mais redondants en substance — pose un problème similaire de déséquilibre, un sujet qui nécessite les techniques plus avancées approfondies au cours 21.

LEÇON 5.5Pièges courants de nettoyage pour le fine-tuning

Cette dernière leçon du module recense des pièges spécifiques au nettoyage d'un dataset de fine-tuning, en complément des principes déjà établis.

Piège 1 : nettoyer l'instruction mais pas la réponse (ou l'inverse)

Un nettoyage appliqué de façon incohérente selon les champs peut introduire une asymétrie de qualité entre l'instruction et sa réponse associée, alors que les deux devraient recevoir la même rigueur de traitement.

Piège 2 : sur-nettoyer au point de perdre la voix naturelle du contenu

Un nettoyage trop agressif (suppression de toute variation stylistique, normalisation excessive de la ponctuation) peut uniformiser artificiellement le dataset au point de produire un modèle au style monotone et peu naturel — un équilibre similaire à celui déjà discuté au cours 19 (module 4, leçon 4.5) entre sur-masquage et sous-masquage, appliqué ici au style plutôt qu'à la protection de données.

Piège 3 : ne pas revalider après nettoyage

Un traitement de nettoyage peut lui-même introduire des erreurs (rappel cours 19, module 3, leçon 3.5, sur les pièges de nettoyage) — une nouvelle passe de validation (approfondie au module 7) après nettoyage reste nécessaire, pas seulement avant.

Ce module clôt la partie "nettoyage" du cours. Le module suivant change de perspective : comment structurer un dataset non plus pour une tâche générique, mais pour des cas d'usage spécifiques — function calling, conversations multi-tours, classification.
Piège courant Considérer le nettoyage comme une étape strictement antérieure à la validation (module 7), alors que le nettoyage lui-même peut introduire de nouvelles erreurs qui nécessitent une revalidation après coup — la validation devrait encadrer le nettoyage des deux côtés, avant ET après, plutôt que de se limiter à une seule vérification en amont.

def controler_proportions_dataset(exemples_par_type: dict[str, list], proportions_cibles: dict[str, float],
                                     taille_totale: int) -> list:
    """Assemble un dataset final en respectant des PROPORTIONS
    explicites entre types de tâches, plutôt que de simplement
    concaténer toutes les sources disponibles sans contrôle."""
    dataset_final = []
    for type_tache, proportion in proportions_cibles.items():
        nombre_a_prendre = int(taille_totale * proportion)
        dataset_final.extend(exemples_par_type[type_tache][:nombre_a_prendre])
    random.shuffle(dataset_final)  # éviter un ordre groupé par type de tâche
    return dataset_final

Le mélange (random.shuffle) en fin de constitution mérite une attention particulière : un dataset où tous les exemples d'un même type de tâche se suivent consécutivement peut, selon la méthode d'entraînement utilisée, induire un apprentissage moins stable qu'un dataset où les types de tâches sont distribués de façon homogène tout au long du fichier.

LEÇON 7.1Split train / validation / test — principes et pièges

Un dataset de fine-tuning est généralement divisé en plusieurs sous-ensembles distincts, chacun avec un rôle précis dans le processus d'entraînement et d'évaluation.

Les trois ensembles et leur rôle : TRAIN (typiquement 80-90%) Les exemples sur lesquels le modèle est effectivement entraîné — la majorité du dataset VALIDATION (typiquement 5-10%) Utilisé PENDANT l'entraînement pour surveiller la progression et détecter un surapprentissage (le modèle mémorise le train sans généraliser) TEST (typiquement 5-10%) Réservé pour une évaluation FINALE, après l'entraînement complet — ne doit JAMAIS être consulté ni utilisé pendant le processus d'entraînement lui-même
import random

def diviser_dataset(exemples: list[dict], proportions: tuple = (0.85, 0.10, 0.05)) -> dict:
    exemples_melanges = exemples.copy()
    random.shuffle(exemples_melanges)
    n = len(exemples_melanges)
    fin_train = int(n * proportions[0])
    fin_validation = fin_train + int(n * proportions[1])
    return {
        "train": exemples_melanges[:fin_train],
        "validation": exemples_melanges[fin_train:fin_validation],
        "test": exemples_melanges[fin_validation:],
    }

Un piège fréquent, distinct de la simple proportion : si le dataset contient des exemples provenant de la même source originale (par exemple, plusieurs variations générées à partir d'un même document, rappel module 4), ces variations ne devraient pas se répartir entre train et test — un modèle qui a "vu" une version très proche d'un exemple de test pendant l'entraînement produira une évaluation artificiellement optimiste, un phénomène appelé fuite de données (data leakage).

Risque de fuite de données entre ensembles : Exemple A (train) : dérivé du document X Exemple B (test) : également dérivé du document X, avec une formulation légèrement différente → Le modèle a indirectement "vu" le contenu du document X pendant l'entraînement (via l'exemple A) — évaluer sa performance sur l'exemple B ne mesure pas une VRAIE généralisation, mais une familiarité résiduelle
Piège courant Découper un dataset en train/validation/test par un simple tirage aléatoire sur les exemples individuels, sans vérifier si plusieurs exemples partagent une même source ou un même document d'origine — un tel découpage risque une fuite de données qui rend l'évaluation finale sur l'ensemble de test artificiellement optimiste.
Exercice Pour un dataset où plusieurs exemples sont dérivés des mêmes documents sources (rappel module 4, leçon 4.1), comment adapteriez-vous la fonction de découpage ci-dessus pour éviter la fuite de données décrite ?

LEÇON 7.2Valider automatiquement le format avant entraînement

Cette leçon assemble une validation finale complète, combinant les vérifications déjà couvertes individuellement dans les modules précédents (structure au module 2, JSONL au module 3, longueur au module 5) en une seule passe de contrôle avant l'entraînement.

def validation_finale_complete(chemin_fichier: str, tokenizer, limite_tokens: int) -> dict:
    """Combine les validations des modules précédents en une
    seule passe — rappel du principe déjà établi au module 3,
    leçon 3.3, d'isoler chaque erreur plutôt que de s'arrêter
    à la première rencontrée."""
    rapport = {"total": 0, "valides": 0, "problemes": []}
    for numero_ligne, exemple in enumerate(lire_jsonl_en_streaming(chemin_fichier), start=1):
        rapport["total"] += 1
        problemes_exemple = []
        if "messages" not in exemple or not exemple["messages"]:
            problemes_exemple.append("structure manquante ou vide")
        elif not all(m.get("role") in ("system", "user", "assistant", "tool") for m in exemple["messages"]):
            problemes_exemple.append("rôle non reconnu (rappel module 5, leçon 5.3)")
        nombre_tokens = compter_tokens_exemple(exemple, tokenizer)
        if nombre_tokens > limite_tokens:
            problemes_exemple.append(f"dépasse la limite de tokens ({nombre_tokens})")
        if problemes_exemple:
            rapport["problemes"].append({"ligne": numero_ligne, "problemes": problemes_exemple})
        else:
            rapport["valides"] += 1
    return rapport

Cette validation finale ne remplace pas les vérifications effectuées à chaque étape antérieure (modules 3 et 5) — elle constitue un dernier filet de sécurité qui confirme, juste avant l'entraînement, qu'aucune régression ne s'est introduite lors des étapes intermédiaires de transformation du dataset.

Piège courant Considérer que les validations effectuées à chaque étape antérieure (modules 3, 5) rendent superflue une validation finale complète juste avant l'entraînement — une étape de transformation ultérieure (déduplication, split, mélange de sources) peut réintroduire une erreur, même après des vérifications antérieures rigoureuses.

LEÇON 7.3Vérifier la distribution et la couverture du dataset

Rappel de la leçon 4.5 (piège 2) : un dataset peut être structurellement valide tout en étant mal réparti entre types de cas. Cette leçon propose une vérification quantitative de cette distribution, complémentaire à la validation structurelle de la leçon précédente.

from collections import Counter

def analyser_distribution(exemples: list[dict], fonction_categorisation) -> dict:
    """Rappel module 6, leçon 6.5 : vérifier QUANTITATIVEMENT
    les proportions entre catégories, plutôt que de supposer
    qu'elles sont équilibrées sans les mesurer."""
    categories = [fonction_categorisation(exemple) for exemple in exemples]
    compteur = Counter(categories)
    total = len(exemples)
    return {categorie: {"nombre": n, "proportion": n / total} for categorie, n in compteur.items()}

# Exemple d'utilisation pour un dataset mêlant plusieurs types
# de tâches (rappel module 6, leçon 6.5)
distribution = analyser_distribution(exemples, lambda ex: ex.get("type_tache", "non_categorise"))
Ce qu'une analyse de distribution permet de détecter : DÉSÉQUILIBRE ENTRE CATÉGORIES Rappel module 6, leçon 6.4 — un déséquilibre de classification (90% positif, 10% négatif) devient visible immédiatement plutôt que découvert après l'entraînement via un modèle biaisé SOUS-REPRÉSENTATION D'UN CAS D'USAGE CRITIQUE Un cas d'usage jugé important (rappel module 6, leçon 6.2, gestion d'erreur de validation en function calling) qui ne représente que 2% du dataset, alors qu'il mériterait une part plus significative compte tenu de sa criticité ABSENCE COMPLÈTE D'UNE CATÉGORIE ATTENDUE Une catégorie prévue dans la conception initiale du dataset (module 8, leçon 8.1) mais absente en pratique — signale un problème dans le pipeline de construction (module 4) passé inaperçu jusqu'ici
Piège courant Valider uniquement la conformité structurelle d'un dataset (leçon 7.2) sans jamais analyser quantitativement sa distribution par catégorie ou type de tâche — un dataset peut être parfaitement valide structurellement tout en étant fortement déséquilibré, un problème invisible sans cette analyse dédiée.

LEÇON 7.4Estimer le coût et la taille du dataset

Le fine-tuning d'un modèle, en particulier via une API commerciale, est généralement facturé au nombre de tokens traités pendant l'entraînement. Cette leçon traite comment estimer ce coût avant de lancer un entraînement, pour éviter une surprise budgétaire après coup.

def estimer_cout_entrainement(exemples: list[dict], tokenizer, cout_par_million_tokens: float,
                                 nombre_epochs: int = 3) -> dict:
    """Le coût dépend du nombre de tokens ET du nombre
    d'EPOCHS (passages complets sur le dataset) — un dataset
    parcouru 3 fois pendant l'entraînement coûte environ 3 fois
    le coût d'un seul passage."""
    total_tokens = sum(compter_tokens_exemple(ex, tokenizer) for ex in exemples)
    total_tokens_avec_epochs = total_tokens * nombre_epochs
    cout_estime = (total_tokens_avec_epochs / 1_000_000) * cout_par_million_tokens
    return {
        "nombre_exemples": len(exemples),
        "total_tokens_par_epoch": total_tokens,
        "total_tokens_entrainement": total_tokens_avec_epochs,
        "cout_estime_usd": round(cout_estime, 2),
    }
Pourquoi estimer AVANT de lancer l'entraînement, pas après : Sans estimation préalable Avec estimation préalable ──────────────────────────────── ──────────────────────────────── Le coût réel n'est découvert Une estimation réaliste qu'APRÈS l'exécution complète permet de décider, en amont, du job d'entraînement — trop tard si le dataset doit être pour ajuster si le montant réduit, ou si le nombre dépasse le budget prévu d'epochs doit être révisé AVANT tout engagement de coût

Au-delà du seul coût monétaire, cette estimation de taille en tokens permet aussi d'anticiper le temps d'entraînement approximatif — une information utile pour planifier un calendrier de projet, indépendamment de la question budgétaire.

Piège courant Lancer un entraînement complet sans avoir estimé au préalable son coût en tokens, en découvrant le montant final seulement après facturation — une estimation, même approximative, prend quelques minutes à calculer et évite des surprises budgétaires qui peuvent être significatives à l'échelle d'un dataset volumineux et de plusieurs epochs.
Exercice Pour un dataset de 5000 exemples avec une moyenne de 300 tokens chacun, entraîné sur 3 epochs, calculez le nombre total de tokens traités pendant l'entraînement.

Ce qu'une documentation de dataset devrait inclure : VERSION ET DATE DE CONSTITUTION Un identifiant de version explicite, similaire au versionnement déjà établi pour les données statiques (rappel cours 18, module 2, leçon 2.2) SOURCES UTILISÉES ET PROPORTIONS Quelle part provient de logs réels (leçon 4.2), de génération synthétique (leçon 4.3), d'annotation manuelle (leçon 4.4) — une traçabilité utile pour diagnostiquer un comportement du modèle final qui semblerait hérité d'une source spécifique STATISTIQUES DE DISTRIBUTION (rappel leçon 7.3) Les proportions par catégorie ou type de tâche, pour que quiconque réutilise ce dataset comprenne sa composition sans devoir la ré-analyser depuis zéro TRANSFORMATIONS APPLIQUÉES Quel nettoyage (module 5), quelle déduplication, quels critères d'exclusion ont été appliqués — pour comprendre ce que le dataset final NE contient PAS, et pourquoi

Cette documentation devient particulièrement précieuse quand un modèle fine-tuné présente un comportement inattendu après déploiement : pouvoir remonter précisément à la version du dataset utilisée, ses sources et ses transformations permet un diagnostic bien plus rapide qu'une reconstitution a posteriori de ces informations, si elles n'ont jamais été consignées.

LEÇON 8.3Étude de cas : construire un dataset pour un agent de support spécialisé

Contexte

Une équipe souhaite fine-tuner un modèle pour qu'il adopte systématiquement le ton et les procédures spécifiques de son service de support client, en complément d'un système existant combinant RAG (cours 9-13) et function calling (cours 17). L'équipe dispose de six mois de logs de conversations réelles (rappel cours 19).

Application de la checklist (leçon 8.1) à ce projet : 1. FORMAT : chat/messages choisi (module 2, leçon 2.2), car le modèle final doit gérer des conversations multi-tours (module 2, leçon 2.3) en production 2. SOURCES : logs réels filtrés pour ne garder que les conversations sans plainte utilisateur (rappel module 4, leçon 4.2, sur la vérification de qualité avant usage), complétés par des exemples synthétiques pour les cas rares insuffisamment représentés dans les logs (module 4, leçon 4.3) 3. NETTOYAGE : suppression des artefacts de copier-coller observés dans certaines réponses d'agents humains présents dans les logs (rappel module 5, leçon 5.1) 4. STRUCTURATION : mélange contrôlé (module 6, leçon 6.5) entre conversations générales et exemples de function calling (module 6, leçon 6.2), avec une proportion volontairement plus élevée de cas de gestion d'erreur que ce qu'on observe naturellement dans les logs 5. VALIDATION : split train/validation/test en veillant à ce qu'une même conversation ne soit jamais scindée entre deux ensembles différents (rappel module 7, leçon 7.1, sur la fuite de données)

Cette étude de cas illustre une décision récurrente dans ce cours : ne pas se contenter de refléter passivement la distribution naturelle des logs (rappel module 4, leçon 4.5, sur la non-représentativité), mais ajuster délibérément certaines proportions — ici, sur-représenter volontairement la gestion d'erreur de function calling — quand cette compétence est jugée particulièrement critique pour l'usage final du modèle.

Piège courant Considérer que reproduire fidèlement la distribution naturelle des logs constitue toujours le choix le plus sûr — dans certains cas, comme celui de cette étude, un ajustement délibéré des proportions vers les compétences les plus critiques produit un modèle mieux préparé que la seule reproduction passive de ce qui a été observé.
