Great Expectations et Pandera en Python — comment transformer des hypothèses implicites sur vos données en contrôles explicites, automatisés et reproductibles, intégrés directement dans vos pipelines. 8 modules, 40 leçons.

MODULE 01 / 08

Fondamentaux de la validation automatisée

Ce cours ouvre le Bloc 7 de la série, consacré à l'outillage et à l'industrialisation des pratiques déjà couvertes dans les blocs précédents. Il traite un sujet transverse à l'ensemble de cette série : comment vérifier automatiquement que des données respectent bien les hypothèses sur lesquelles reposent tous les pipelines déjà construits — RAG (cours 9-13), agents IA (cours 17-19), fine-tuning (cours 20-22).

LEÇON 1.1Pourquoi valider les données automatiquement

Tout au long de cette série, des hypothèses implicites ont soutenu chaque pipeline construit : qu'un champ de date respecte un format donné, qu'un identifiant reste unique, qu'une colonne ne contienne jamais de valeur manquante inattendue. Ces hypothèses, rarement vérifiées explicitement, deviennent une source de défaillance silencieuse dès qu'une source de données évolue sans que personne ne le remarque.

Le problème que la validation automatisée résout : Pipeline construit en supposant IMPLICITEMENT que : - la colonne "email" contient toujours une adresse valide - la colonne "prix" est toujours positive - la colonne "id_client" ne contient jamais de doublon │ ▼ Ces hypothèses ne sont écrites NULLE PART de façon explicite — elles vivent uniquement dans la tête de la personne qui a construit le pipeline, ou dans du code de traitement qui les suppose silencieusement vraies │ ▼ Une source de données change (nouvelle intégration, erreur amont, migration) et VIOLE une de ces hypothèses │ ▼ Sans validation explicite : le pipeline continue de tourner, produit un résultat SILENCIEUSEMENT INCORRECT, découvert parfois bien plus tard, à un coût de diagnostic élevé

Ce risque n'est pas nouveau dans cette série : il rejoint directement le principe de péremption silencieuse déjà établi au cours 18 (module 2, leçon 2.4) et celui des logs débogables du cours 19 — une défaillance qui ne "plante" pas techniquement est souvent bien plus coûteuse à détecter qu'une erreur bruyante. La validation automatisée rend ces hypothèses implicites explicites, vérifiables, et déclenchées systématiquement plutôt que découvertes après coup.

Piège courant Considérer que des tests unitaires sur le CODE d'un pipeline suffisent à garantir sa fiabilité, en oubliant que le code peut être parfaitement correct tout en recevant des DONNÉES qui violent les hypothèses sur lesquelles ce code repose — un problème que seule une validation portant directement sur les données, pas seulement sur la logique de traitement, peut détecter.
Exercice Pour un pipeline que vous avez construit ou étudié dans cette série (RAG, fine-tuning, agent), identifiez une hypothèse implicite sur les données qui, si elle était violée, produirait une défaillance silencieuse plutôt qu'une erreur visible.

LEÇON 1.2Validation manuelle vs automatisée : les limites de l'humain

Rappel indirect du cours 20 (module 4, leçon 4.4, sur la revue manuelle d'échantillon) : une vérification humaine reste précieuse, mais elle a des limites structurelles que ce cours propose de dépasser par l'automatisation — sans pour autant l'éliminer entièrement.

Cette comparaison ne signifie pas que l'automatisation remplace entièrement le jugement humain : rappel du même principe déjà établi au cours 22 (module 6, leçon 6.4, sur la zone grise) — l'automatisation excelle à vérifier des règles explicites et répétables, tandis que le jugement humain reste nécessaire pour des cas ambigus ou pour concevoir les règles elles-mêmes.

Piège courant Opposer validation manuelle et automatisée comme des choix mutuellement exclusifs, alors qu'elles se complètent : l'automatisation vérifie systématiquement des règles explicites à grande échelle, tandis que la revue manuelle reste utile pour concevoir ces règles et traiter les cas qu'aucune règle automatisée ne peut encore capturer.

LEÇON 1.3Où la validation s'insère dans un pipeline de données

Cette leçon situe la validation automatisée dans les pipelines déjà construits tout au long de cette série, en identifiant les points d'insertion les plus pertinents.

Points d'insertion de la validation dans des pipelines déjà couverts par cette série : PIPELINE RAG (cours 9-13) Après extraction et nettoyage (cours 11), AVANT chunking et indexation — vérifier que les documents extraits respectent le format attendu avant de les traiter davantage PIPELINE DE FINE-TUNING (cours 20-22) Après formatage (cours 20), AVANT l'entraînement — vérifier la conformité structurelle du JSONL (rappel cours 20, module 3) de façon systématique et automatisée plutôt qu'avec le script de validation ad hoc déjà illustré PIPELINE DE DONNÉES TEMPS RÉEL (cours 18) À la réception de chaque nouvelle donnée depuis une source externe — vérifier sa conformité avant de la mettre en cache ou de la transmettre à un agent

LEÇON 1.5Erreurs courantes à l'introduction de la validation automatisée

Cette dernière leçon du module recense les erreurs les plus fréquentes lors de la première mise en place d'une validation automatisée, approfondies dans les modules suivants.

Erreur 1 : vouloir tout valider dès le premier jour

Tenter d'écrire un schéma exhaustif couvrant toutes les contraintes imaginables avant même de commencer, plutôt que de démarrer avec quelques règles essentielles et d'itérer — un principe qui rejoint la progressivité déjà recommandée pour d'autres pratiques de cette série.

Erreur 2 : ne pas décider à l'avance ce qui doit se passer en cas d'échec

Mettre en place une validation sans avoir défini le comportement attendu en cas de violation détectée (bloquer le pipeline, alerter, journaliser) — approfondi au module 6, leçon 6.2.

Erreur 3 : figer un schéma sans jamais le faire évoluer

Traiter un schéma de validation comme définitif une fois écrit, sans processus pour le réviser à mesure que les données ou les besoins évoluent — approfondi au module 7.

Erreur 4 : valider sans jamais consulter les résultats

Mettre en place une validation qui s'exécute silencieusement, sans reporting ni suivi dans le temps, rendant l'effort de mise en place largement stérile — approfondi au module 7, leçon 7.4.

Les quatre erreurs à éviter, résumées : 1. TOUT VALIDER DÈS LE DÉPART → Effort disproportionné, démarrage lent 2. ÉCHECS SANS COMPORTEMENT DÉFINI → Validation inutile en pratique 3. SCHÉMA FIGÉ → Dérive entre schéma et réalité 4. RÉSULTATS JAMAIS CONSULTÉS → Effort de mise en place stérile

Les modules suivants traitent chacune de ces erreurs : les modules 2-4 détaillent la conception progressive de schémas avec Pandera et Great Expectations, le module 6 le comportement face aux échecs, et le module 7 l'évolution et le reporting dans le temps.

Piège courant Considérer la mise en place d'une validation automatisée comme un projet ponctuel à finaliser une fois pour toutes, plutôt que comme une pratique continue qui évolue avec le pipeline qu'elle protège — un schéma de validation, comme le code qu'il accompagne, nécessite maintenance et évolution dans la durée.

MODULE 02 / 08

Concepts fondamentaux : schémas et attentes

Avant d'aborder Pandera (module 3) et Great Expectations (module 4), ce module établit un vocabulaire et des concepts communs aux deux outils — indépendants de toute syntaxe spécifique, pour comprendre ce que valider des données signifie concrètement.

LEÇON 2.1Qu'est-ce qu'un schéma de données et une "expectation"

Un schéma de données est une description formelle de ce à quoi des données conformes devraient ressembler — les colonnes attendues, leurs types, leurs contraintes. Une expectation (attente), terminologie propre à Great Expectations mais dont le concept s'applique aussi à Pandera, désigne une règle individuelle et vérifiable au sein de ce schéma.

Relation entre schéma et expectations : SCHÉMA (l'ensemble) ├── EXPECTATION : la colonne "age" doit être un entier ├── EXPECTATION : la colonne "age" doit être comprise entre 0 et 120 ├── EXPECTATION : la colonne "email" doit respecter un format d'email └── EXPECTATION : la colonne "id_client" ne doit jamais être nulle → Un SCHÉMA regroupe plusieurs EXPECTATIONS, chacune vérifiable indépendamment, formant ensemble un CONTRAT complet sur la structure et le contenu attendu des données

Cette notion de contrat rejoint directement un principe déjà esquissé au cours 20 (module 7, leçon 7.5, sur la documentation de dataset) : un schéma de validation formalise explicitement ce qui, jusqu'ici dans cette série, restait souvent implicite dans le code de traitement ou dans la tête de l'équipe qui a construit le pipeline.

Piège courant Confondre un schéma de validation avec un schéma de base de données classique (qui décrit uniquement la structure — types de colonnes) — un schéma de validation, au sens de ce cours, va plus loin en exprimant aussi des contraintes de contenu et de qualité (plages de valeurs, unicité, cohérence), pas seulement la structure technique.
Exercice Pour un jeu de données client (nom, email, âge, date d'inscription), formulez trois expectations distinctes qui, ensemble, constitueraient un début de schéma de validation.

LEÇON 2.2Types de contraintes : type, plage, unicité, nullité

Cette leçon détaille les catégories de contraintes les plus fondamentales, communes à la quasi-totalité des outils de validation, y compris ceux étudiés aux modules 3 et 4.

Les quatre catégories de contraintes les plus courantes : CONTRAINTE DE TYPE La colonne doit contenir des valeurs d'un type précis (entier, texte, date, booléen) CONTRAINTE DE PLAGE La valeur doit se situer dans un intervalle acceptable (un âge entre 0 et 120, un prix toujours positif) CONTRAINTE D'UNICITÉ Une valeur ne doit apparaître qu'une seule fois dans la colonne (un identifiant client, par exemple) CONTRAINTE DE NULLITÉ La colonne peut ou ne peut PAS contenir de valeurs manquantes — une distinction cruciale selon le champ

Ces quatre catégories, bien que basiques, couvrent déjà une part importante des défaillances silencieuses évoquées à la leçon 1.1 : un champ d'identifiant qui devient soudainement non unique, une colonne numérique qui reçoit une valeur textuelle inattendue, ou une contrainte de nullité violée par une source amont modifiée sans préavis.

Piège courant Se limiter aux seules contraintes de type, en négligeant les contraintes de plage, d'unicité et de nullité qui capturent souvent des défaillances bien plus fréquentes en pratique — une colonne "âge" de type entier valide techniquement peut malgré tout contenir la valeur -5 ou 300, deux erreurs qu'une simple vérification de type ne détecterait jamais.
Exercice Pour la colonne "date_inscription" d'un jeu de données client, formulez une contrainte pour chacune des quatre catégories de cette leçon.

LEÇON 2.3Contraintes statistiques et de distribution

Rappel direct du cours 21 (module 3, sur la mesure du biais) : au-delà des contraintes individuelles de la leçon 2.2, un schéma peut aussi exprimer des attentes sur la distribution globale d'une colonne — une extension naturelle des mêmes principes de mesure statistique déjà appliqués à un contexte différent.

Exemples de contraintes statistiques (au-delà d'une seule ligne) : MOYENNE ET ÉCART-TYPE ATTENDUS La moyenne de la colonne "montant_commande" devrait rester dans une plage cohérente avec l'historique connu — un écart soudain peut signaler un problème de source, pas seulement une évolution légitime du comportement métier PROPORTION DE VALEURS MANQUANTES ACCEPTABLE Rappel cours 20, module 6, leçon 6.4 (sur le déséquilibre de label) — une proportion de valeurs nulles qui dépasse un seuil habituel peut signaler une dégradation de la source de collecte DISTRIBUTION DE CATÉGORIES ATTENDUE Rappel direct cours 21, module 3, leçon 3.1 (entropie de distribution) — le même principe appliqué ici à la validation continue d'un pipeline de données, pas seulement à l'analyse ponctuelle d'un dataset

Ce type de contrainte est plus délicat à définir que les contraintes individuelles de la leçon 2.2 : une valeur peut être individuellement valide (dans la bonne plage, du bon type) tout en participant à une distribution globale anormale — un problème qui ne devient visible qu'en observant l'ensemble de la colonne, pas une seule ligne isolément.

Piège courant Se limiter à des contraintes ligne par ligne (leçon 2.2) sans jamais vérifier de contraintes statistiques sur l'ensemble d'une colonne — un déséquilibre de distribution (rappel cours 21) peut passer complètement inaperçu si chaque valeur individuelle reste, prise isolément, parfaitement valide.
Exercice Pour une colonne "pays_livraison" dans un système e-commerce, quelle contrainte de distribution pourrait signaler un problème si elle était soudainement violée (par exemple, un seul pays représentant 99% des commandes) ?

LEÇON 2.4Contraintes relationnelles entre colonnes

Certaines contraintes ne peuvent pas être vérifiées en examinant une seule colonne isolément : elles portent sur la relation entre plusieurs colonnes d'un même jeu de données — un niveau de validation plus sophistiqué que les contraintes des leçons précédentes.

Exemples de contraintes relationnelles : COHÉRENCE TEMPORELLE La colonne "date_livraison" doit toujours être POSTÉRIEURE à la colonne "date_commande" — une contrainte qui ne peut être vérifiée qu'en comparant les deux colonnes ensemble COHÉRENCE CONDITIONNELLE Si la colonne "statut" vaut "remboursé", alors la colonne "montant_rembourse" ne devrait jamais être nulle ni égale à zéro — une règle qui dépend de la valeur d'une AUTRE colonne COHÉRENCE D'AGRÉGATION La somme des lignes de détail d'une commande devrait correspondre au total enregistré dans une table récapitulative — une contrainte qui porte sur une relation entre plusieurs ENREGISTREMENTS, pas seulement plusieurs colonnes d'une même ligne

Ces contraintes relationnelles sont souvent les plus révélatrices de bugs subtils dans un pipeline de données : chaque colonne prise isolément peut être parfaitement valide selon les critères des leçons 2.2-2.3, tout en violant une cohérence logique entre elles — un exemple concret et fréquent d'un problème de qualité invisible sans une vérification spécifiquement relationnelle.

Piège courant Concevoir un schéma de validation qui ne couvre que des contraintes colonne par colonne, en négligeant les contraintes relationnelles qui capturent souvent les incohérences les plus significatives d'un point de vue métier — une date de livraison antérieure à sa date de commande est un signal d'alerte bien plus clair qu'une simple valeur hors plage.
Exercice Pour un jeu de données de commandes e-commerce (colonnes : statut, montant_total, montant_rembourse), formulez une contrainte relationnelle entre ces trois colonnes.

LEÇON 2.5Documenter un schéma comme un contrat de données

Cette dernière leçon du module introduit la notion de data contract (contrat de données), approfondie au module 7 : un schéma de validation, correctement documenté, ne sert pas seulement à détecter des erreurs — il devient une référence explicite et partagée sur ce que des données conformes signifient pour une équipe.

Ce qu'un schéma bien documenté apporte, au-delà de la simple détection technique d'erreurs : COMMUNICATION ENTRE ÉQUIPES Une équipe qui produit des données et une équipe qui les consomme peuvent se référer au MÊME schéma explicite, plutôt qu'à des hypothèses informelles et potentiellement divergentes ONBOARDING FACILITÉ Une nouvelle personne rejoignant un projet peut consulter le schéma pour comprendre rapidement ce qu'une donnée "valide" signifie dans ce contexte précis, plutôt que de devoir déduire ces règles du code de traitement existant RÉFÉRENCE EN CAS DE LITIGE Si une équipe consommatrice de données rencontre un problème, le schéma sert de référence objective pour déterminer si la donnée reçue respectait ou non le contrat convenu

Cette notion de contrat rejoint directement le principe de documentation déjà établi tout au long du Bloc 6 (cours 20-22) : un schéma de validation n'est pas seulement un artefact technique, mais un document de référence partagé, qui gagne à être versionné et documenté avec le même sérieux que le code lui-même — un thème approfondi au module 7 de ce cours.

Ce module clôt la partie "concepts fondamentaux" du cours. Les modules suivants appliquent concrètement ces concepts avec deux outils Python : Pandera (module 3) puis Great Expectations (module 4), avant de les comparer au module 5.
Piège courant Considérer un schéma de validation comme un simple artefact technique interne, sans le documenter ni le partager comme un contrat explicite entre les équipes qui produisent et celles qui consomment les données — cette omission prive le schéma d'une grande partie de sa valeur organisationnelle, au-delà de sa seule fonction de détection technique.

MODULE 03 / 08

Pandera en profondeur

Ce module applique concrètement les concepts du module 2 avec Pandera, une bibliothèque Python qui exprime les schémas de validation directement en code, dans un style proche de pandas — le premier des deux outils principaux de ce cours.

LEÇON 3.1Premiers pas avec Pandera : DataFrameSchema

Pandera exprime un schéma de validation (rappel module 2, leçon 2.1) sous la forme d'un objet DataFrameSchema, listant les colonnes attendues et leurs contraintes — une syntaxe qui rappelle directement la définition d'un DataFrame pandas, ce qui facilite son adoption pour quiconque connaît déjà cet écosystème.

import pandera as pa
from pandera import Column, Check

schema_clients = pa.DataFrameSchema({
    "id_client": Column(int, unique=True, nullable=False),
    "age": Column(int, Check.in_range(0, 120)),
    "email": Column(str, Check.str_matches(r"^[\w.+-]+@[\w-]+\.[a-z]{2,}$")),
})

# Valider un DataFrame existant
df_valide = schema_clients.validate(df_clients)
Correspondance directe avec les concepts du module 2 : Column(int, unique=True, nullable=False) → Rappel module 2, leçon 2.2 : contrainte de TYPE (int), d'UNICITÉ (unique=True), de NULLITÉ (nullable=False) Check.in_range(0, 120) → Rappel module 2, leçon 2.2 : contrainte de PLAGE Check.str_matches(...) → Une contrainte de FORMAT, exprimée via une expression régulière — un type de contrainte supplémentaire au-delà des quatre catégories de base du module 2

L'appel schema_clients.validate(df_clients) lève une exception si une contrainte est violée, interrompant l'exécution du programme — un comportement à la fois pratique pour un script simple et potentiellement problématique pour un pipeline en production, un compromis approfondi au module 6, leçon 6.2.

Piège courant Définir un schéma Pandera qui ne couvre que les colonnes jugées les plus importantes, en laissant les autres colonnes du DataFrame totalement non vérifiées — par défaut, Pandera ignore les colonnes non déclarées dans le schéma, ce qui peut laisser passer des problèmes sur des colonnes qu'on pensait implicitement couvertes.
Exercice Pour le schéma ci-dessus, ajoutez une colonne "date_inscription" avec une contrainte de type approprié pour une date.

LEÇON 3.2Valider des colonnes : types, contraintes, checks personnalisés

Au-delà des contraintes prédéfinies de la leçon 3.1, Pandera permet de définir des checks personnalisés — des fonctions Python arbitraires exprimant une logique de validation propre à un projet, y compris des contraintes relationnelles entre colonnes (rappel module 2, leçon 2.4).

def date_livraison_apres_commande(df) -> bool:
    """Rappel module 2, leçon 2.4 — contrainte RELATIONNELLE
    entre deux colonnes, exprimée ici comme un check Pandera
    appliqué à l'ensemble du DataFrame plutôt qu'à une seule
    colonne isolément."""
    return (df["date_livraison"] >= df["date_commande"]).all()

schema_commandes = pa.DataFrameSchema(
    {
        "date_commande": Column("datetime64[ns]"),
        "date_livraison": Column("datetime64[ns]"),
        "montant": Column(float, Check.greater_than(0)),
    },
    checks=Check(date_livraison_apres_commande, error="livraison avant commande"),
)

MODULE 04 / 08

Great Expectations en profondeur

Ce module explore Great Expectations, un outil de philosophie différente de Pandera : plutôt que des schémas définis en code Python pur, une plateforme complète organisée autour de suites d'attentes, d'un contexte de données centralisé, et d'une documentation générée automatiquement.

LEÇON 4.1Concepts clés : Expectation, Suite, Data Context, Checkpoint

Great Expectations organise la validation autour de plusieurs concepts structurants, plus riches que la simple structure de schéma déjà vue avec Pandera (module 3).

Les quatre concepts clés de Great Expectations : EXPECTATION Une règle individuelle vérifiable (rappel module 2, leçon 2.1) — par exemple "expect_column_values_to_be_between" SUITE (Expectation Suite) Un ENSEMBLE nommé d'expectations, l'équivalent d'un schéma complet (rappel module 2, leçon 2.1), mais avec un nom et une identité propres, réutilisable à travers plusieurs jeux de données DATA CONTEXT Le point d'entrée central du projet — configure où sont stockées les suites, les résultats de validation, et la documentation générée (approfondi leçon 4.4) CHECKPOINT Un objet qui associe une SUITE à des DONNÉES précises et définit comment exécuter la validation (quand, avec quelles actions en cas d'échec — approfondi module 6, leçon 6.2)

Cette architecture, plus élaborée que celle de Pandera, reflète une philosophie différente : Great Expectations est conçu comme une plateforme complète de gouvernance de la qualité des données, pas seulement comme une bibliothèque de validation ponctuelle — un compromis entre richesse fonctionnelle et complexité d'adoption, approfondi au module 5.

Piège courant Aborder Great Expectations en cherchant l'équivalent direct d'un simple schéma Pandera, sans comprendre que son architecture (Data Context, Checkpoint) est pensée pour une utilisation en plateforme complète, pas seulement pour une validation ponctuelle en quelques lignes de code — une attente qui peut rendre la prise en main initiale plus déroutante que prévu.

LEÇON 6.1Valider en entrée (ingestion) vs en sortie

Rappel direct de la leçon 1.3 (module 1) : la validation peut se positionner à différents points d'un pipeline, avec des implications différentes selon qu'elle intervient à l'ingestion (avant tout traitement) ou en sortie (juste avant la consommation par un système en aval).

VALIDATION EN ENTRÉE (à l'ingestion) VALIDATION EN SORTIE (avant ──────────────────────────────── consommation en aval) Détecte les problèmes AU PLUS TÔT, ──────────────────────────────── avant qu'ils ne se propagent dans Vérifie que le TRAITEMENT tout le pipeline de traitement lui-même n'a pas introduit de problème (rappel principe Protège contre des données EXTERNES déjà établi au cours 21, déjà défaillantes à la source module 5, leçon 5.4, sur la vérification après correction) Ne peut PAS détecter un bug introduit PENDANT le traitement lui-même Détecte les bugs de TRANSFORMATION, pas ceux déjà présents dans la source brute

Ces deux positions ne sont pas mutuellement exclusives : rappel du principe déjà établi au cours 20 (module 1, leçon 1.4, sur le pipeline complet), une validation robuste s'applique généralement aux DEUX frontières — à l'entrée pour se protéger des données externes défaillantes, et en sortie pour vérifier que le traitement lui-même n'a rien cassé, complétant ainsi la couverture de bout en bout du pipeline.

Piège courant Valider uniquement à l'entrée d'un pipeline, en supposant que des données valides en entrée garantissent automatiquement un résultat valide en sortie — un bug dans la logique de transformation elle-même peut corrompre des données pourtant parfaitement valides à l'origine, un problème que seule une validation en sortie peut détecter.

Positionnement de la validation dans un DAG orchestré (graphe de tâches) : TÂCHE 1 : Extraction des données brutes │ ▼ TÂCHE 2 : VALIDATION EN ENTRÉE (rappel leçon 6.1) → Si échec BLOQUANT (rappel leçon 6.2) : le DAG s'arrête ici, les tâches suivantes ne s'exécutent PAS │ ▼ (seulement si validation réussie) TÂCHE 3 : Transformation des données │ ▼ TÂCHE 4 : VALIDATION EN SORTIE (rappel leçon 6.1) │ ▼ (seulement si validation réussie) TÂCHE 5 : Chargement vers la destination finale

Piège courant Intégrer une tâche de validation dans un orchestrateur sans configurer explicitement la dépendance entre cette tâche et les suivantes — sans cette dépendance, un échec de validation pourrait être enregistré sans empêcher l'exécution des tâches en aval, annulant l'intérêt principal de bloquer le pipeline en cas de problème critique.

LEÇON 7.1Versionner un schéma de validation

Rappel direct du cours 20 (module 7, leçon 7.5) et du cours 21 (module 7, leçon 7.5) : les schémas de validation, tout comme les datasets déjà couverts dans cette série, méritent un versionnement explicite — un schéma modifié sans traçabilité rend impossible de comprendre après coup pourquoi une validation se comportait différemment à un moment donné.

SCHEMA_VERSION = "2.1.0"

    {

LEÇON 7.2Faire évoluer un schéma sans casser les pipelines existants

Cette leçon traite un défi spécifique à la gouvernance de schémas : comment modifier une contrainte sans provoquer une cascade d'échecs de validation dans des pipelines en aval qui dépendent de l'ancien comportement — un problème de compatibilité ascendante à part entière.

Deux types de changements de schéma, aux implications différentes : CHANGEMENT COMPATIBLE (non cassant) CHANGEMENT INCOMPATIBLE (cassant) ──────────────────────────────── ──────────────────────────────── Ajouter une colonne OPTIONNELLE Rendre une contrainte PLUS (rappel exemple leçon 7.1, STRICTE (réduire une plage "code_pays" avec required=False) acceptée, par exemple) Assouplir une contrainte existante Supprimer une colonne encore (élargir une plage acceptée) utilisée en aval Ajouter une nouvelle expectation Renommer une colonne sans INFORMATIVE (alerte, pas blocage — période de transition rappel module 6, leçon 6.2)

Pour un changement incompatible, une pratique recommandée consiste à introduire une période de transition : faire coexister l'ancienne et la nouvelle contrainte, avec l'ancienne en mode "alerte" plutôt que "blocage" (rappel module 6, leçon 6.2) pendant une durée suffisante pour que les équipes consommatrices adaptent leurs propres traitements avant que la contrainte ne devienne réellement bloquante.

Piège courant Introduire un changement de schéma incompatible directement en mode bloquant, sans période de transition ni communication préalable aux équipes consommatrices — un tel changement peut interrompre brutalement des pipelines en aval qui n'avaient aucun moyen d'anticiper cette modification.

LEÇON 7.3Tester ses propres schémas de validation

Un schéma de validation est lui-même du code, sujet à ses propres erreurs — cette leçon traite comment le tester, un sujet qui rejoint directement les pratiques de test approfondies au cours 24 de ce même bloc (pipelines de transformation reproductibles et tests).

def test_schema_rejette_age_negatif():
    """Un schéma de validation mérite ses PROPRES tests,
    vérifiant qu'il accepte bien les cas valides ET rejette
    bien les cas invalides qu'il est censé détecter."""
    df_invalide = pd.DataFrame({"id_client": [1], "age": [-5], "email": ["a@b.com"]})
    with pytest.raises(pa.errors.SchemaError):
        schema_clients.validate(df_invalide)

def test_schema_accepte_donnees_valides():
    df_valide = pd.DataFrame({"id_client": [1], "age": [30], "email": ["a@b.com"]})
    resultat = schema_clients.validate(df_valide)
    assert resultat is not None
Pourquoi tester un schéma de validation lui-même : Un schéma trop PERMISSIF (une contrainte mal écrite qui n'attrape pas réellement les cas invalides visés) donne une FAUSSE CONFIANCE — la validation "passe" sans réellement protéger contre le problème qu'elle était censée détecter Un schéma trop STRICT (une contrainte mal calibrée qui rejette des cas en réalité valides) bloque inutilement un pipeline légitime — rappel du même risque déjà évoqué au cours 22, module 6, leçon 6.4, sur la sur-correction

Ces deux types de tests — vérifier qu'un cas invalide est bien rejeté, ET qu'un cas valide est bien accepté — sont tous deux nécessaires : un schéma qui ne serait testé que sur des cas valides pourrait dissimuler une contrainte défaillante qui n'attrape en réalité aucun problème, un risque similaire à celui déjà évoqué pour la calibration du LLM-as-judge au cours 22 (module 5, leçon 5.4).

Piège courant Ne tester un schéma de validation que sur des données valides, en vérifiant seulement qu'il ne bloque pas les cas légitimes, sans jamais vérifier qu'il détecte réellement les cas invalides qu'il est censé attraper — un schéma qui ne fait qu'accepter tout sans jamais rejeter n'apporte aucune protection réelle, malgré une apparence de validation en place.

LEÇON 7.4Reporting et suivi dans le temps des échecs de validation

Rappel direct du cours 19 (module 6, sur les métriques et signaux d'amélioration) : au-delà de la réaction immédiate à un échec (module 6, leçon 6.2), un suivi agrégé des échecs de validation dans le temps révèle des tendances qu'une vue ponctuelle ne peut pas capturer.

def calculer_tendance_echecs(historique_validations: list[dict]) -> dict:
    """Rappel cours 19, module 6, leçon 6.1 — même principe
    d'agrégation de métriques dans le temps, appliqué ici aux
    résultats de validation de données plutôt qu'aux traces
    d'agent IA."""
    par_semaine = defaultdict(lambda: {"total": 0, "echecs": 0})
    for validation in historique_validations:
        semaine = validation["horodatage"].isocalendar()[1]
        par_semaine[semaine]["total"] += 1
        if not validation["succes"]:
            par_semaine[semaine]["echecs"] += 1
    return {s: v["echecs"] / v["total"] for s, v in par_semaine.items()}
Ce qu'un suivi de tendance dans le temps permet de détecter, que la vue ponctuelle d'un seul échec ne révèle pas : Une DÉGRADATION PROGRESSIVE d'une source de données — un taux d'échec qui augmente lentement semaine après semaine, signalant un problème qui s'aggrave plutôt qu'un incident isolé (rappel du même principe de détection précoce déjà établi au cours 25, à venir dans ce même bloc, sur le monitoring de la dégradation de qualité) Une CONTRAINTE MAL CALIBRÉE qui échoue systématiquement à un taux non négligeable, signalant un problème dans le SCHÉMA lui-même plutôt que dans les données (rappel leçon 7.3, sur les tests de schéma)

Ce suivi de tendance prépare directement le sujet du cours 25 de ce même bloc, consacré au monitoring de la dégradation de qualité des sources de données dans le temps — un prolongement naturel du reporting de validation déjà entamé ici, à une échelle et avec une sophistication plus poussées.

Piège courant Se contenter d'une réaction immédiate à chaque échec de validation individuel (rappel module 6, leçon 6.2) sans jamais agréger ces échecs dans le temps pour détecter des tendances — une dégradation progressive et silencieuse peut passer inaperçue si chaque échec est traité isolément, sans vue d'ensemble sur son évolution.

LEÇON 8.3Étude de cas : valider un pipeline d'ingestion pour un système RAG

Contexte

Reprenant le pipeline RAG déjà construit aux cours 9-13 : une équipe souhaite ajouter une validation automatisée à l'étape d'ingestion de documents, avant leur nettoyage (cours 11) et leur chunking (cours 9), pour détecter les problèmes de source avant qu'ils ne se propagent dans l'ensemble du pipeline.

Application du pipeline de ce cours à ce contexte RAG : CHOIX D'OUTIL (module 5) : Pandera, choisi pour sa légèreté d'intégration dans le code Python existant du pipeline d'ingestion, sans besoin de Data Docs partagées à ce stade SCHÉMA DÉFINI (modules 2-3) : - "identifiant_document" : unique, non nul - "contenu_texte" : non nul, longueur minimale de 50 caractères (rappel cours 20, module 5, leçon 5.2, sur la détection de contenu tronqué) - "date_extraction" : type date valide - Contrainte relationnelle (rappel module 2, leçon 2.4) : la date d'extraction ne doit jamais être future POSITIONNEMENT (module 6, leçon 6.1) : validation en ENTRÉE, juste après l'extraction brute (cours 11, 14, 15) et AVANT le chunking (cours 9), pour éviter de traiter des documents déjà invalides STRATÉGIE DE RÉACTION (module 6, leçon 6.2) : blocage pour l'unicité et la nullité (critiques), alerte pour la longueur minimale (peut légitimement varier selon le type de document)

Cette étude de cas illustre comment ce cours 23 s'articule avec les blocs précédents de la série : la validation ne remplace pas les techniques de nettoyage déjà couvertes (cours 11, 14-15), elle les complète en formalisant explicitement les hypothèses que ces techniques de nettoyage supposaient jusqu'ici implicitement.

Piège courant Ajouter une validation à un pipeline RAG déjà en production sans d'abord exécuter cette validation en mode "alerte seulement" (rappel module 6, leçon 6.2) sur les données existantes, pour vérifier qu'elle ne bloquerait pas à tort des documents légitimes déjà intégrés avec succès dans le système.
