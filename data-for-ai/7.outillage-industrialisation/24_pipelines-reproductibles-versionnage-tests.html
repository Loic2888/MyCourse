Pipelines de Transformation Reproductibles

Versionnage et tests — comment garantir qu'un pipeline de données produit toujours le même résultat à partir des mêmes entrées, et détecter automatiquement toute régression avant qu'elle n'atteigne la production. 8 modules, 40 leçons.

MODULE 01 / 08

Fondamentaux de la reproductibilité

Ce cours poursuit le Bloc 7 de la série, entamé au cours 23 sur la validation automatisée. Il traite un problème complémentaire : même un pipeline dont les données sont valides à chaque étape (cours 23) peut échouer à produire le même résultat d'une exécution à l'autre — un problème de reproductibilité, distinct de celui de la validité.

LEÇON 1.1Qu'est-ce qu'un pipeline reproductible et pourquoi ça compte

Un pipeline de transformation de données est reproductible s'il produit exactement le même résultat lorsqu'il est exécuté à nouveau avec les mêmes données d'entrée et la même version du code — une propriété qui semble évidente en théorie, mais qui échoue fréquemment en pratique pour des raisons subtiles, approfondies au module 4.

Ce que la reproductibilité permet concrètement : DIAGNOSTIC D'UN PROBLÈME PASSÉ Rejouer exactement le pipeline tel qu'il s'exécutait à un moment donné, pour comprendre pourquoi un résultat particulier a été produit — rappel du même besoin déjà établi au cours 19 (logs et traces) mais appliqué ici au pipeline de transformation lui-même, pas seulement à un agent VALIDATION D'UNE MODIFICATION Vérifier qu'un changement de code produit bien le résultat attendu, en comparant à une exécution de référence connue (approfondi au module 6, sur les tests de non-régression) COLLABORATION FIABLE ENTRE PERSONNES Une collègue qui exécute le même pipeline sur sa propre machine devrait obtenir EXACTEMENT le même résultat qu'une autre personne l'ayant exécuté ailleurs — sans cette garantie, toute divergence de résultat devient une source de confusion et de perte de temps à diagnostiquer

Ce sujet complète directement celui du cours 23 : la validation (cours 23) vérifie que les données respectent des contraintes à un instant donné, tandis que la reproductibilité (ce cours) vérifie que le même processus de transformation, appliqué aux mêmes données, produit toujours le même résultat — deux propriétés indépendantes, un pipeline pouvant satisfaire l'une sans l'autre.

Piège courant Supposer qu'un pipeline dont chaque étape produit des données valides (rappel cours 23) est nécessairement reproductible — la validité des données à un instant donné ne garantit en rien qu'une exécution ultérieure du même pipeline, avec les mêmes entrées, produira exactement le même résultat.
Exercice Décrivez une situation où un pipeline de données que vous avez utilisé ou observé a produit un résultat différent lors de deux exécutions successives, alors que rien n'avait, en apparence, changé entre les deux.

LEÇON 1.2Les sources de non-reproductibilité

Cette leçon recense les catégories principales de causes qui rendent un pipeline non reproductible, en s'appuyant sur des exemples déjà rencontrés dans les blocs précédents de cette série — chacune approfondie individuellement au module 4.

Catégories de non-reproductibilité, avec des exemples déjà rencontrés dans cette série : CODE NON VERSIONNÉ OU MAL VERSIONNÉ (approfondi module 2) Une modification du code de transformation appliquée sans trace, rendant impossible de savoir quelle version exacte a produit un résultat donné DONNÉES SOURCES QUI CHANGENT SANS VERSIONNEMENT (approfondi module 3) — rappel cours 18, sur la fraîcheur des données : une source qui évolue entre deux exécutions du même pipeline change nécessairement le résultat, sans que le CODE lui-même n'ait changé ALÉATOIRE NON CONTRÔLÉ (approfondi module 4, leçon 4.2) — rappel cours 20, module 7, sur le split train/test : un tirage aléatoire non figé produit un résultat différent à chaque exécution DÉPENDANCE AU TEMPS OU À L'ENVIRONNEMENT D'EXÉCUTION (approfondi module 4, leçon 4.3) — un pipeline qui utilise la date du jour, ou qui se comporte différemment selon la machine sur laquelle il s'exécute

Cette taxonomie prépare directement la structure du reste de ce cours : le module 2 traite le versionnement de code, le module 3 le versionnement de données, et le module 4 les sources de non-déterminisme au sens strict (aléatoire, temps, environnement) — trois dimensions distinctes qui, ensemble, couvrent la quasi-totalité des causes de non-reproductibilité rencontrées en pratique.

Piège courant Attribuer systématiquement un résultat différent entre deux exécutions à un "bug" du code de transformation, sans envisager que la cause pourrait résider ailleurs — dans les données sources elles-mêmes (module 3) ou dans une source d'aléatoire non maîtrisée (module 4) plutôt que dans une erreur de logique de traitement.

LEÇON 1.5Erreurs courantes de conception

Cette dernière leçon du module recense les erreurs les plus fréquentes lors de la conception d'un pipeline visant la reproductibilité, approfondies individuellement dans les modules suivants.

Erreur 1 : versionner le code sans versionner les données

Suivre rigoureusement les modifications du code de transformation (rappel module 2) tout en laissant les données sources totalement non versionnées — une reproductibilité partielle qui échoue dès que la source de données change, approfondi au module 3.

Erreur 2 : ignorer les sources d'aléatoire dans le pipeline

Ne pas fixer les graines aléatoires (seeds) utilisées à différentes étapes du pipeline, produisant un résultat légèrement différent à chaque exécution malgré des entrées identiques — approfondi au module 4, leçon 4.2.

Erreur 3 : ne tester le pipeline qu'une seule fois manuellement

Vérifier une seule fois que le pipeline fonctionne correctement, sans mettre en place de tests automatisés qui détecteraient une régression future — approfondi aux modules 5-7.

Erreur 4 : ne jamais rejouer un pipeline pour vérifier sa reproductibilité réelle

Supposer qu'un pipeline est reproductible sans jamais le vérifier empiriquement en le rejouant et en comparant les résultats — approfondi au module 4, leçon 4.5.

Les quatre erreurs à éviter, résumées : 1. CODE VERSIONNÉ, DONNÉES NON VERSIONNÉES → Reproductibilité partielle 2. ALÉATOIRE NON CONTRÔLÉ → Résultat variable à chaque exécution 3. TESTS MANUELS UNIQUEMENT → Régressions futures non détectées 4. REPRODUCTIBILITÉ JAMAIS VÉRIFIÉE → Confiance non fondée

Les modules suivants traitent chacune de ces erreurs : les modules 2-3 détaillent le versionnement de code et de données, le module 4 la gestion du déterminisme, et les modules 5-7 la mise en place de tests automatisés et de leur intégration continue.

Piège courant Considérer la reproductibilité comme une propriété binaire acquise une fois pour toutes après un effort initial, plutôt que comme une discipline continue à maintenir à mesure que le pipeline évolue — un pipeline reproductible aujourd'hui peut cesser de l'être après une modification anodine en apparence, sans les garde-fous appropriés (modules 5-7).
Exercice de synthèse Pour clore ce module : parmi les quatre erreurs listées, laquelle vous semble la plus probable dans un projet que vous avez connu ou pourriez rencontrer — et pourquoi ?
MODULE 02 / 08

Versionner le code de transformation

Ce module traite la première des trois grandes catégories de non-reproductibilité identifiées au module 1 : un code de transformation mal versionné ou mal structuré. Ces principes reprennent des pratiques d'ingénierie logicielle classiques, appliquées spécifiquement au contexte des pipelines de données.

LEÇON 2.1Rappel des bases : Git pour le code de pipeline

Le contrôle de version (Git) constitue le socle minimal de toute reproductibilité de code : chaque modification du pipeline de transformation devrait être tracée, avec la possibilité de revenir à n'importe quelle version antérieure et de savoir exactement quel changement a produit quel résultat.

Ce que le versionnement de code apporte spécifiquement à un pipeline de transformation de données : TRAÇABILITÉ DES MODIFICATIONS Chaque changement de logique de transformation (rappel cours 11, sur le nettoyage de texte ; cours 9, sur le chunking) est associé à un commit identifiable, avec un message expliquant le POURQUOI du changement CAPACITÉ À REVENIR EN ARRIÈRE Si une modification récente du pipeline produit un résultat inattendu, revenir à la version précédente devient une opération immédiate plutôt qu'une reconstruction manuelle CORRÉLATION AVEC LES RÉSULTATS PRODUITS Rappel du principe déjà établi au cours 20 (module 7, leçon 7.5) pour les datasets — associer un résultat produit à la version EXACTE du code qui l'a généré, pas seulement à une date approximative

Ce principe, bien que basique, est souvent négligé spécifiquement pour le code de transformation de données — en particulier dans des environnements de notebooks exploratoires (rappel des pratiques du Bloc 1 de cette série) où le versionnement rigoureux est moins naturel que dans un projet logiciel structuré dès le départ.

Piège courant Développer un pipeline de transformation de données dans des notebooks non versionnés ou versionnés de façon incohérente (cellules exécutées dans un ordre non reproductible), une pratique courante lors de l'exploration initiale mais qui devient un risque significatif dès que ce même code alimente un pipeline en production.
Exercice Pour un pipeline que vous avez développé ou observé, le code de transformation était-il versionné avec la même rigueur que le reste du projet logiciel, ou traité comme un artefact secondaire moins surveillé ?

LEÇON 2.2Structurer un pipeline versionnable et modulaire

Au-delà du simple fait de versionner le code, sa structure influence directement sa reproductibilité et sa testabilité (approfondie au module 5) : un pipeline découpé en fonctions modulaires et bien nommées se prête bien mieux au versionnement granulaire et aux tests qu'un script monolithique.

# MOINS REPRODUCTIBLE : un script monolithique qui mélange
# extraction, nettoyage et chunking en une seule fonction
def traiter_documents_v1(chemin_dossier):
    # 200 lignes mélangeant extraction, nettoyage, chunking...
    pass

# PLUS REPRODUCTIBLE : des fonctions modulaires, chacune
# responsable d'une seule étape, testable indépendamment
# (rappel module 5, sur les tests unitaires)
def extraire_documents(chemin_dossier) -> list[str]:
    ...

def nettoyer_texte(documents: list[str]) -> list[str]:
    ...

def decouper_en_chunks(documents_nettoyes: list[str]) -> list[dict]:
    ...

def pipeline_complet(chemin_dossier) -> list[dict]:
    documents = extraire_documents(chemin_dossier)
    documents_nettoyes = nettoyer_texte(documents)
    return decouper_en_chunks(documents_nettoyes)
Pourquoi la modularité sert directement la reproductibilité : Un CHANGEMENT dans la logique de nettoyage (rappel cours 11) peut être versionné et RETRACÉ indépendamment du reste du pipeline — un commit qui modifie UNIQUEMENT "nettoyer_texte" indique clairement la portée exacte du changement Chaque fonction peut être TESTÉE et REJOUÉE isolément (approfondi module 5, leçon 5.2), plutôt que de nécessiter l'exécution complète du pipeline pour vérifier un seul aspect

Cette structuration modulaire rejoint directement le principe déjà établi dans plusieurs cours de cette série (par exemple, cours 17, module 3, leçon 3.4, sur la simplicité vs expressivité des fonctions) : diviser une logique complexe en composants spécifiques et bien délimités facilite non seulement la compréhension, mais aussi la traçabilité et la vérification indépendante de chaque partie.

Piège courant Écrire un pipeline de transformation comme un script long et monolithique, où chaque modification touche potentiellement l'ensemble du fichier — cette structure rend le versionnement moins granulaire (un commit modifie souvent bien plus que ce qui était réellement visé) et complique fortement les tests isolés de chaque étape.
Exercice Pour le pipeline RAG déjà construit aux cours 9-13, identifiez trois fonctions modulaires distinctes qui pourraient structurer ce pipeline selon le principe de cette leçon.

LEÇON 2.3Gérer les dépendances et les environnements

Une source fréquente et souvent négligée de non-reproductibilité : deux exécutions du même code, sur deux machines différentes, utilisant des versions différentes des bibliothèques Python sous-jacentes (pandas, un tokenizer, un modèle d'embeddings) peuvent produire des résultats légèrement différents, malgré un code source identique.

# requirements.txt SANS versions figées — DANGEREUX pour
# la reproductibilité, chaque installation peut récupérer
# une version différente des bibliothèques
pandas
transformers

# requirements.txt AVEC versions figées (lockfile) — chaque
# installation récupère EXACTEMENT les mêmes versions
pandas==2.1.4
transformers==4.36.2
Pourquoi les versions de bibliothèques affectent la reproductibilité, avec un exemple direct de cette série : Rappel cours 10 (embeddings) : deux versions différentes d'une bibliothèque de calcul d'embeddings peuvent produire des vecteurs LÉGÈREMENT DIFFÉRENTS pour un même texte — un changement invisible au niveau du CODE, mais qui modifie le résultat final du pipeline RAG (recherche vectorielle, cours 13) de façon subtile → Un "lockfile" (versions exactement figées) élimine cette source de variation entre deux installations distinctes du même projet, sur des machines différentes ou à des moments différents

Ce problème rejoint directement un principe déjà esquissé implicitement au cours 20 (module 7, leçon 7.5, sur la documentation de dataset) : documenter et figer non seulement le code et les données, mais aussi l'environnement d'exécution complet — une dimension de reproductibilité souvent oubliée car invisible tant qu'aucun problème ne se manifeste.

Piège courant Spécifier les dépendances d'un projet sans figer leurs versions exactes (un simple "pandas" plutôt que "pandas==2.1.4"), en supposant que cela n'affecte pas les résultats produits — certaines mises à jour de bibliothèques, en particulier pour des modèles d'embeddings ou de NLP, peuvent modifier subtilement le comportement numérique sans que le code appelant n'ait changé.
Exercice Pour un pipeline utilisant une bibliothèque de calcul d'embeddings (rappel cours 10), pourquoi une mise à jour mineure de cette bibliothèque pourrait-elle produire des résultats de recherche vectorielle (cours 13) légèrement différents, malgré un code de pipeline inchangé ?

Piège courant Coder en dur des valeurs de configuration (tailles de chunks, seuils, chemins de fichiers) directement dans la logique de transformation, plutôt que de les exposer comme des paramètres explicites — cette pratique complique la traçabilité de quelle configuration exacte a produit un résultat donné, et rend plus difficile de faire varier ces valeurs pour des tests (module 5).

LEÇON 2.5Pièges courants de versionnage de code

Cette dernière leçon du module recense des pièges spécifiques au versionnement de code de pipeline, en complément des principes déjà établis.

Piège 1 : commits trop larges et peu descriptifs

Regrouper plusieurs changements sans rapport dans un même commit avec un message vague ("mise à jour du pipeline") rend difficile de comprendre après coup quel changement précis a affecté quel comportement du pipeline.

Piège 2 : ne pas versionner les fichiers de configuration

Rappel de la leçon 2.4 : versionner rigoureusement le code tout en laissant les fichiers de configuration ou de paramètres hors du contrôle de version, recréant une source de non-traçabilité que la paramétrisation explicite était censée éliminer.

Piège 3 : environnements de développement non reproductibles entre membres d'une équipe

Rappel de la leçon 2.3 : chaque membre d'une équipe installant les dépendances à des moments différents, sans lockfile partagé, peut se retrouver avec des versions divergentes qui produisent des résultats subtilement différents d'une machine à l'autre.

Ce module clôt la partie "versionnement du code" du cours. Le module suivant traite la seconde catégorie de non-reproductibilité déjà identifiée au module 1 : les données elles-mêmes, qui nécessitent une discipline de versionnement distincte du code.
Piège courant Considérer que le versionnement du code seul (Git) suffit à garantir la reproductibilité complète d'un pipeline, en négligeant que les données sources, l'environnement d'exécution, et la configuration doivent être versionnés avec la même rigueur pour obtenir une reproductibilité réellement complète.

MODULE 03 / 08

Versionner les données elles-mêmes

Ce module traite la seconde catégorie de non-reproductibilité identifiée au module 1 : même avec un code parfaitement versionné (module 2), un pipeline reste non reproductible si les données sources changent sans traçabilité — un problème qui nécessite des outils et pratiques spécifiques, distincts de Git.

LEÇON 3.1Pourquoi versionner les données, pas seulement le code

Rappel direct du cours 20 (module 7, leçon 7.5) et du cours 21 (module 7, leçon 7.5) : le versionnement de datasets a déjà été établi comme une pratique nécessaire dans le contexte du fine-tuning. Ce module généralise ce même principe à toute donnée utilisée par un pipeline de transformation, pas seulement aux datasets d'entraînement.

Pourquoi Git seul ne suffit pas pour versionner des données : Git est conçu pour du TEXTE relativement compact (code source) — il gère mal des fichiers volumineux ou binaires (rappel cours 13, sur les bases de données vectorielles ; cours 14, sur des documents scannés), avec un historique qui grossit rapidement et devient inefficace Les données évoluent souvent selon un rythme et une logique différents du code — une source externe peut se mettre à jour indépendamment de toute modification du pipeline (rappel cours 18, sur le cycle de vie des données statiques) → Un système DÉDIÉ au versionnement de données (approfondi à la leçon 3.2) gère ces contraintes spécifiques mieux qu'un usage détourné de Git conçu à l'origine pour du code

Cette distinction rejoint directement le même principe déjà établi au cours 18 (module 2, sur le cycle de vie des données statiques) : les données, tout comme le code, ont un cycle de vie propre — version, mise à jour, obsolescence — qui mérite d'être tracé explicitement, avec des outils adaptés à leur volume et à leur nature, plutôt que traité comme un simple sous-produit du versionnement de code.

Piège courant Considérer que verser des données dans un dépôt Git au même titre que du code suffit à les versionner correctement — cette pratique fonctionne pour de petits fichiers mais devient rapidement problématique pour des données volumineuses (rappel cours 13-14), avec un historique Git qui grossit de façon disproportionnée et des performances qui se dégradent.

Piège courant Conserver systématiquement des versions complètes de données volumineuses à chaque mise à jour, sans envisager de stratégie de stockage différentiel ou d'archivage pour les versions plus anciennes — un coût de stockage qui peut croître de façon disproportionnée à mesure que les versions s'accumulent, sans bénéfice proportionné pour des versions rarement consultées.

LEÇON 4.1Sources de non-déterminisme

Cette leçon détaille les catégories de non-déterminisme les plus fréquentes dans un pipeline de transformation de données, en s'appuyant sur des exemples concrets déjà rencontrés dans cette série.

Les quatre catégories principales de non-déterminisme : ALÉATOIRE NON CONTRÔLÉ (approfondi leçon 4.2) Rappel cours 20, module 7, leçon 7.1 — un split train/validation/test qui mélange aléatoirement les exemples sans graine fixée produira une répartition DIFFÉRENTE à chaque exécution DÉPENDANCE AU TEMPS D'EXÉCUTION (approfondi leçon 4.3) Un pipeline qui utilise la date ou l'heure courante (par exemple, pour calculer un âge de document ou une péremption, rappel cours 18, module 2) produit nécessairement un résultat différent selon le MOMENT où il s'exécute ORDRE DE TRAITEMENT NON GARANTI Un traitement PARALLÈLE de plusieurs éléments (rappel cours 17, module 6, leçon 6.2, sur les appels en parallèle) peut, selon l'implémentation, produire un résultat dans un ORDRE différent d'une exécution à l'autre DÉPENDANCES EXTERNES VOLATILES (approfondi leçon 4.4) Rappel cours 18 — un appel à une API externe ou à un service temps réel peut renvoyer une valeur différente d'un instant à l'autre, indépendamment du pipeline lui-même

import random
import numpy as np

def fixer_toutes_les_graines(graine: int = 42) -> None:

    de fixation de graine déjà appliqué au split train/test,
    généralisé ici à TOUTES les sources d'aléatoire d'un
    pipeline, pas seulement à la division finale du dataset."""
    random.seed(graine)
    np.random.seed(graine)
    # Toute autre bibliothèque utilisant l'aléatoire (un
    # framework de machine learning, par exemple) nécessite
    # sa PROPRE fixation de graine, spécifique à son API
Piège fréquent : fixer UNE seule graine, en oubliant que plusieurs bibliothèques maintiennent chacune leur PROPRE générateur aléatoire indépendant : random.seed(42) → fixe le module random natif de Python np.random.seed(42) → fixe NumPy, un générateur DISTINCT torch.manual_seed(42) → fixerait PyTorch, un troisième générateur, si utilisé → Oublier UNE SEULE de ces fixations, si la bibliothèque correspondante est utilisée quelque part dans le pipeline, suffit à réintroduire du non-déterminisme malgré les autres graines correctement fixées

Ce piège de fixation partielle est particulièrement insidieux : un pipeline peut sembler déterministe lors d'un test superficiel (si le générateur non fixé n'est utilisé que dans une étape secondaire rarement examinée), tout en produisant occasionnellement des résultats différents dès que cette étape entre en jeu de façon plus visible.

Piège courant Fixer la graine d'une seule bibliothèque (par exemple, le module random natif de Python) en supposant que cela suffit à garantir un déterminisme complet, alors que d'autres bibliothèques utilisées dans le même pipeline (NumPy, un framework de machine learning) maintiennent chacune leur propre générateur indépendant, nécessitant sa propre fixation explicite.

LEÇON 4.3Neutraliser les dépendances au temps et à l'environnement

Rappel direct du cours 18 (module 2, sur le cycle de vie des données statiques) : un pipeline qui calcule une valeur relative au temps courant (âge d'un document, péremption d'une donnée) produit nécessairement un résultat différent selon le moment exact de son exécution — un problème distinct de l'aléatoire (leçon 4.2) mais tout aussi problématique pour la reproductibilité.

# NON REPRODUCTIBLE : dépend du moment EXACT de l'exécution
def calculer_anciennete_document(date_creation, maintenant=None):
    maintenant = maintenant or datetime.utcnow()  # varie à chaque appel !
    return (maintenant - date_creation).days

# REPRODUCTIBLE : le "moment de référence" est un PARAMÈTRE
# explicite (rappel module 2, leçon 2.4, sur la paramétrisation),
# pas une valeur implicite du système au moment de l'exécution
def calculer_anciennete_document(date_creation, date_reference: datetime) -> int:
    """Rappel module 2, leçon 2.4 — la date de référence devient
    un paramètre EXPLICITE, enregistré à chaque exécution
    (rappel leçon 3.3, sur les métadonnées d'exécution) plutôt
    qu'implicitement dérivé du moment d'exécution."""
    return (date_reference - date_creation).days
Principe général : transformer une dépendance IMPLICITE au temps d'exécution en un PARAMÈTRE explicite AVANT (implicite) APRÈS (explicite, reproductible) ──────────────────────── ──────────────────────── datetime.utcnow() appelé Une date de référence, DIRECTEMENT dans la logique déterminée UNE FOIS au de transformation début du pipeline, passée EXPLICITEMENT à chaque Chaque appel peut retourner fonction qui en a besoin une valeur LÉGÈREMENT différente selon le moment Rejouer le pipeline avec la exact d'exécution MÊME date de référence produit exactement le MÊME résultat

Ce même principe s'étend au-delà du temps : toute valeur dépendant de l'environnement d'exécution (le nom de la machine, une variable d'environnement, la locale du système) devrait suivre la même logique — capturée explicitement en paramètre plutôt que lue implicitement depuis l'environnement au moment de l'exécution.

Piège courant Appeler directement une fonction de date/heure système (comme datetime.utcnow()) au cœur de la logique de transformation, plutôt que de capturer une date de référence explicite au démarrage du pipeline et de la propager comme paramètre — cette pratique rend le résultat du pipeline dépendant du moment exact de son exécution, empêchant toute reproduction fidèle ultérieure.

Stratégies pour isoler cette dépendance externe : CAPTURER LA RÉPONSE ET LA VERSIONNER (rappel module 3) Enregistrer la réponse exacte reçue d'un service externe au moment de l'exécution, versionnée comme n'importe quelle autre donnée d'entrée — permet de REJOUER le pipeline avec cette même réponse capturée, sans dépendre d'un nouvel appel MOCKER LE SERVICE EXTERNE POUR LES TESTS (approfondi module 5) Remplacer l'appel réel par une réponse simulée et contrôlée lors des tests (module 5), pour isoler la logique de traitement de la volatilité du service externe lui-même DISTINGUER PIPELINE DE PRODUCTION ET PIPELINE REJOUABLE Le pipeline de PRODUCTION peut légitimement appeler le service en direct (rappel cours 18) ; un pipeline REJOUÉ à des fins de diagnostic ou de test devrait utiliser la réponse CAPTURÉE plutôt qu'un nouvel appel en direct

Cette distinction entre pipeline de production (qui peut légitimement dépendre de données fraîches, rappel cours 18) et pipeline rejoué à des fins de diagnostic ou de test est essentielle : la reproductibilité, au sens de ce cours, ne cherche pas à éliminer toute dépendance externe en production, mais à garantir qu'une exécution PASSÉE puisse être fidèlement reconstituée pour investigation.

Piège courant Chercher à éliminer complètement toute dépendance à des services externes volatiles dans un pipeline de production, alors que l'objectif réel de la reproductibilité est de pouvoir REJOUER une exécution passée de façon fidèle — la solution réside dans la capture et le versionnement des réponses obtenues, pas dans le refus d'utiliser des données temps réel en production.

LEÇON 4.5Vérifier le déterminisme : rejouer un pipeline et comparer les résultats

Cette dernière leçon du module traite un principe déjà esquissé à la leçon 1.5 (erreur 4) : la reproductibilité ne devrait jamais être supposée, mais vérifiée empiriquement — en rejouant effectivement le pipeline avec les mêmes entrées et en comparant le résultat obtenu à une exécution de référence.

def verifier_determinisme(fonction_pipeline, entrees_test, nombre_executions: int = 3) -> bool:
    """Rejoue le MÊME pipeline plusieurs fois avec les MÊMES
    entrées, et vérifie que le résultat est IDENTIQUE à chaque
    fois — la seule vérification empirique fiable du
    déterminisme, plutôt qu'une simple inspection du code."""
    resultats = [fonction_pipeline(entrees_test) for _ in range(nombre_executions)]
    premier_resultat = resultats[0]
    return all(resultat == premier_resultat for resultat in resultats)
Pourquoi cette vérification empirique reste nécessaire, même après avoir appliqué les principes des leçons 4.2-4.4 : Une inspection MANUELLE du code peut manquer une source de non-déterminisme subtile (rappel leçon 4.1, sur l'ordre de traitement parallèle) — REJOUER effectivement le pipeline et COMPARER les résultats reste la seule preuve empirique fiable Cette vérification devrait elle-même devenir un TEST AUTOMATISÉ (approfondi au module 5), exécuté régulièrement plutôt qu'une vérification ponctuelle effectuée une seule fois

LEÇON 5.1Pourquoi tester un pipeline de données comme on teste du code

Rappel direct du cours 23 (module 7, leçon 7.3) : un schéma de validation, en tant que code, mérite ses propres tests. Ce principe s'étend naturellement à l'ensemble d'un pipeline de transformation — chaque fonction de traitement (rappel module 2, leçon 2.2, sur la modularité) constitue un candidat pour un test automatisé, au même titre que n'importe quelle fonction logicielle.

Pourquoi un pipeline de données mérite les mêmes standards de test qu'un logiciel classique : Une fonction de NETTOYAGE (rappel cours 11) peut avoir un bug qui ne se manifeste que sur certains cas particuliers (caractères spéciaux, encodages inhabituels) — un test automatisé détecte cette régression avant qu'elle n'affecte la production Une fonction de CHUNKING (rappel cours 9) modifiée pour corriger un cas peut, sans le vouloir, casser un autre cas déjà correctement géré auparavant — un test empêche cette régression silencieuse → Sans tests automatisés, chaque modification du pipeline repose sur la seule VIGILANCE humaine pour détecter une régression — une garantie bien plus fragile qu'une suite de tests exécutée systématiquement

Ce principe rejoint directement celui déjà établi à la leçon 1.5 (erreur 3) : une vérification manuelle ponctuelle, aussi rigoureuse soit-elle au moment où elle est effectuée, ne protège en rien contre une régression future introduite par une modification ultérieure du pipeline — seuls des tests automatisés, exécutés systématiquement, offrent cette garantie continue.

Piège courant Considérer qu'un pipeline de données, parce qu'il "fonctionne" au moment de sa mise en place, n'a pas besoin de la même rigueur de test qu'un logiciel applicatif classique — cette distinction est artificielle : un bug dans une fonction de transformation de données a des conséquences tout aussi réelles qu'un bug dans n'importe quel autre code, souvent plus difficiles à détecter car silencieuses (rappel cours 23, module 1, leçon 1.1).

LEÇON 5.3Tests d'intégration sur le pipeline complet

Au-delà des tests unitaires (leçon 5.2), qui vérifient chaque fonction isolément, les tests d'intégration vérifient que l'ensemble des fonctions, assemblées dans le pipeline complet, produisent un résultat cohérent de bout en bout — un niveau de test complémentaire, pas substituable au précédent.

Pourquoi les tests unitaires seuls ne suffisent pas : Chaque fonction individuelle peut PASSER ses propres tests unitaires (leçon 5.2), tout en étant mal INTÉGRÉE avec les autres — par exemple, si "nettoyer_texte" retourne un format que "decouper_en_chunks" n'attend pas correctement → Les tests d'INTÉGRATION vérifient spécifiquement cette COMPATIBILITÉ entre les étapes du pipeline, un problème invisible si l'on ne teste que chaque fonction isolément

Cette distinction entre tests unitaires et tests d'intégration rejoint un principe déjà établi implicitement au cours 20 (module 8, leçon 8.2, sur le pipeline complet) : vérifier chaque composant individuellement ne garantit pas que l'assemblage complet fonctionne correctement — les deux niveaux de test sont nécessaires et complémentaires, ni l'un ni l'autre suffisant seul.

Piège courant Se contenter de tests unitaires exhaustifs sur chaque fonction individuelle, en supposant que leur bon fonctionnement isolé garantit automatiquement un pipeline complet fonctionnel — l'intégration entre plusieurs fonctions correctes individuellement peut malgré tout révéler des incompatibilités invisibles au niveau unitaire.

MODULE 06 / 08

Tests de non-régression et de bout en bout

Ce module approfondit une catégorie de test spécifique, complémentaire aux tests unitaires et d'intégration du module 5 : détecter qu'une modification du pipeline a changé un résultat de façon non intentionnelle — un problème directement lié à la reproductibilité au cœur de ce cours.

LEÇON 6.1Détecter qu'une modification a changé le résultat sans le vouloir

Une régression désigne un changement de comportement non intentionnel introduit par une modification du code — le pipeline continue de "fonctionner" au sens où il ne plante pas, mais produit un résultat différent de celui attendu, souvent sans que personne ne s'en aperçoive immédiatement.

Pourquoi les tests unitaires (module 5) ne suffisent pas toujours à détecter une régression : Un test unitaire vérifie qu'une fonction respecte des propriétés CONNUES À L'AVANCE (rappel module 5, leçon 5.2) Une régression peut affecter un aspect du résultat qui n'était PAS explicitement couvert par un test existant — un changement subtil de FORMATAGE, un ordre différent des éléments, une légère variation numérique qui ne viole aucune règle testée mais diffère malgré tout du résultat attendu → Détecter ce type de changement nécessite de COMPARER le résultat complet à une RÉFÉRENCE connue, plutôt que de vérifier seulement des propriétés partielles (approfondi à la leçon 6.2, sur le snapshot testing)

Ce risque rejoint directement le principe déjà établi au cours 21 (module 6, leçon 6.5, sur la vérification après correction) : toute modification, même bien intentionnée, mérite une vérification explicite de son impact réel — une intuition qui "ça devrait marcher" ne remplace jamais une comparaison effective avec un résultat de référence.

Piège courant Supposer qu'une modification du pipeline, ayant passé tous les tests unitaires existants (module 5), ne peut pas avoir introduit de régression — les tests unitaires ne couvrent que les propriétés explicitement vérifiées, laissant place à des changements de comportement subtils sur des aspects non couverts par la suite de tests existante.

LEÇON 6.2Snapshot testing : comparer une sortie à une référence connue

Le snapshot testing (test par capture d'instantané) répond directement à la limite identifiée à la leçon 6.1 : capturer le résultat complet d'un pipeline à un instant T comme référence, puis comparer chaque exécution future à cette référence exacte, signalant toute divergence — même celles non anticipées par des tests unitaires explicites.

    du pipeline pour une entrée de référence, et le compare
    à un SNAPSHOT enregistré précédemment, détectant TOUT écart
    plutôt que seulement les propriétés explicitement vérifiées
    par des tests unitaires (rappel leçon 6.1)."""
    resultat_actuel = pipeline_chunking(DOCUMENT_DE_REFERENCE)
    with open("snapshots/chunking_reference.json") as f:

Cycle de vie d'un snapshot test : 1. PREMIÈRE EXÉCUTION : le résultat du pipeline est capturé et enregistré comme snapshot de référence (après une revue humaine confirmant qu'il est correct) │ ▼ 2. EXÉCUTIONS SUIVANTES : le nouveau résultat est comparé AUTOMATIQUEMENT au snapshot enregistré │ ┌───────────┴───────────┐ ▼ ▼ IDENTIQUE DIFFÉRENT → test réussi → ALERTE : soit une RÉGRESSION (à corriger), soit un changement VOULU (le snapshot doit alors être mis à jour intentionnellement, rappel leçon 6.5)

Ce mécanisme rejoint directement le concept déjà établi au module 4 (leçon 4.5, sur la vérification empirique du déterminisme) : plutôt que de faire confiance à une inspection manuelle du code, comparer effectivement un résultat à une référence connue constitue la seule preuve fiable qu'aucun changement non intentionnel ne s'est produit.

Piège courant Mettre à jour un snapshot de référence automatiquement dès qu'un test échoue, sans jamais examiner si la différence détectée constitue une régression réelle ou un changement voulu — cette pratique transforme le snapshot testing en une vérification purement mécanique, perdant sa valeur de détection si les différences ne sont jamais réellement examinées avant validation.

LEÇON 7.1Exécuter les tests automatiquement à chaque changement (CI)

Ce mécanisme rejoint directement le principe déjà établi au cours 23 (module 6, leçon 6.2, sur la stratégie de blocage) : tout comme une validation de données peut bloquer un pipeline en cas de violation critique, un système de CI peut bloquer l'intégration d'une modification de code qui ferait échouer la suite de tests — une même logique de garde-fou automatisé, appliquée ici au cycle de développement plutôt qu'à l'exécution du pipeline en production.

LEÇON 7.3Gérer les environnements de test, staging, production

Les trois environnements typiques et leur rôle : TEST (ou développement) Exécution locale ou dans un environnement isolé, avec des données de test (rappel module 5, leçon 5.4, sur les fixtures) — le lieu où les tests des modules 5-6 s'exécutent en premier lieu STAGING (pré-production) Exécution dans un environnement proche de la production réelle, souvent avec un sous-ensemble de données réelles (rappel module 6, leçon 6.4, sur l'échantillonnage) — un dernier filet de sécurité avant le déploiement complet PRODUCTION Exécution réelle, sur l'intégralité des données, avec un impact direct sur les utilisateurs ou systèmes en aval — atteinte seulement après validation dans les deux environnements précédents

LEÇON 8.3Étude de cas : rendre reproductible un pipeline RAG

Contexte

Reprenant le pipeline RAG déjà construit aux cours 9-13 et déjà partiellement validé au cours 23 (module 8, leçon 8.3) : une équipe souhaite le rendre pleinement reproductible et testé, après avoir constaté que deux exécutions successives, sur les mêmes documents sources, produisaient des chunks légèrement différents.

Diagnostic et application du cours à ce contexte : DIAGNOSTIC (module 4, leçon 4.1) : l'équipe découvre que le chunking (cours 9) utilise un découpage par similarité sémantique impliquant un tirage aléatoire non maîtrisé pour départager des cas ambigus — une source de non-déterminisme non identifiée jusqu'ici CORRECTION (module 4, leçon 4.2) : fixation explicite de la graine aléatoire utilisée par cette étape de chunking VERSIONNEMENT (modules 2-3) : le corpus documentaire est versionné avec DVC, lié à la version de code du pipeline via un enregistrement conjoint (module 3, leçon 3.3) TESTS AJOUTÉS (modules 5-6) : un test unitaire vérifie que le chunking respecte la taille maximale (module 5, leçon 5.2), et un snapshot test capture le résultat complet sur un document de référence pour détecter toute régression future (module 6, leçon 6.2) VÉRIFICATION EMPIRIQUE (module 4, leçon 4.5) : le pipeline est rejoué trois fois sur les mêmes documents, confirmant un résultat désormais IDENTIQUE à chaque exécution

Cette étude de cas illustre comment ce cours 24 complète directement le cours 23 sur ce même pipeline RAG : la validation de données (cours 23) avait déjà vérifié la conformité des documents en entrée, mais n'avait pas révélé ce problème de non-déterminisme, propre au PROCESSUS de transformation lui-même plutôt qu'au contenu des données.

Piège courant Face à des résultats légèrement différents entre deux exécutions, chercher la cause uniquement du côté des données (en supposant qu'elles ont changé) sans envisager qu'une source de non-déterminisme interne au pipeline lui-même (module 4) pourrait expliquer cette variation, malgré des données sources rigoureusement identiques.
